# タスクの開発実行

あなたは経験豊富なソフトウェア開発者です。詳細設計に基づいて開発を進めます。

タスク「$ARGUMENTS[0]」の開発を開始します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク指定子）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。**カンマ区切りで複数のタスクを指定できます**（例: `task1,task2,task3`）。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します（**単一タスク指定時のみ**） |

**引数全体**: `$ARGUMENTS`

### 実行モードの判定【共通ブロックより先に評価】

**この判定は、次節「重要: `--team` の有無による分岐【最優先】」よりも先に行ってください。** 実行モードが決まらないと `--team` の扱いが確定しないためです。

第1引数（タスク指定子）を以下の規則でパースし、`mode`（single / multi）・`tasks[]`（タスク名の配列・入力順）・`team_enabled`（真偽値）を確定させます。

| # | 規則 | 具体 |
|---|------|------|
| AP-1 | 先頭トークンをタスク指定子、2 番目以降をフラグとして扱う | `task1,task2 --team` → 指定子 `task1,task2` / フラグ `--team` |
| AP-2 | 指定子にカンマを含めば **複数タスクモード**、含まなければ **単一タスクモード** | 後方互換の分岐点。カンマがなければ以降の挙動は従来と完全に同一 |
| AP-3 | 区切り文字は `,` のみ。カンマ前後の空白は **エラー** | `task1, task2` は空白で 2 トークンに割れ、2 番目が既知フラグでないため AP-6 でエラー |
| AP-4 | 空要素は **エラー** | `task1,,task2` / `task1,task2,` / `,task1` |
| AP-5 | タスク名は `^[A-Za-z0-9._-]+$` に一致すること。`.` のみ／`..` を含むものは **エラー** | パストラバーサル・コマンド注入の防止 |
| AP-6 | 2 番目以降のトークンが既知フラグ以外なら **エラー**。**既知フラグは `--team` のみ**であり、`--tema` / `--no-review` / `--review-only` のような未知フラグは**黙って無視せずエラー**とする | 空白混入の検出を兼ねる。黙って無視すると `--tema` のような誤記が既定の実行経路へ落ちるが、本スキルはレビュー・修正ループで**リポジトリ本体のコードを書き換える**ため、従来「何も起きない」で済んだものが「意図しない変更」になる |
| AP-7 | 同一タスク名の重複は先頭 1 件のみ採用し、重複分は警告のうえ除去 | 報告を明快にするための事前除去 |
| AP-8 | **複数タスクモードかつ `--team` 指定時は `--team` を無視**し、警告を表示して続行 | コンテキスト分離を優先。理由は下記 |

> **レビューを省略する導線は提供していません。** `--no-review` / `--review-only` に相当するオプションは存在せず、レビュー・修正ループは常に実行されます。

**エラー時は即時終了してください**（ファイル作成・git 操作を一切行わない）。**この即時終了は「ステップ0: 全フェーズを Task として登録する」よりも前**に行います（登録してから落ちると、実行されないフェーズが進捗表示に残るため）。

タスク指定子が不正な場合に表示する文言:

```
❌ タスク指定が不正です: <理由>
   - カンマ区切りは空白なしで指定してください（例: task1,task2,task3）
   - 空の要素（連続カンマ・先頭/末尾カンマ）は指定できません
   - タスク名に使用できる文字は英数字・ハイフン・アンダースコア・ドットのみです
```

未知フラグを検出した場合に表示する文言（AP-6）:

```
❌ 不明なオプションです: <トークン>
   このスキルが受け付けるオプションは --team のみです。
   （--no-review / --review-only 相当のオプションはありません。レビュー・修正ループは常に実行されます）
```

AP-8 に該当する場合に表示する警告文言:

```
⚠️ 複数タスク指定時は --team を利用できないため、--team を無視して実行します（理由: タスク実装をサブエージェントへ委譲するため、その内部でチームメイトを spawn できません）。
```

#### 判定順序【この順序で確定させること】

```
(1) 引数トークン列の分解                 ← AP-1
(2) フラグ集合の確定と未知フラグ検出      ← AP-6（エラーなら即時終了。ステップ0 より前）
(3) タスク指定子のパース                 ← AP-3〜AP-5, AP-7
(4) mode の確定（single / multi）         ← AP-2
(5) team_enabled の確定                  ← AP-8（multi なら false へ強制＋警告）
(6) ステップ0: フェーズ登録               ← mode により登録系列が決まる
(7) 「重要: --team の有無による分岐」の評価
```

**モード確定後の扱い**:

| モード | 次節「`--team` の有無による分岐」の評価 | 実行する手順 |
|---|---|---|
| 単一タスクモード | 通常どおり評価する（`--team` があれば Agent Teams モードへ） | ステップ1〜5 |
| 複数タスクモード | **`--team` を「含まれない場合」として評価する**（AP-8 で無視済みのため） | ステップ6（ステップ5 の規約を参照） |

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、各 teammate の成果を `Agent` の **戻り値**（最終メッセージが tool result として返る）で収集し、進捗はチームリード（あなた）が Task（ステップ0 で確定した進捗管理方式）で追跡する暗黙チーム方式で実行します。`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても上記の戻り値方式で成立します。

（注: 旧来のチーム生成／破棄 API は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も `Agent` の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定。`SendMessage` を併用する場合は `name` を付与して宛先を指定できるようにします）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）がステップ0 で確定した方式（Task 方式／フォールバック時はチェックリスト）で追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は `Agent` の戻り値で受け取ります。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

design.md の実装タスク一覧（各 `T-nnn` の **依存** フィールド）から依存関係を分析し、**独立して並行実装できるタスク群**を特定してください。todo.md がある場合は併せて参照してください。

チームメイトに以下のように作業を分担してください:

- **並行実装**: 依存関係がないタスクは異なるチームメイトに割り当てて並行実装
- **順次実装**: 依存関係があるタスクはチームリード（あなた）が順次実装
- **各チームメイトへの指示**: 対象ファイル、実装内容、コーディング規約を明確に伝達

**重要**: 各チームメイトが同じファイルを同時に編集しないよう、ファイル単位で作業を分割してください。

##### レビューフェーズの役割分担（`--team` の適用対象）

`--team` 有効時、レビューは**3体を同一メッセージ内で並列 spawn** し、レビュー観点（下記「レビュー観点」の5観点）を次のとおり分割します:

| 担当 | 観点 |
|---|---|
| 担当A | ①要件定義との整合性 ②設計書との整合性 ＋ ③実装タスクの完了状況 |
| 担当B | ④コード品質（可読性・保守性・エラーハンドリング・テストの有無と網羅性） |
| 担当C | ⑤セキュリティ・堅牢性 |

- チームリード（あなた）が行ってよいのは**重複排除・優先度の統一・`R-nnn` の採番統一のみ**です。**指摘の取捨選択は行いません**（RI-5）。
- **レビュー担当の構成をループ間で変えないこと**（LC-7）。`--team` 有効なら毎パス3体、無効なら毎パス1体を維持します。構成を変えると観点が入れ替わって署名が不安定になり、停滞判定（EA-1）が原理的に働きません。
- 一部の担当しか稼働しなかった場合は稼働分で続行し、欠けた観点を dev-result.md へ明記します（E-15）。0体なら共通ブロックのフォールバック文言を表示したうえで、**レビュー委譲そのものは別途1体で試行します**（Agent Teams のフォールバック＝レビューの自己化ではありません。E-25）。

##### 修正フェーズは `--team` の適用対象外

**修正は単一エージェントが逐次行います**（RI-8。単一タスクモードではチームリード自身、複数タスクモードでは単一の修正サブエージェント）。並列化すると共有資源が競合し、どの修正がどの指摘に対応したのかが失われて終了保証が成立しなくなるためです。

#### 統合

チームリード（あなた）は全チームメイトの成果を統合し、動作確認を行った上で dev-result.md を作成してください。

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/dev-result.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/dev-result.md`

**複数タスクモードの場合**: タスクごとにパスが変わるため、以降は `<TASK>`（ループ中の対象タスク名）を用いて表記します。

- `<PROJECT_ROOT>/.claude/tasks/<TASK>/design.md`
- `<PROJECT_ROOT>/.claude/tasks/<TASK>/todo.md`（存在する場合）
- `<PROJECT_ROOT>/.claude/tasks/<TASK>/dev-result.md`

成果物 `dev-result.md` は、**タスクごとのディレクトリ配下にそれぞれ作成**します。

## 手順

### ステップ0: 全フェーズを Task として登録する【FR-1: フロー強制】

本スキルの手順に着手する前に、進捗管理用の Task ツールをロードしてください
（deferred tool のため、ロードしないと呼び出せません）。この ToolSearch は進捗管理のための
ものであり、Agent Teams とは無関係です（`--team` の有無にかかわらず実行します）。

```
ToolSearch query="select:TaskCreate,TaskUpdate,TaskList,TaskGet" max_results=10
```

判定は **スキル実行あたり1回だけ** 行い、フェーズごとに繰り返さないこと。

| ToolSearch の結果 | 進捗管理の方式 |
|---|---|
| `<functions>` ブロックに `TaskCreate` / `TaskUpdate` が含まれる | **Task 方式**（主経路） |
| 含まれない、または ToolSearch がエラー終了 | **チェックリスト方式**（フォールバック） |

**Task 方式（主経路）**: 下記の全フェーズを `TaskCreate` で1件ずつ登録し、各フェーズの着手時に
`TaskUpdate` で `in_progress` へ、完了時に `completed` へ遷移させます。`subject` はフェーズ名
（imperative 形）、`description` にはそのフェーズで行うことを1文で記述します。

**チェックリスト方式（フォールバック）**: 下記の全フェーズを `- [ ]` 形式のチェックリストとして
応答中に宣言し、各フェーズの完了直後にチェックリストを再掲して `- [x]` へ更新します。
**フォールバックしたことを告知するメッセージは表示しないでください**（チェックリスト自体が
進捗表示を兼ねます）。

いずれの方式でも登録（宣言）は **省略不可** です（成果物の必須要素）。列挙順に実行し、
どのフェーズもスキップ・前倒しをしないこと。

登録するフェーズは **実行モード（「実行モードの判定」節で確定させたもの）によって異なります**。該当する側のみを登録してください。

**単一タスクモードのフェーズ**（この順序・各項目は imperative 形・**12件**）:

1. プロジェクトルートを pwd で解決する
2. レビュー・修正ループを含む実行であることを警告表示する
3. design.md を読み込む（todo.md があれば併せて読む）
4. dev-result-template.md を読み込む
5. dev-result.md を初期化する（実装タスク一覧からチェックリスト抽出）
6. 実装タスクを順に実装する（着手時に下記「実装タスクの動的追加」を行う）
7. 実装フェーズの結果を dev-result.md へ追記する
8. レビュー担当への入力集合を確定する（req.md・design.md・レビュー対象ファイルのパス）
9. レビュー・修正ループを実行する（1周ごとに下記「確認パスの動的追加」を行う）
10. ループの終了理由と未解消の指摘を dev-result.md へ追記する
11. dev-result.md を完成させメタ情報を追記する
12. 実行結果を報告する（ループ周回数・未解消の `R-nnn`・レビュー隔離の成否）

**複数タスクモードのフェーズ**（この順序・各項目は imperative 形・**7件**）:

1. プロジェクトルートを pwd で解決する
2. 引数をパースし対象タスク一覧を確定する
3. 事前検証を実行する（git 清浄性・成果物の存在・完了済みの検出）
4. コスト警告を表示する
5. 実装対象の件数を表示する
6. タスクごとに実装・レビュー・修正を委譲しコミットする（着手時に下記「実装タスクの動的追加」を行う）
7. 実行結果サマリを報告する

> **警告フェーズの位置**: コスト警告の目的は**トークンを費やす前に予算を告知する**ことです。単一タスクモードでは design.md の読解と実装が最大の消費源のため pwd の直後に置き、複数タスクモードでは事前検証で中断する経路（V-1〜V-3）が警告より前にあるほうがよい（中断するなら警告は不要な情報）ため、事前検証の**後**・件数表示の**前**に置きます。

> **件数削減のための統合を行わないこと。** 上記の件数は、実行主体が移動しただけのフェーズ（レビュー担当が自身の応答内で管理するもの）と、対象そのものが廃止されたフェーズを整理した結果です。**相異なるフェーズを1つへまとめてはいけません。**

#### 確認パスの動的追加

固定フェーズ「レビュー・修正ループを実行する」に対し、**確認パス1周ごとに次を動的追加**します（`TaskCreate`。フォールバック時はチェックリスト項目として追加）。

| 追加タイミング | `subject` |
|---|---|
| パス `i` の開始時（カウンタを `i` へインクリメントした直後） | `[review pass <i>/3] レビューを委譲し指摘を集約する` |
| そのパスで `修正必須` が1件以上あった場合のみ | `[fix pass <i>/3] 修正必須の指摘を修正する` |

- **パス内の個別項目（各 `R-nnn` の修正）は Task 化しません**（項目数が入力依存で発散するため）。
- 早期中断した場合、**進行中のパスは `in_progress` のまま残します**（`deleted` は「不要になった」を意味し失敗を表さないため使いません）。
- **複数タスクモードではパス Task を追加しません**（ループは委譲先の内部で回るため）。既存の `[task <i>/<N>]` のみを保持し、文言も変えません。

> **禁止事項**: (a) Task 登録／チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 状態遷移（`completed` 化・完了マーク更新）の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が自身の
> Task 一覧（フォールバック時はチェックリスト）で全フェーズを追跡してください。チームメイトへ
> 委任した作業は `Agent` の戻り値で完了を確認してから `completed` へ遷移させます。

#### ステップ4 の直前: 実装タスクの動的追加【FR-1】

dev-result.md 初期化（ステップ3 / フェーズ4）が完了したら、実装を始める前に、ステップ1 で抽出した
各実装タスクを 1 件ずつ `TaskCreate` で追加してください（フォールバック時はチェックリスト項目として
追加します）。以降、各タスクの着手時に `in_progress`、完了時に `completed` へ遷移させます。
全タスクが `completed` になったことを確認してから、固定フェーズ「実装タスクを順に実装する」を
`completed` にしてください。

- `subject` の接頭辞は**抽出元によって使い分けます**:

  | 抽出元 | `subject` の形式 | 例 |
  |---|---|---|
  | design.md の `## 12. 実装タスク一覧`（識別子あり） | **`[T-nnn] <タスク名>`** | `[T-003] 認証ミドルウェアを実装する` |
  | todo.md（識別子なし） | `[todo <i>/<N>] <todo のタスク名>` | `[todo 3/9] 認証ミドルウェアを実装する` |

  **両方を読む A-4 では `T-nnn` 系列を採用し**、todo.md にしかない項目のみ `[todo <i>/<N>]` で補ってください。
  `TaskCreate` に親子関係の指定がないため、階層は subject の接頭辞で表現します。
  `addBlocks` / `addBlockedBy` は依存関係の意味論であり、階層表現には使いません。
- 件数 `<N>` は実行時に入力ファイルを読んで初めて判明するため、件数は固定せず「各タスクを追加せよ」
  という指示の形を取ります。
- `--team` 有効時は、担当チームメイト名を `description` に付記し、チームリード（あなた）の
  Task 一覧で進捗を追跡します。
- **複数タスクモードの場合**は、todo.md の個々の実装タスクではなく **対象タスク名そのもの**
  （`<TASK>` ごとに 1 件）を `subject` = `[task <i>/<N>] <TASK> を実装する` として登録してください。
  todo.md の各実装タスクの追跡は、委譲先のサブエージェントが自身の応答内で行います
  （サブエージェントによる Task ツールの利用は禁止します）。

## 権限の切替線【実装フェーズ ↔ レビュー・修正フェーズ】

**境界の位置**: 「実装フェーズの最後の `T-nnn` が完了し、`dev-result.md` の実装セクション（実装概要・変更ファイル一覧・技術的な実装詳細）を書き終えた時点」。

| モード | 具体的な位置 |
|---|---|
| 単一タスクモード | ステップ4（実装）の完了直後、ステップ5（レビュー・修正ループ）の開始前 |
| 複数タスクモード | **タスクごとに引かれる**。実装委譲が `STATUS: success` を返した直後、当該タスクのコミットの前 |

| 観点 | 実装フェーズ | レビュー・修正フェーズ |
|---|---|---|
| **成果物への権限** | `dev-result.md` を**新規作成・全面上書き**。実装コードは `T-nnn` の範囲で自由に作成・変更 | `dev-result.md` は**末尾追記のみ**（＋ W-3 / W-6 が許す限定編集）。コードは**未解決の `R-nnn`（修正必須）に紐づく箇所のみ**変更可 |
| **`--team` の適用範囲** | **適用対象**（依存関係のないタスクを並行実装） | **レビューにのみ適用**（3体並列）。**修正フェーズは対象外**（単一エージェント逐次） |
| **判定の入力** | req.md / design.md / todo.md / 既存コード / 実装フェーズの全文脈 | **req.md / design.md / 対象ファイルのパス / レビュー観点のみ**（RP-1〜RP-11）。実装フェーズの文脈は入力にも却下の根拠にも用いない |
| **サブエージェント委譲** | 単一: 行わない／複数: **実装そのものを委譲**（必須） | **レビューは委譲が必須**（RI-1）。**修正は単一主体が行い、並列委譲を禁止** |

> **この非対称が必要な理由**: 実装フェーズが `dev-result.md` を全面上書きしてよいのは、そこが実装記録の初回生成だからです。レビュー・修正フェーズが同じ権限を持つと、ループの各周で前周の指摘・却下理由・署名が消え、監査可能性（EA-2）と終了保証がともに失われます。同様に判定の入力を絞らなければ、レビューの構造的隔離が「読まないでください」という指示に退化します。

### ステップ5: レビュー・修正ループ【両モード共通の規約】

実装フェーズの完了後、**レビュー → 修正 → 再レビュー**のループを**最大3周**まで自動実行します。単一タスクモードではチームリード（あなた）がこの節に従って直接ループを回し、複数タスクモードでは**タスクごとに**この節の規約を委譲先へ埋め込んで実行させます（ステップ6-3）。

#### 5-1. コスト警告 W-A【省略・要約禁止・確認入力は求めない】

実装に着手する**前**（単一タスクモードは pwd の直後、複数タスクモードは事前検証の後・件数表示の前）に、次を必ず表示してください。トークンを費やす前に予算を告知することが目的であるため、生成・実装のあとに出しても意味を持ちません。

```
⚠️ 本スキルは実装のあと、レビュー → 修正 → 再レビューのループを最大 3 回まで自動実行します。
   レビューは毎周サブエージェントへ委譲するため、実装のみを行う場合に比べてトークン消費が
   おおむね 1.5〜2.5 倍（--team 指定時は 3 倍前後）になります。
   対象: <TASK 一覧（複数タスクモードでは件数も）> / 上限ループ: 3 回 / レビュー担当: <1 体 | 3 体並列>
   レビューを省略する導線は提供していません。実装のみを行うことはできません。
```

各レビューパスの開始時には、警告記号を使わない進捗行を1行だけ出します:

```
ℹ️ レビュー <n>/3 を実行します（対象: <m> ファイル / 前周の未解決: <k> 件）
```

#### 5-2. レビュー委譲器（RI-1〜RI-8）

**問題の定式化**: 実装・レビュー判定・修正の3工程が同一主体・同一コンテキストで実行されます。実装時に「この設計で要件を満たす」と結論した主体が、レビュー時に「満たしていない」と言うのは**直前の自分の結論の否認**です。したがって**過少指摘（危険側）が構造的に優勢**になります。被害は「要件未充足・脆弱性を含んだ実装が、レビュー済みという記録つきでコミットされること」です。

| # | 規則 |
|---|---|
| **RI-1（必須）** | レビューは `general-purpose` サブエージェント（**同期**・`run_in_background: false`）へ**必ず委譲する**。`--team` の有無にかかわらず1体以上を起動する。メイン会話が自らレビューしてよいのは E-13 / E-14 の degrade 経路のみ |
| **RI-2** | 委譲プロンプトへ含めてよいのは RP-1〜RP-11 のみ（5-3 の限定列挙）。「渡してはならないもの」の情報を1項目でも含めた時点で隔離は失効する |
| **RI-3** | 2周目以降に渡す前周情報は `R-nnn` / 1行要約 / 状態（解消済 / 未解消）に限る。**却下理由・優先度の変更理由・修正の難易度は渡さない** |
| **RI-4** | 委譲先の戻り値は**そのまま採用**する。メイン会話が指摘を**削除・降格することは禁止**する。異議は却下手続き（RI-7）でのみ行える |
| **RI-5** | `--team` 有効時は3体を**同一メッセージ内で並列 spawn** する。メイン会話が行ってよいのは重複排除・優先度の統一・`R-nnn` の採番統一のみであり、**指摘の取捨選択は行わない** |
| **RI-6** | **複数タスクモードでもレビュー委譲を行う**。修正も**別の同期サブエージェントへ委譲**し、メイン会話はループ制御とコミットのみを担う |
| **RI-7** | 却下する場合、**根拠類型 ID（J-1〜J-5）と外部参照可能な証拠**を `dev-result.md` へ必ず記載する。**証拠を書けない却下は却下として認めず、未解決の修正必須として扱う**（fail-safe） |
| **RI-8** | 修正フェーズは**単一エージェント**が行う（`--team` 適用外）。共有資源の競合と終了保証の不成立を避けるため |

> **RI-6 の根拠**: 複数タスクモードは実装をサブエージェントへ委譲しており、メイン会話は `STATUS` / `FILES` / `SUMMARY` の数十行しか受け取っていません。つまり**メイン会話は実装の内心を一度も保持していない**ため、`メイン会話 → [実装 A] → 戻り値 → [レビュー B（A とは別コンテキスト）] → [修正 C] → コミット` の順序が成立し、**単一タスクモードよりも隔離が構造的に強くなります**。ここで自己レビューへ落とすと req.md と全変更ファイルがメイン会話へ流入し、複数タスクモードの存在意義（コンテキストの線形累積の回避）が失われます。

**チームメイト／委譲先への依頼時の禁止事項**: 「重大なものだけ挙げてください」「些細な指摘は不要です」等の**指摘を抑制する方向のバイアス注入を禁止**します。「実装者は熟練している」「設計どおりに実装されているはず」等の**事前の品質評価を伝えることを禁止**します。**指摘件数の上限・目安を伝えることを禁止**します（B-1 の対象範囲の上限は伝えてかまいません。入力の範囲であって出力の抑制ではないためです）。

#### 5-3. 委譲プロンプトの構成（RP-1〜RP-11）

入力の隔離を「指示」ではなく「構造」として成立させるため、プロンプトは次の11項目**のみ**で構成します。**列挙にないものを足さないことが規約です。**

| # | 埋め込む項目 | 隔離上の位置づけ |
|---|---|---|
| RP-1 | プロジェクトルートの絶対パス | 必須 |
| RP-2 | 対象タスク名 `<TASK>` | 必須 |
| RP-3 | `req.md`（必須）/ `design.md`（必須）/ `todo.md`（存在する場合のみ）の絶対パス | **`dev-result.md` を渡さない** |
| RP-4 | **レビュー対象ファイルのパス一覧**（RS-1〜RS-4 で確定した集合） | 渡すのは**パスのみ**。差分・実装意図・変更理由は渡さない |
| RP-5 | レビュー観点（5-5。`--team` 時は担当分のみ） | 必須 |
| RP-6 | 実装タスク一覧の消費契約（`## 12.` の検出手順・`T-nnn` の抽出規則） | 完了照合のため |
| RP-7 | 欠陥類型の固定語彙（5-7） | 署名の安定性に必須 |
| RP-8 | 優先度の判定基準（高＝必須 / 中・低＝推奨） | 停止条件の機械判定に必須 |
| RP-9 | 戻り値フォーマット（5-6）の厳守 | 必須 |
| RP-10 | 禁止事項（5-4） | 必須 |
| RP-11 | 「コードを修正してはならない（読み取りと報告のみ）」 | 修正はメイン会話の責務。委譲先が直すと `R-nnn` と修正の対応が失われる |

**渡してはならないもの（隔離の実体）**:

| 禁止入力 | 理由 |
|---|---|
| `dev-result.md` の内容（実装概要・技術的詳細・動作確認結果） | 実装担当の**自己申告**。「こう実装した理由」を読むと指摘が抑制される |
| 実装フェーズで検討し捨てた代替案・トレードオフ | 直前の自分の結論の追認になる |
| 前周の**却下理由**・優先度の変更理由・修正の難易度 | 渡すと再指摘が抑止され、停滞検知が「収束」に見せかけられる |
| 「軽微な指摘は不要」等の抑制指示、指摘件数の目安・上限 | 過少指摘（危険側）へのバイアス注入 |
| 総合判定の期待値・「問題ないはず」といった前置き | 同上 |
| メイン会話の会話履歴・他タスクの情報 | 隔離の失効 |

> **`dev-result.md` を渡さないことが本設計の要です。** 変更ファイル一覧は `dev-result.md` から**パスの配列としてだけ抽出**して渡してください。これにより隔離が「読まないでください」という指示ではなく「そもそも渡らない」という構造になります。

2周目以降に渡してよい前周情報は **`R-nnn` / 1行要約 / 状態（解消済 / 未解消）** に限ります（RI-3）。あわせて RS-0 の指示（「前周の指摘の解消確認と、修正差分に起因する新規欠陥のみを見る。新しい観点でのレビューは行わない」）を明記します。

#### 5-4. 委譲先への禁止事項（プロンプトへ逐語で埋め込む）

(1) **ファイルの作成・編集・削除を一切行わない**（`Write` / `Edit` / `NotebookEdit` 禁止。読み取り専用のレビューであるため） (2) **git の状態を変更する操作を一切行わない** (3) **他タスクのディレクトリに触れない** (4) **進捗管理用の Task ツールを使用しない**（タスクリストはセッション単位で共有されるためメイン会話の進捗表示を汚染する） (5) **`AskUserQuestion` を使用しない**（サブエージェントの承認はユーザーの承認ではない。判断が必要な点は結論を出さず指摘として報告する） (6) **さらに別のサブエージェントを spawn しない** (7) **修正を提案するにとどめ、修正を実施しない**。

#### 5-5. レビュー観点

①**要件定義との整合性**（req.md の各要件が正しく実装されているか） ②**設計書との整合性**（design.md のアーキテクチャ・コンポーネント設計に従っているか） ③**実装タスクの完了状況**（`T-nnn`。`todo.md` があればその項目も従来どおり照合） ④**コード品質**（可読性・保守性・エラーハンドリング・テストの有無と網羅性） ⑤**セキュリティ・堅牢性**。

`--team` 時の3体は **①②＋③ / ④ / ⑤** に分割します（「役割分担」節を参照）。

#### 5-6. レビュー委譲の戻り値契約（RB-1〜RB-9）

実装委譲の `STATUS:` / `FILES:` / `SUMMARY:` と同じ**行指向・先頭キー方式**を維持します。

```
STATUS: success
VERDICT: 修正必須
FINDINGS: 2
--- L-1
PRIORITY: 高
CLASS: requirement_unmet
LOCATION: src/Auth/Token.php#validate
BASIS: req.md FR-3「失効トークンは 401 を返す」
DETAIL: 失効チェックが未実装のため、期限切れトークンで保護リソースへアクセスできる
FIX: validate() の冒頭で exp クレームを検証し、失効時は 401 を返す
--- L-2
PRIORITY: 中
CLASS: test_missing
LOCATION: tests/AuthTest.php
BASIS: T-004 の完了条件「有効・失効・不正署名の3ケース」
DETAIL: 異常系のユニットテストが存在しない
FIX: 失効・不正署名の2ケースを追加する
OBSERVATIONS:
- 例外階層の設計は design.md §5 に忠実で、既存の命名規約とも一致している
SUMMARY: 要件 FR-3 の失効判定が未実装。他は設計に準拠している。
```

失敗時は `STATUS: failure` ＋ `REASON:` の2行のみ。

| 規約 | 内容 |
|---|---|
| RB-1 | `STATUS` は `success` / `failure` のいずれか。**1行目**に置く |
| RB-2 | 散文の前置き・後置きを付けない（先頭が `STATUS:` で始まること） |
| RB-3 | `VERDICT` は3値。**`PRIORITY: 高` が1件以上なら必ず `修正必須`**、高が0件で中／低が1件以上なら `修正推奨`、0件なら `修正不要`（機械的に決まるため担当の裁量で変えない） |
| RB-4 | 指摘は `--- L-<n>` で区切る。`L-n` は**担当ローカルの序数**であり、`R-nnn` は返さない（採番はメイン会話の責務） |
| RB-5 | 1指摘は `PRIORITY` / `CLASS` / `LOCATION` / `BASIS` / `DETAIL` / `FIX` の**6キー必須**。省略・順序入替を禁止 |
| RB-6 | `CLASS` は 5-7 の9値のみ。語彙外はフォーマット逸脱として扱う |
| RB-7 | `LOCATION` は `<相対パス>` または `<相対パス>#<シンボル名>`。**行番号は書かない**（H-3 と整合） |
| RB-8 | `OBSERVATIONS` は指摘0件でも**必ず出力**する。該当なしなら `- なし` |
| RB-9 | `FINDINGS:` の件数と `--- L-n` ブロック数が一致しない場合はフォーマット逸脱 |

> **`RB-` 接頭辞について**: 操作予算（5-13）が `B-1`〜`B-4` を用いるため、戻り値契約は `RB-`（review return）で区別します。

#### 5-7. 欠陥類型と安定識別子 `R-nnn`

**採番規約【本則・`--team` の有無を問わず適用】**:

| 項目 | 規定 |
|---|---|
| 書式 | `` `R-nnn` ``（3桁ゼロ埋め・`R-001` から） |
| 採番順 | **検出順**（ループ内は指摘の出現順） |
| 欠番 | 許容する |
| 重複 | 禁止 |
| 追番 | 「その時点で存在する最大値 + 1」。**既存番号は振り直さない** |
| 再利用 | **削除した ID は再利用しない** |
| **採番主体** | **呼び出し元（メイン会話）が一元的に行う。委譲先のレビュー担当に `R-nnn` を振らせない** |

> **なぜ採番主体を本則に固定するか**: レビュー担当は入力隔離により前回の指摘を知らないため、同じ欠陥を毎ループ「新規」として報告します。ID の継承を呼び出し元が行わないと、署名が毎ループ別物になり**停滞判定が原理的に働きません**。この規則が `--team` 節にしかないと、単一委譲経路で継承が失われます。

**「実質同一」の判定基準（継承の条件）**: 次の**3要素がすべて一致**した場合に実質同一とみなし、既存 ID を継承します。

| 要素 | 正規化 | 一致条件 |
|---|---|---|
| 対象ファイル | リポジトリ相対パス（`<PROJECT_ROOT>` 接頭辞と `./` を除去） | 完全一致 |
| 対象シンボル | 最も内側の関数／クラス／メソッド名。**Markdown では最も近い見出しのテキスト**（連番を除去: `## 12. 実装タスク一覧` → `実装タスク一覧`） | 完全一致 |
| 欠陥類型 | 下記の閉じた語彙 | 完全一致 |

**継承の妨げにしないもの**: 行番号の変化、要約・詳細の言い回しの違い、優先度の見解差。
**別 ID とするもの**: 同一ファイル・同一シンボルでも欠陥類型が異なる場合（修正の当たり所が別であり、片方だけ解消しうるため）。

**欠陥類型の語彙（この9値のみ。判別不能は `other`）**:

| 値 | 意味 | 既定の優先度 |
|---|---|---|
| `requirement_unmet` | req.md の要件が未実装・部分実装 | 高 |
| `design_deviation` | design.md の設計・規約と異なる実装 | 高 |
| `task_incomplete` | `T-nnn`（または todo.md 項目）が未完了 | 高 |
| `correctness` | ロジック誤り・境界条件・状態遷移の誤り | 高 |
| `security` | 入力検証・認証認可・秘密情報の露出 | 高 |
| `error_handling` | 例外・失敗経路の未処理 | 中 |
| `test_missing` | テストの欠落・網羅不足 | 中 |
| `maintainability` | 可読性・重複・命名・抽象化 | 低 |
| `other` | 上記に当てはまらない | 低 |

語彙を閉じるのは、自由記述だと類型が毎回変わり署名が別物になるためです。副次的効果として**優先度の恣意的な操作を封じます**。英語スネークケースとしたのは、日本語だと中黒・長音・送り仮名の表記ゆれで署名が不安定になるためです。

#### 5-8. 停滞判定の署名（H-1〜H-7）

```
fingerprint = "<R-nnn>|<欠陥類型>|<根拠ハッシュ>"
signature   = sorted(set(fingerprints))   # 順序非依存
```

**署名の算出対象は「区分: 必須」かつ「未解消」の指摘に限ります。** 却下済み・記録のみ（推奨）・保留は毎ループ定数として残り、かつ委譲先が毎回別の言い回しで再掲するため、含めると署名が本来一致すべき場面で不一致になり停滞を見逃します。停止条件（必須0件）と署名の対象を一致させることで、両者が同じ集合を見ます。

**根拠ハッシュ**: **ハッシュ対象に散文を含めません。** 次の4要素を `|` で連結し、正規化したうえで **sha256 の先頭8桁**（小文字16進）とします。

```
hash_input = "<相対パス>|<シンボル>|<欠陥類型>|<根拠アンカー>"
```

`根拠アンカー` は次の3種のいずれか1つ（優先順）: ①**要件 ID**（`FR-5` / `NFR-2` 等） ②**設計の節番号**（`§5-2` / `## 12` 等） ③**該当コードの1行**（正規化済み）。

| # | 正規化規則（この順） |
|---|---|
| H-1 | 小文字化し、連続空白を単一空白へ畳む |
| H-2 | パスは `<PROJECT_ROOT>` 接頭辞・`./` を除去したリポジトリ相対形へ。区切りは `/` |
| H-3 | **行番号・列番号は削除する**（`skill.md:120` → `skill.md`） |
| H-4 | シンボルは最も内側の関数／クラス／メソッド名。Markdown は最も近い見出しテキストから連番・記号を除去 |
| H-5 | 要件 ID・節番号は `大文字英字 + ハイフン + 数字` へ正規化（`fr-5` → `FR-5`） |
| H-6 | コード引用は前後の空白・末尾のカンマ／セミコロンを除去。文字列リテラルの中身は保持する |
| H-7 | 指摘の要約・詳細（散文）は**ハッシュ対象に含めない** |

> **H-3 / H-7 の意図**: レビューの証跡は**モデルが毎回書き起こす散文**であり、そのままでは1文字も同じになりません。行番号を残せば無関係な修正で全指摘の署名が変わり、EA-1 が永久に成立しなくなります。

**順序非依存な比較の実務手順**: ①各 fingerprint を1つの文字列にする ②辞書順にソートし `, ` で連結して1行にする ③`### ループ N` の `- 署名:` 行へその1行をそのまま書く ④次ループでは直前の `- 署名:` 行と新しい行を**文字列として比較する**。

#### 5-9. 指摘の集約（N-1〜N-4）

| 手順 | 内容 |
|---|---|
| N-1 | 受領した各 `L-n` について根拠ハッシュ（5-8）を計算する |
| N-2 | `dev-result.md` に記録済みの `R-nnn` の根拠ハッシュと突合し、**一致すれば既存 ID を継承**する |
| N-3 | 一致しなければ `既存の最大値 + 1` で新規採番する |
| N-4 | `--team` 時は、担当間で根拠ハッシュが一致する指摘を1件へ統合し、優先度は**最も高いもの**を採る |

#### 5-10. 総合判定・優先度・対応語彙・却下

**3値判定の導出（単一の真実源）**:

```
優先度 高       → 区分: 必須
優先度 中 / 低  → 区分: 推奨

必須の未解消 ≥ 1                    → 総合判定: 修正必須
必須の未解消 = 0 かつ 推奨 ≥ 1      → 総合判定: 修正推奨
必須の未解消 = 0 かつ 推奨 = 0      → 総合判定: 修正不要
```

総合判定を独立の入力にせず**優先度から導出**するのは、独立フィールドにすると「指摘は高だが総合判定は修正推奨」という自己矛盾が生じ、停止条件が判定不能になるためです。真実源は各 `R-nnn` の `優先度` ただ1つです。

**停止条件**: `最新ループの署名集合が空である`。署名は「必須かつ未解消」に限定されているため、**`- 署名:` 行が空 ⇔ 修正必須が0件**となり、1行を見るだけで判定できます。

**優先度の引き下げ防止**: 委譲先は `欠陥類型`（閉じた語彙）を返し、優先度は 5-7 の既定表から機械的に決まります。呼び出し元（＝実装した主体）が既定より**引き下げる**場合は却下と同等の監査対象とし、`- 区分変更: 必須 → 推奨（J-n: 根拠）` 行の追加＋`## 終了サマリ` への列挙を必須とします。**引き上げは自由**（監査不要）。

> **これがないと、全指摘を「低」へ付け替えるだけでループを即終了できます。** 過少指摘バイアスが最も安く発現する経路であり、非対称な監査（下げるときだけ説明責任）で塞ぎます。

**`- 対応:` の固定語彙**:

| 値 | 意味 |
|---|---|
| `未着手` | 必須。次の修正フェーズで着手する |
| `修正済（ループN）` | 修正コードを書いた。**再レビュー未通過** |
| `修正済（ループN）→ 再レビュー合格（ループM）` | 解消。チェックボックスを `[x]` にする |
| `記録のみ（推奨のため自動修正しない）` | **推奨の既定値**。このスキルは触らない |
| `保留（要判断）` / `保留（安全境界）` / `保留（スコープ外）` | 自分で修正しない類型。停止判定の対象から除外する |
| `却下（J-n: 根拠）` | 下記 |
| `打ち切り（修正予算超過）` / `未着手（修正予算超過）` | B-2 / B-3 |

**却下の根拠類型（J-1〜J-5・この5つのみ）**:

| # | 類型 | 必須の証拠 |
|---|---|---|
| **J-1** | **事実誤認** — 指摘が前提とするコード・シグネチャ・設定が実在しない | 反証となる**ファイルパス:行番号**と当該箇所の実際の内容の引用 |
| **J-2** | **仕様どおり** — req.md / design.md に明記された仕様に合致する | **req.md または design.md の見出し名と該当記述の引用**（要約不可・原文の引用） |
| **J-3** | **スコープ外** — 今回の `T-nnn` の対象範囲外の既存コードに対する指摘 | 対象範囲である `T-nnn` の一覧と、当該箇所がそこに含まれないことの説明 |
| **J-4** | **既存パターン準拠** — 単独で変更すると一貫性を損なう | **同一パターンの既存箇所を2件以上、パス:行で列挙** |
| **J-5** | **優先度による対象外** — 区分が「推奨」であり自動修正の対象外 | 区分が `推奨` であること（`必須` には適用不可） |

**却下の根拠として認めない語彙（逐語）**: 「実装時にそう判断したため」「意図的な実装である」「設計意図に沿っている」（J-2 の引用を伴わない場合）「動作に影響しない」「実害がない」（コード・テストの提示を伴わない場合）「既存コードもそうなっている」（J-4 の2件以上の提示を伴わない場合）「修正コストが見合わない」「レビュー担当の誤解と思われる」（J-1 の反証を伴わない場合）。

**証拠を書けない却下は却下として認めず、未解決の修正必須として扱います**（fail-safe）。**区分: 必須の却下は J-1 / J-4 に限ります**。J-2 / J-3 / J-5 で必須を却下する場合は `## 終了サマリ` の `- 要件・設計の変更が必要なため未対応:` へ必ず転記してください。

> **却下は「実装フェーズの内心が判定に流入する唯一の出口」です。** J-1〜J-5 はいずれも外部参照可能な証拠（ファイル:行、または原文引用）を要求するため、内心そのものは却下の根拠になり得ません。

#### 5-11. ループ制御（LC-1〜LC-8）・終了条件（S-1〜S-6）・早期中断（EA-1〜EA-5）

| # | 規則 |
|---|---|
| **LC-1** | カウンタ `loop` は各**レビューパスの開始時**にインクリメントする。初回レビューが `loop = 1` |
| **LC-2** | 上限は **3**。`loop = 3` のレビューで未解決の修正必須が残った場合、**修正フェーズへ進まずに中断**する（4回目のレビューは行わない） |
| **LC-3** | `loop` と各パスの署名は `dev-result.md` の `## レビュー・修正ログ` へ**追記**して永続化する。状態を保持する専用ファイルは**設けない**（環境を書き換えず、中断からの再開機構も持たないため、ジャーナルを必要とする復帰対象が存在しない） |
| **LC-4** | **カウンタのリセットは禁止**する。承認を得る対話経路も設けない（本スキルは `AskUserQuestion` を用いない。中断して利用者へ委ねる） |
| **LC-5** | 修正フェーズで**コード変更が1件も発生しなかった**場合、次のレビューパスへ進まず**即座に中断**する。判定は「修正フェーズで `Edit` / `Write` を適用したファイルの集合が空であること」を**主判定**とし、複数タスクモードでは `git status --porcelain`（G-0 適用後）を補助検証に用いる（単一タスクモードは git 非依存で動作する必要があるため git を主判定にしない） |
| **LC-6** | `loop` は**タスクごとに初期化**する（複数タスクモード）。タスクが変われば指摘の集合が別物であり、前タスクの署名・ループ番号を引き継ぐ根拠がない |
| **LC-7** | レビュー担当の**構成をループ間で変えない**。`--team` 有効なら毎パス3体、無効なら毎パス1体を維持する |
| **LC-8** | 実装フェーズが変更したファイルが**0件**の場合、レビューパスを1回も実行せず「レビュー対象なし」として正常終了する（E-27） |

> **上限を3とした根拠**: `task-verify` のループは「実行結果」という**外部の証拠源**が毎周新しい情報を供給するため上限5が機能します。レビューのループは**同一入力に対する同一モデルの再判断**であり、新情報が入りません。2周目で指摘が消えるのは「自分が直したから」であって、収束は品質を意味しません。

**終了条件の評価順序【必須・この順序】**: 各レビューパスの完了直後に、上から順に評価し**最初に一致した条件で確定**します。

| 順 | 条件 | 判定 | 帰結 |
|---|---|---|---|
| **S-1** | 未解決の修正必須が **0件**（保留・却下を除く） | **正常終了** | コミットへ進む（複数）／完了報告（単一） |
| **S-2** | `signature[loop] == signature[loop-1]`（EA-1） | 早期中断 | コミットしない。E-17 |
| **S-3** | `signature[loop] ⊋ signature[loop-1]` が2回連続（EA-3） | 早期中断 | コミットしない。E-18 |
| **S-4** | `loop == 3`（LC-2） | 中断 | コミットしない。E-16 |
| **S-5** | 修正フェーズを実行 → 変更0件（LC-5） | 即中断 | コミットしない。E-19 |
| **S-6** | 上記いずれでもない | 次のレビューパスへ | — |

> **S-1 を最上位に置く根拠**: 最も安価な判定であり、かつ全件解決しているのに「停滞」と報告する誤検知（空集合どうしの一致）を防ぎます。**空集合どうしの一致は EA-1 の対象外**です（S-1 で先に抜けるため到達しません）。
> **S-2・S-3 を S-4 より前に置く根拠**: 中断理由として「停滞・退行」のほうが「上限到達」より情報量が多く、利用者の次の一手が決まるためです。

**早期中断**:

| # | 規則 |
|---|---|
| **EA-1** | `signature[loop] == signature[loop-1]`（集合として完全一致）なら**早期中断**。これが「2周連続で指摘内容が変化しない」の定義 |
| **EA-2** | 署名は毎パス `### ループ N` へ記録し、後から監査できるようにする |
| **EA-3** | `signature[loop] ⊋ signature[loop-1]`（前周の指摘が全て残り新規が増えた）が**2回連続**したら、修正が退行を生んでいるとみなし早期中断。「修正により新たな指摘が発生している」と明記する |
| **EA-4** | EA-1 / EA-3 のいずれで中断した場合も、**`dev-result.md` への追記と未解決 `R-nnn` の提示は必ず完了させてから**終了する |
| **EA-5** | 却下した指摘が次パスで再提示された場合、それは署名が一致する経路であり EA-1 で正しく中断へ向かう。**再提示を抑止するために却下理由を委譲先へ渡してはならない**（RI-3） |

#### 5-12. 再レビューのスコープ（RS-0〜RS-6）

| # | 規則 |
|---|---|
| **RS-0** | **2周目以降は「新規観点の追加」を行わない。** 委譲プロンプトへ「前周の指摘の解消確認と、修正差分に起因する新規欠陥のみを見る。新しい観点でのレビューは行わない」と明記する |
| **RS-1** | 初回（`loop = 1`）は**実装フェーズが変更した全ファイル**を対象とする |
| **RS-2** | 2周目以降: 前周の未解決指摘に対応する箇所の解消確認 |
| **RS-3** | 2周目以降: 前周の修正で変更した**ファイル全体**（修正箇所だけでなくファイル単位） |
| **RS-4** | 2周目以降: RS-3 のファイルを import / require / 継承・実装している**呼び出し元（1階層のみ）** |
| **RS-5** | 上記以外の実装ファイルは**再レビューしない** |
| **RS-6** | RS-2〜RS-4 の合計が実装変更ファイル数の **70%** を超えたら、絞り込みを諦めて全件再レビューする |

> **絞り込みの根拠はコストではなく終了保証です。** 同一入力を毎周フルスキャンすると、モデルの非決定性により毎周わずかに異なる可読性・保守性の指摘が生成され、署名が永久に一致しません（EA-1 が働きません）。RS-0 と RS-5 は終了保証を成立させるための条文であり、コスト削減はその副次効果です。

#### 5-13. 操作予算（B-1〜B-4）

ブラウザ操作はありませんが、原因箇所を特定できないときの `Grep` → `Read` → `Grep` の連鎖という同型の発散経路が実在します。

| # | 予算 |
|---|---|
| **B-1** | **レビュー委譲1回あたりの対象上限**: ファイル 40件／総行数 6,000行。超過する場合は「変更行数の多い順」に上限まで採り、残余は `未レビュー（予算超過）` として `dev-result.md` へファイル名を列挙する（黙って落とさない） |
| **B-2** | **1指摘の修正あたりのツール呼び出し予算 12回**（`Read` / `Grep` / `Glob` / `Edit` / `Write` / `Bash` の合計）。超過した指摘は `打ち切り（修正予算超過）` として記録し次へ進む |
| **B-3** | **1ループの修正フェーズ全体の予算 60回**。超過したら以降の指摘を `未着手（修正予算超過）` として記録し、終了条件の評価（5-11）へ進む |
| **B-4** | 予算超過で打ち切った指摘は**未解決のまま残る**ため次パスで必ず再提示される。したがって予算超過は握り潰しにならず、最終的に上限到達（E-16）または停滞（E-17）として利用者へ提示される |

#### 5-14. `dev-result.md` への追記規約（W-1〜W-9）

| 規則 | 内容 |
|---|---|
| W-1 | `## メタ情報` は**常に最終セクション**。追記は必ずその直前へ挿入する |
| W-2 | `## レビュー・修正ログ` へは `### ループ N` を**追記のみ**。過去ループのブロックで書き換えてよいのは `- ループ状態:` の値だけ |
| W-3 | `## レビュー指摘一覧` へは新規 `R-nnn` を**末尾追記のみ**。既存項目で書き換えてよいのは ①チェックボックス（**再レビューで解消を確認したときのみ** `[x]`。修正した時点では付けない）②`- 対応:` 行 の**2箇所に限る** |
| W-4 | `- 対象:` / `- 根拠:` / `- 署名:` / 見出し行の `優先度` `区分` `類型` は**変更禁止**（署名の安定性を壊すため）。区分を引き下げる場合は既存値を残したまま `- 区分変更:` 行を**追加**する |
| W-5 | 実装フェーズのセクションは、レビュー修正で実体が変わった場合に限り上書き更新してよい。`## 変更ファイル一覧` はレビュー修正で触れたファイルを**追記**し、コミット対象の和集合（C-9）と一致させる |
| W-6 | `## レビュー総合判定` / `## task-verify へ引き継ぐ事項` / `## 終了サマリ` / `## メタ情報` は**上書き更新**（現在値を表すため） |
| W-7 | `## 欠陥ではない所見` は各ループの所見を**追記**し、過去の所見を削除しない。同一観点で評価が変わった場合は新行を追記し `（ループ2 更新）` と注記する |
| W-8 | メタ情報の Agent Teams は Agent Teams の成立2条件のみで決まる。**レビュー委譲によるサブエージェント起動は成立条件に含めない**（`--team` 未指定なら委譲していても `無効（指定なし）`） |
| W-9 | 作成タイミングは**実装フェーズ完了直後**に1回。レビュー・修正フェーズは以降**追記のみ**。**指摘0件でも** `## レビュー総合判定` と `### ループ 1` を必ず書く（0件であることの記録が「レビューを実施した」唯一の証拠になる） |

**読み返し方針**: `dev-result.md` は**追記のみで読み返しません**。ループ状態（`loop` / 署名 / 未解決 `R-nnn`）はメイン会話が保持します。

#### 5-17. レビュー・修正フェーズのエラーハンドリング（E-13〜E-28）

「モード」列は `単` = 単一タスクモード、`複` = 複数タスクモード。E-1〜E-12 はステップ6-4 のとおり維持します。

| ID | 事象 | 対応 | 全体 | モード |
|---|---|---|---|---|
| **E-13** | **レビュー委譲の spawn 失敗・応答なし** | **自己レビューへ degrade**。告知を表示し `dev-result.md` へ記録 | 継続 | 単/複 |
| **E-14** | **レビュー戻り値のフォーマット逸脱** | **1回だけ再委譲**。2回目も逸脱なら自己レビューへ degrade | 継続 | 単/複 |
| **E-15** | **`--team` でレビュー担当が一部のみ稼働** | 稼働分で続行し、欠けた観点を `dev-result.md` へ明記。0体なら既存フォールバック文言を表示して1体委譲へ（それも失敗なら E-13） | 継続 | 単 |
| **E-16** | **ループ上限到達**（LC-2 / S-4） | 中断。未解決の `R-nnn`（修正必須）を全件提示。**コミットしない** | **中断** | 単/複 |
| **E-17** | **停滞**（EA-1 / S-2） | 早期中断。一致した署名を提示。**コミットしない** | **中断** | 単/複 |
| **E-18** | **退行**（EA-3 / S-3） | 早期中断。「修正により新たな指摘が発生している」と明記。**コミットしない** | **中断** | 単/複 |
| **E-19** | **無変更**（LC-5 / S-5） | 即中断。修正方針が立たなかった `R-nnn` を提示。**コミットしない** | **中断** | 単/複 |
| **E-20** | **修正が書き込み禁止対象への変更を要する** | 当該指摘を `保留（安全境界）` として記録し継続。停止判定の対象から外す | 継続 | 単/複 |
| **E-21** | **修正が req.md / design.md の変更を要する** | 当該指摘を `保留（要判断）` として記録し継続。`/task-req-update` → `/task-design` → `/task-dev` の本流へ戻す旨を完了時に案内 | 継続 | 単/複 |
| **E-22** | **修正後にテスト・ビルドが失敗** | 失敗内容を次パスのレビュー入力へ含めて継続。テストコマンドが不明なら判定を行わない（不明であることを記録する） | 継続 | 単/複 |
| **E-23** | **`dev-result.md` への追記に失敗** | **中断**。記録が残らない状態でループを回さない（監査可能性が失われ EA-2 が成立しない） | **中断** | 単/複 |
| **E-24** | **操作予算の超過**（B-1〜B-3） | `打ち切り（予算超過）` / `未レビュー（予算超過）` として記録し継続 | 継続 | 単/複 |
| **E-25** | **`--team` 指定だがチームメイトが0体** | フォールバック文言を表示しメタ情報へ `無効（フォールバック）` を記録。レビューは**1体委譲で続行**（レビュー委譲は `--team` と独立） | 継続 | 単 |
| **E-26** | **修正委譲の失敗**（複数タスクモード） | 失敗として記録し中断（コミットしない） | **中断** | 複 |
| **E-27** | **レビュー対象ファイルが0件**（LC-8） | レビューパスを実行せず「レビュー対象なし」と記録して正常終了 | 正常終了 | 単/複 |
| **E-28** | **旧 review.md / fix-result.md を検出**（BC-2） | 1回だけ告知し、読まず・変更せず続行 | 継続 | 単/複 |

**原則**:

- **fail-fast（実装系・ループ終了系）／fail-soft（検証系・委譲系）**: 実装・コミット・ループの未収束は即中断する。成果物の欠落・実装済み・レビュー委譲の失敗は当該範囲のみを degrade / スキップする。
- **完了分のコミットは維持する。** `git reset` / `git revert` による自動ロールバックは行わない。
- **黙って劣化しない。** `--team` の無視、コミットのスキップ、残存変更、**自己レビューへの degrade、予算超過による打ち切り、保留扱いにした指摘**のいずれも必ず明示表示する。
- **記録を伴わない継続をしない。** degrade・保留・打ち切りはすべて `dev-result.md` へ記録してから継続する。画面出力は残らず、後から監査できないため。

#### 5-18. degrade 告知【省略・要約禁止】

```
⚠️ レビューをサブエージェントへ委譲できなかったため、自己レビューで続行します（理由: <spawn 失敗 / 応答なし / 戻り値のフォーマット逸脱が2回>）。
   実装した主体自身がレビューを行うため、指摘が過少になる可能性があります（構造的隔離が働きません）。
```

**記録先**: `dev-result.md` の `## プロジェクト概要` の `- レビュー体制:` と `### ループ N` の `- レビュー体制:` の**両方**へ必ず残してください。画面表示だけで済ませてはいけません（画面出力は残らず、後から監査できないためです）。

#### 5-19. 中断時の状態告知

**共通原則**: 本スキルの中断は「**実装は完了しているがレビューループは未完**」という中間状態を生みます。「作成していないもの」だけを列挙すると利用者が「何も行われなかった」と誤読するため、**すべての中断文言は「完了したもの」を先に述べます**。

| 経路 | 対応する ID | 文言の骨子 |
|---|---|---|
| ① ループ上限到達・単一 | E-16 | 完了（実装済・レビュー3回）→ 未解消 `R-nnn` の全件列挙 → 「コミットしていません（単一モードは git を操作しません）」→ 手動修正か本流への差し戻しの案内 |
| ② ループ上限到達・複数 | E-16 | 完了（当該タスクの実装済・**未コミット**）→ 先行タスクのコミットは維持 → 未解消 `R-nnn` → 再実行時の自動スキップ → 未実行の後続タスク名 |
| ③ 停滞 | E-17 | 完了 → **一致した署名を提示** → 「自動修正では解消できない可能性が高い」 |
| ④ 退行 | E-18 | 完了 → **増加した `R-nnn` を提示** → 「実装直後より悪化している可能性があるため `git diff` で確認を」（自動で巻き戻さない旨） |
| ⑤ 無変更 | E-19 | 完了 → 「修正方針を立てられなかった `R-nnn`」→ 「同じ入力からは同じ結果しか出ない」 |
| ⑥ 保留ありの**正常終了** | — | 中断ではないが**必ず表示**。`保留（要判断）` / `保留（安全境界）` / 修正推奨 を区分別に列挙する |

経路①の完成形（他経路も同じ構造で書いてください）:

```
⚠️ レビュー・修正ループが上限（3回）に達したため中断しました。

   完了したもの:
   - 実装: 完了しています（変更ファイルは dev-result.md の「変更ファイル一覧」を参照）
   - レビュー: 3 回実行し、記録は dev-result.md に残しています

   未解消の指摘（修正必須・<n> 件）:
   - R-003 [security] src/Auth/Token.php — <1行要約>

   修正はコミットしていません（本スキルは単一タスクモードで git を操作しません）。
   上記の指摘は自動修正では解消できませんでした。内容を確認し、手動で修正するか、
   要件・設計の見直しが必要であれば /task-req-update → /task-design から本流へ戻してください。
```

#### 5-20. 本ループの限界【設計上の受容事項・完了時にも案内する】

- **同一モデルの盲点は隔離しても共有されます。** 別コンテキストへ委譲してもモデルが同じである以上、見落としの傾向は共有されます。RI-1〜RI-8 が防げるのは「直前の自分の結論を否認したくない」という一貫性バイアスのみであり、モデル固有の知識欠落は防げません。
- **レビューループの収束は品質を意味しません。** 外部の証拠源がないため「指摘が0件になった」ことを品質の証明として扱いません。**本当の合否判定は `task-verify`（動的検証）が持ちます。**

### ステップ6: 複数タスクモードの実行手順

**複数タスクモード（第1引数にカンマを含む場合）でのみ実行します。** 単一タスクモードではこの節を完全に無視してください。

#### 6-1. 事前検証

実装に着手する前に、以下を **1 回の Bash 呼び出しにまとめて**検証してください（トークン節約のため）。

| 検証 | 手段 | 不合格時の挙動 |
|------|------|--------------|
| V-1 git リポジトリであること | `git rev-parse --is-inside-work-tree` | **全体中断**（コミットが行えないため） |
| V-2 ワーキングツリーの清浄性 | `git status --porcelain` を **G-0〜G-2** に従って評価する | **全体中断**（何も実装しない） |
| V-3 実行開始時ブランチの記録 | `git rev-parse --abbrev-ref HEAD` | 取得できなければ全体中断（detached HEAD は警告のうえ続行可） |
| V-4 タスク成果物の存在 | 各タスクの `design.md`（**必須**。`todo.md` の有無は問わない） | **当該タスクのみスキップ**（区分: スキップ（成果物欠落））。全体は継続 |
| V-5 完了済みの検出 | `dev-result.md` の存在 | **当該タスクのみスキップ**（区分: スキップ（実装済み））。全体は継続 |

**dirty 判定の規約（G-0〜G-3）**:

| # | 規則 |
|---|---|
| **G-0（除外規則・最初に適用）** | dirty 判定に用いる `git status --porcelain` の出力から、**`.claude/tasks/<TASK>/**`（実行対象として指定された全タスクのディレクトリ）に属するパスを除外**したうえで G-1〜G-3 を評価する。これらは本スキル自身の成果物であり上書きが仕様であるため。除外は**指定されたタスクに限る**（非対象タスクのディレクトリは dirty として扱う） |
| **G-1（基準線の記録）** | 実行開始時に**1回だけ**評価し、その集合を `baseline_dirty` として保持する。**実行中に再判定しない。** 実行中に生じた変更は `changed_by_skill`（実装委譲の `FILES` ∪ 修正フェーズで編集したパス）へ逐次追記し、以降のいかなる dirty 判定も **`baseline_dirty ∪ changed_by_skill ∪ .claude/tasks/<対象TASK>/**` を除外した集合**に対して行う |
| **G-2（V-2 の判定）** | `baseline_dirty` が空でなければ**全体中断**。未コミットファイルの一覧と対処方法を必ず添える（下記の中断文言） |
| **G-3（コミット後の残存確認）** | コミット後の残存確認は、**`changed_by_skill` に含まれるが `FILES` に挙がらなかったパスのみ**を残存として警告する |

> **G-1 の要点**: レビュー・修正フェーズは**リポジトリ本体のコードを変更する**ため、実行中に dirty を再判定すると**自分自身の変更で必ず引っかかります**。これを **判定の回数**（実行開始時の1回のみ＝時点の固定）と **除外集合**（自分が生んだ変更を除外＝集合の固定）の2点で解消します。除外集合を静的なパスパターンでは書けないため、`changed_by_skill` は実行時に構築します。

集約コマンドの例（`<PROJECT_ROOT>` と タスク名は実際の値に置換すること）:

```bash
cd <PROJECT_ROOT> && \
git rev-parse --is-inside-work-tree && \
git rev-parse --abbrev-ref HEAD && \
git status --porcelain && \
for t in task1 task2 task3; do
  d=".claude/tasks/$t/design.md"
  printf '%s design=%s tasks=%s todo=%s dev=%s\n' "$t" \
    "$(test -f "$d" && echo y || echo n)" \
    "$(test -f "$d" && grep -qE '^## .*実装タスク一覧' "$d" && echo y || echo n)" \
    "$(test -f .claude/tasks/$t/todo.md && echo y || echo n)" \
    "$(test -f .claude/tasks/$t/dev-result.md && echo y || echo n)"
done
```

`design=` のみが V-4 の合否を決めます。`tasks=`（実装タスク一覧の有無）と `todo=` は判定には用いず、**ステップ1 の A-1〜A-5 分岐をどのパスで処理するか**を見極めるための情報です（`design=y tasks=n todo=n` が A-3＝追記パスに対応します）。

V-2 が不合格の場合は、**未コミットファイルの一覧と対処方法を必ず添えて**中断してください。直前に `task-design` を実行していると `.claude/tasks/**` が未コミットのまま残り、ここで中断する可能性が高いためです。

```
❌ ワーキングツリーに未コミットの変更があるため中断しました。
   タスク単位でコミットを分ける仕様のため、実行前に既存の変更をコミットまたは退避してください。
   未コミットの変更:
   <git status --porcelain の出力>
```

#### 6-2. コスト警告と実装対象の件数を表示する

事前検証を通過したら、**まず 5-1 のコスト警告 W-A を表示**してください（中断する経路が警告より前にあるほうがよいため、事前検証の後に置きます）。続いて実装対象の件数を表示します。

**ユーザーの確認入力は求めず、そのまま実装を開始してください。** 表示例:

```
実装対象: 2 件 / 指定 3 件
  - task1  … 実装対象
  - task2  … スキップ（実装済み: dev-result.md が存在）
  - task3  … 実装対象
実装を開始します（コミット先ブランチ: main）。
```

実装対象が 0 件になった場合は、「実装対象がありません」と表示し、6-5 のサマリを出して**正常終了**してください。

#### 6-3. タスクごとの実装・レビュー・修正の委譲

対象タスクを **引数に書かれた順序で 1 件ずつ逐次処理**します（並列実行はしません）。各タスクについて、**(a) 実装委譲 → (b) 戻り値の検証 → (c) レビュー・修正ループ → (d) コミット** の順に実行してください。

> **委譲の順序が隔離を生みます。** `メイン会話 → [実装サブエージェント A] → 戻り値受領 → [レビューサブエージェント B（A とは別コンテキスト）] → [修正サブエージェント C] → コミット` の順序により、レビュー担当は実装担当の内心（`dev-result.md` の自己申告）を一切受け取りません（RI-6）。

**(a) サブエージェントへの委譲**

`Agent` ツールで実装を委譲します。パラメータ:

| パラメータ | 値 | 理由 |
|-----------|-----|------|
| `subagent_type` | `general-purpose` | ファイル書き込み・Bash が必要（`Explore` / `Plan` は書き込み不可） |
| `run_in_background` | `false`（同期） | 逐次処理とコミット順序の保証に必須。戻り値を受けてから次へ進む |
| `model` | **指定しない** | セッションモデルを継承する方針に整合 |
| `description` | `implement <TASK>` | 進捗表示用 |
| `isolation` | 指定しない | 逐次実行のため worktree 分離は不要 |

**サブエージェントはメイン会話のコンテキストを引き継ぎません。** 以下をすべてプロンプトへ明示的に埋め込んでください（1 つでも欠けると実装できません）:

1. プロジェクトルートの絶対パス
2. 対象タスク名 `<TASK>`
3. 読み込むべきファイルの絶対パス（`<PROJECT_ROOT>/.claude/tasks/<TASK>/design.md` = **必須**、`todo.md` = **存在する場合のみ**）
4. 報告書テンプレートの**絶対パス**（このスキルのベースディレクトリ配下の `templates/dev-result-template.md` を、起動時に提示された `Base directory for this skill` から解決したもの）
5. 実施すべき作業（本スキルのステップ1〜4 相当）:
   - design.md（必須）の読み込みと、todo.md が存在する場合の併読
   - `## 12. 実装タスク一覧` の検出（`実装タスク一覧` を含む `## ` 見出し 〜 次の `## ` の直前を範囲とし、`` `T-nnn` `` を含む `- [ ]` 行を出現順に抽出）
   - 下記の分岐表に従った入力解決（**サブエージェントはメイン会話の判断を引き継がないため、分岐表そのものをプロンプトへ埋め込むこと**）
   - テンプレートの読み込み
   - `<PROJECT_ROOT>/.claude/tasks/<TASK>/dev-result.md` の初期化（実装タスク一覧からチェックリスト抽出）
   - `T-nnn` の採番順に従った実装と、進捗に応じた dev-result.md の更新
   - dev-result.md の**実装セクションまで**の完成（メタ情報に 実行モデル名・実行日時・`Agent Teams: 無効（指定なし）` を記入）。**`## レビュー総合判定` 以降のレビュー・修正記録セクションには一切書き込まないこと**（そこは呼び出し元がレビュー・修正ループで追記する領域であり、権限の切替線の向こう側です）

   プロンプトへ埋め込む分岐表（**先に todo.md の有無を判定し、そのうえで実装タスク一覧の有無を見る**こと。順序を逆にすると todo.md を持つ既存タスクが design.md 単独パスへ落ち、後方互換が壊れます）:

   | # | design.md | todo.md | 実装タスク一覧 | 挙動 |
   |---|---|---|---|---|
   | A-1 | 不在 | — | — | 実装せず `STATUS: failure`（成果物欠落）で返す |
   | A-2 | あり | 不在 | あり | design.md 単独で着手する |
   | A-3 | あり | 不在 | **なし** | 設計章から実装単位を抽出して `T-001` から採番し、`## メタ情報` の直前へ `## 12. 実装タスク一覧` を追記してから着手する。既存セクションの番号は振り直さない。工数見積もりは追記しない。1件も抽出できなければ追記せず `STATUS: failure`（成果物欠落）で返す |
   | A-4 | あり | あり | あり | **両方を必ず参照**。実装順は `T-nnn` を一次情報源とし、todo.md を補助情報として併読する。矛盾する場合は **design.md を正**とし、その旨を dev-result.md の「既知の課題・改善点」へ記録する |
   | A-5 | あり | あり | **なし** | **両方を必ず参照**。todo.md が作業分解を持つため追記は行わない（従来どおりの挙動） |

   `T-nnn` の**欠番は正常**として扱い何も表示しないこと。**重複**があれば警告のうえ続行し、記載順・記載どおりの識別子で処理して、突合が曖昧になる旨を dev-result.md へ記録すること。**design.md のチェックボックスは書き換えないこと**（進捗は dev-result.md が持ちます）。
6. 開発方針（段階的実装・品質重視・既存コード尊重）
7. **禁止事項**: `git add` / `git commit` / `git push` など **git の状態を変更する操作を一切行わないこと**（コミットはメイン会話の責務）。**他タスクのディレクトリに触れないこと**。**`TaskCreate` / `TaskUpdate` など進捗管理用の Task ツールを使用しないこと**（タスクリストはセッション単位で共有されるため、メイン会話の進捗表示を汚染します）。内部の進捗は自身の応答内で管理してください。**`AskUserQuestion` を使用しないこと**（サブエージェントの承認はユーザーの承認ではありません）。**さらに別のサブエージェントを spawn しないこと**。
8. 戻り値フォーマットの厳守（下記 (b)）

**(b) 戻り値の契約**

サブエージェントには、最終メッセージを以下の固定フォーマットで返すよう指示してください。

成功時:

```
STATUS: success
FILES:
- <プロジェクトルートからの相対パス>
- <プロジェクトルートからの相対パス>
SUMMARY: <1〜3行の実装概要>
```

失敗時:

```
STATUS: failure
REASON: <失敗理由・どこまで実装したか>
FILES:
- <途中まで変更したファイル（あれば）>
```

| 規約 | 内容 |
|------|------|
| A-1 | `STATUS` は `success` / `failure` のいずれか。1 行目に置く |
| A-2 | `FILES` はプロジェクトルートからの相対パス。新規作成・修正・削除をすべて列挙し、`.claude/tasks/<TASK>/dev-result.md` を必ず含める |
| A-3 | 散文の前置き・後置きを付けない（先頭が `STATUS:` で始まること） |
| A-4 | フォーマット逸脱・`STATUS` 判別不能の場合、**`failure` とみなして中断する**（安全側に倒す） |
| A-5 | パスに空白・特殊文字を含む場合もそのままの相対パスで 1 行 1 件として記す |

**(c) レビュー・修正ループ**

戻り値が `STATUS: success` の場合、**コミットの前に**ステップ5 のレビュー・修正ループを当該タスクに対して実行します。

| # | 手順 |
|---|---|
| 1 | 実装委譲の `FILES` から `.claude/tasks/<TASK>/**` を除いたものを**レビュー対象ファイルのパス一覧**とする（RS-1）。0件なら E-27 として当該タスクのループを実行せず (d) へ進む |
| 2 | `general-purpose` サブエージェント（**同期**）へレビューを委譲する。プロンプトは RP-1〜RP-11 のみで構成し、**`dev-result.md` を渡さない**（RI-2） |
| 3 | 戻り値（RB-1〜RB-9）を受け、`R-nnn` の採番・継承（N-1〜N-4）と署名の算出（5-8）を行い、`dev-result.md` へ追記する |
| 4 | 終了条件（S-1〜S-6）を評価する。`修正必須` が1件以上あれば、**修正を別の同期サブエージェントへ委譲**する（RI-6。修正委譲の失敗は E-26 で中断） |
| 5 | 修正委譲の戻り値の `FILES` を `changed_by_skill` へ追記し、次のレビューパスへ戻る（上限3周） |

**レビュー委譲・修正委譲のプロンプトへ埋め込むもの**: ステップ5 の該当規約（レビューなら 5-3〜5-7、修正なら 5-10 の対応語彙・却下類型 J-1〜J-5・5-13 の操作予算・5-16 の書き込み禁止対象）を**逐語で**埋め込んでください。サブエージェントはメイン会話のコンテキストを引き継がないため、要約すると隔離規約・却下監査が指示レベルへ退化します。

**修正委譲先への禁止事項**: 5-4 の (2)〜(6) に加えて、**`req.md` / `design.md` を変更しないこと**（E-21）、**レビュー指摘に紐づかない箇所を変更しないこと**を明記してください。

S-1（未解決の修正必須が0件）で正常終了した場合のみ (d) へ進みます。E-16〜E-19 で抜けた場合は**コミットせず中断**し、後続タスクへも進みません（C-11）。

**(d) コミット**

**未解決の修正必須が0件で正常終了した場合のみ**、直ちにコミットします。

```bash
cd <PROJECT_ROOT> && git add -- <file1> <file2> ...
cd <PROJECT_ROOT> && git diff --cached --quiet || git commit -m "<TASK>"
```

| 規則 | 内容 |
|------|------|
| C-1 | ステージングは戻り値の `FILES` 一覧に限定する。`git add -A` / `git add .` / `git commit -a` は **使用禁止** |
| C-2 | パス指定には `--` を前置し、ファイル名を個別引数として渡す（`-` 始まりのパスやグロブ誤展開を防ぐ） |
| C-3 | `FILES` に `dev-result.md` が含まれていなければ、オーケストレータ側で補完してステージする |
| C-4 | 削除されたファイルも `git add -- <path>` でステージされる |
| C-5 | コミットメッセージは **タスク名そのまま**（`git commit -m "task1"`）。既存リポジトリの `[add]` / `[up]` 等のプレフィクス規約には合わせない |
| C-6 | `git diff --cached --quiet` が真（差分なし）ならコミットをスキップし、区分「実装完了（コミットなし）」として報告する |
| C-7 | `git push` / ブランチ作成・切替 / `git reset --hard` / `git checkout -- <path>` / `git clean` などの破壊的・遠隔操作は **行わない** |
| C-8 | コミット後の残存確認は **G-3** に従う（`changed_by_skill` に含まれるが `FILES` に挙がらなかったパスのみを残存とみなす）。残存があれば **警告を表示**し、サマリに記録する。次タスクへは進む |
| **C-9** | ステージ対象は **実装委譲の `FILES` ∪ レビュー修正で変更したファイル ∪ `dev-result.md`** の和集合。`git add -A` / `git add .` / `git commit -a` の禁止（C-1）は維持する |
| **C-10** | **レビュー・修正のための追加コミットを作らない**。1タスクにつきコミットは最大1回 |
| **C-11** | **コミットするのは「未解決の修正必須が0件」で正常終了した場合のみ**（S-1）。E-16〜E-19 で抜けた場合は**コミットせず中断**し、後続タスクへも進まない |
| **C-12** | コミット直前に、`changed_by_skill` へ 5-16 の書き込み禁止対象が混入していないか確認する。混入していれば当該パスを**ステージせず**、警告を表示してタスクを失敗として中断する |

> **C-11 の根拠**: 未解消の修正必須を残したまま実装をコミットすると、「レビュー済み」という記録つきで欠陥がコミットされます。これは本スキルが防ごうとしている事象そのものです。退行検知（EA-3）で抜けた場合はコードが壊れている可能性が高く、なおさらコミットしてはいけません。

**git 操作の安全境界**（この表以外の git 操作は行わないこと）:

| 許可 | 禁止 |
|------|------|
| `git status` / `git rev-parse` / `git diff` / `git diff --cached`（読み取り） | `git push`（遠隔への反映） |
| `git add -- <明示パス>` | `git add -A` / `git add .` / `git commit -a` |
| `git commit -m "<TASK>"` | `git reset` / `git checkout -- <path>` / `git restore` / `git clean`（**修正の巻き戻しを自動で行わない**） |
| — | ブランチ作成・切替 / `git rebase` / `git merge` / `git tag` / `git config` |

> `git diff` を許可へ追加しているのは、レビュー対象の変更行数（B-1 の絞り込み）と LC-5 の補助検証に必要なためです。書き込みを伴いません。

#### 6-4. エラー時の中断

| ID | 事象 | 対応 | 全体 |
|----|------|------|------|
| E-1 | 引数の書式不正 | エラー表示して終了。ファイル作成・git 操作は一切行わない | 中断 |
| E-2 | git リポジトリでない（V-1） | エラー表示して終了 | 中断 |
| E-3 | ワーキングツリーが汚れている（G-2） | 未コミット一覧とともにエラー表示して終了 | 中断 |
| E-4 | `design.md` 欠落（V-4） | 当該タスクをスキップ（成果物欠落）として記録 | 継続 |
| E-5 | `dev-result.md` が既存（V-5） | 当該タスクをスキップ（実装済み）として記録 | 継続 |
| E-6 | 実装対象が 0 件 | 「実装対象がありません」と表示しサマリを出す | 正常終了 |
| E-7 | サブエージェントの spawn 失敗・応答なし | 失敗として記録し中断 | 中断 |
| E-8 | 戻り値が `STATUS: failure` | 失敗として記録し中断（コミットしない） | 中断 |
| E-9 | 戻り値のフォーマット逸脱（A-4） | 失敗として記録し中断（コミットしない） | 中断 |
| E-10 | `git add` が失敗 | 失敗として記録し中断。ステージ済み内容は `git reset` せず残す | 中断 |
| E-11 | ステージ後に差分なし（C-6） | コミットをスキップし継続 | 継続 |
| E-12 | コミット後に未コミット変更が残存（G-3） | 警告表示・サマリに記録して継続 | 継続 |

**レビュー・修正フェーズの異常系（E-13〜E-28）はステップ5-17 を参照してください。** 両モード共通で適用されます。

原則（ステップ5-17 と同一）:

- **fail-fast（実装系・ループ終了系）／fail-soft（検証系・委譲系）**: 実装・コミット・ループの未収束は即中断し、後続タスクを実行しない。成果物の欠落・実装済み・レビュー委譲の失敗は当該範囲のみを degrade / スキップする。
- **完了分のコミットは維持する。** `git reset` / `git revert` による自動ロールバックは行わない。
- **黙って劣化しない。** `--team` の無視、コミットのスキップ、残存変更、自己レビューへの degrade、予算超過による打ち切り、保留扱いにした指摘のいずれも必ず明示表示する。
- **記録を伴わない継続をしない。** degrade・保留・打ち切りはすべて `dev-result.md` へ記録してから継続する。

中断した場合は、サマリに加えて次の案内を必ず表示してください（未コミットの変更が残るため、そのまま再実行すると V-2 で必ず中断します）:

```
⚠️ 中断しました。未コミットの変更が残っています。
   再実行する前に、残った変更をコミットまたは破棄してください。
   完了済みのタスクは既にコミット済みのため、再実行時は自動でスキップされます。
```

#### 6-5. 実行結果サマリ

「完了後」節を参照してください。

## 開発方針

- **段階的実装**: 実装タスク一覧（`T-nnn`）の採番順に一つずつ実装
- **品質重視**: 可読性・保守性・テスタビリティを考慮
- **既存コード尊重**: 既存のコーディング規約・パターンに従う
- **進捗報告**: 各タスク完了時にチェックリストを更新
- **レビューの構造的隔離**: 実装が終わったら必ずレビューを別コンテキストへ委譲する（RI-1）。自分でレビューしてよいのは degrade 経路のみ
- **記録を伴わない継続をしない**: degrade・保留・打ち切りはすべて `dev-result.md` へ記録してから継続する

## 完了後

### 単一タスクモード

従来の1行に加えて、**ループ結果を必ず表示してください**:

```
開発作業が完了しました。dev-result.md に詳細な報告書を作成しました。
レビュー・修正ループ: <n>/3 周で完了（未解消の修正必須 0 件 / レビュー隔離: 委譲 <m> 体）
```

続けて、**レビューループの収束は品質の証明ではない**旨を必ず添えてください（外部の証拠源がないためです）。**本当の合否判定は `task-verify`（動的検証）が持ちます。**

保留（`保留（要判断）` / `保留（安全境界）` / `保留（スコープ外）`）や修正推奨の指摘が残っている場合は、正常終了であっても区分別に列挙してください（5-19 経路⑥）。中断した場合は 5-19 の該当経路の文言を表示します。

**モード表示・サマリ表・事前検証メッセージは出しません**（これらは複数タスクモード専用の表示です）。

> **後方互換の対象について**: 従来の「単一タスクモードは表示を含めて完全に同一」という規定は維持できません。レビュー・修正ループの結果（周回数・未解消の `R-nnn`・レビュー隔離の成否）は黙って劣化しないために告知が必須であるためです。後方互換の対象は**入力仕様（引数・読み込むファイル）と生成物の配置**に限定します。

### 複数タスクモード

正常終了・中断のいずれの場合も、**必ず**タスクごとの結果を一覧で報告してください。

```markdown
## 実行結果サマリ

| # | タスク | 結果 | コミット | 備考 |
|---|-------|------|---------|------|
| 1 | task1 | 実装完了 | あり (`task1`) | 変更 4 ファイル |
| 2 | task2 | スキップ（成果物欠落） | なし | design.md が存在しません |
| 3 | task3 | 失敗 | なし | テスト実行に失敗（未コミットの変更が残っています） |
| 4 | task4 | 未実行 | なし | task3 の失敗により中断 |

コミット先ブランチ: main（push は行っていません）
```

結果区分は次の 5 値から選びます: `実装完了` / `スキップ（成果物欠落）` / `スキップ（実装済み）` / `失敗` / `未実行`。
コミット欄は `あり (\`<TASK>\`)` / `なし（差分なし）` / `なし` のいずれかを記載します。

**レビュー・修正ループが収束しなかったタスク**（E-16〜E-19）は、実装自体は完了していてもコミットされないため（C-11）、結果区分は `失敗`、コミット欄は `なし` とし、**備考へ中断理由（上限到達 / 停滞 / 退行 / 無変更）と未解消の `R-nnn` の件数**を記載してください。「実装は完了しているがコミットしていない」ことが備考から読み取れる必要があります。

中断した場合は、サマリの後にステップ6-4 の中断案内（未コミットの変更が残っている旨）と、ステップ5-19 の該当経路の文言を続けて表示してください。

### 報告書のメタ情報（両モード共通）

報告書（dev-result.md）のメタ情報セクションに、実行モデル名・実行日時・Agent Teams の値（有効 / 無効（指定なし） / 無効（フォールバック））を正確に記入してください。複数タスクモードでは、この記入は各タスクの dev-result.md に対して**サブエージェントが行います**（`Agent Teams: 無効（指定なし）`）。
