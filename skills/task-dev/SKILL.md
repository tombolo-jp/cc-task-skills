# タスクの開発実行

あなたは経験豊富なソフトウェア開発者です。詳細設計とToDoリストに基づいて開発を進めます。

タスク「$ARGUMENTS[0]」の開発を開始します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク指定子）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。**カンマ区切りで複数のタスクを指定できます**（例: `task1,task2,task3`）。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します（**単一タスク指定時のみ**） |

**引数全体**: `$ARGUMENTS`

### 実行モードの判定【共通ブロックより先に評価】

**この判定は、次節「重要: `--team` の有無による分岐【最優先】」よりも先に行ってください。** 実行モードが決まらないと `--team` の扱いが確定しないためです。

第1引数（タスク指定子）を以下の規則でパースし、`mode`（single / multi）・`tasks[]`（タスク名の配列・入力順）・`team_enabled`（真偽値）を確定させます。

| # | 規則 | 具体 |
|---|------|------|
| R-1 | 先頭トークンをタスク指定子、2 番目以降をフラグとして扱う | `task1,task2 --team` → 指定子 `task1,task2` / フラグ `--team` |
| R-2 | 指定子にカンマを含めば **複数タスクモード**、含まなければ **単一タスクモード** | 後方互換の分岐点。カンマがなければ以降の挙動は従来と完全に同一 |
| R-3 | 区切り文字は `,` のみ。カンマ前後の空白は **エラー** | `task1, task2` は空白で 2 トークンに割れ、2 番目が既知フラグでないため R-6 でエラー |
| R-4 | 空要素は **エラー** | `task1,,task2` / `task1,task2,` / `,task1` |
| R-5 | タスク名は `^[A-Za-z0-9._-]+$` に一致すること。`.` のみ／`..` を含むものは **エラー** | パストラバーサル・コマンド注入の防止 |
| R-6 | 2 番目以降のトークンが既知フラグ（`--team`）以外なら **エラー** | 空白混入の検出を兼ねる |
| R-7 | 同一タスク名の重複は先頭 1 件のみ採用し、重複分は警告のうえ除去 | 報告を明快にするための事前除去 |
| R-8 | **複数タスクモードかつ `--team` 指定時は `--team` を無視**し、警告を表示して続行 | コンテキスト分離を優先。理由は下記 |

**エラー時は即時終了してください**（ファイル作成・git 操作を一切行わない）。表示する文言:

```
❌ タスク指定が不正です: <理由>
   - カンマ区切りは空白なしで指定してください（例: task1,task2,task3）
   - 空の要素（連続カンマ・先頭/末尾カンマ）は指定できません
   - タスク名に使用できる文字は英数字・ハイフン・アンダースコア・ドットのみです
```

R-8 に該当する場合に表示する警告文言:

```
⚠️ 複数タスク指定時は --team を利用できないため、--team を無視して実行します（理由: タスク実装をサブエージェントへ委譲するため、その内部でチームメイトを spawn できません）。
```

**モード確定後の扱い**:

| モード | 次節「`--team` の有無による分岐」の評価 | 実行する手順 |
|---|---|---|
| 単一タスクモード | 通常どおり評価する（`--team` があれば Agent Teams モードへ） | ステップ1〜4（従来どおり） |
| 複数タスクモード | **`--team` を「含まれない場合」として評価する**（R-8 で無視済みのため） | ステップ5 |

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、各 teammate の成果を `Agent` の **戻り値**（最終メッセージが tool result として返る）で収集し、進捗はチームリード（あなた）が Task（ステップ0 で確定した進捗管理方式）で追跡する暗黙チーム方式で実行します。`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても上記の戻り値方式で成立します。

（注: 旧来のチーム生成／破棄 API は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も `Agent` の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定。`SendMessage` を併用する場合は `name` を付与して宛先を指定できるようにします）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）がステップ0 で確定した方式（Task 方式／フォールバック時はチェックリスト）で追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は `Agent` の戻り値で受け取ります。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

todo.md の依存関係を分析し、**独立して並行実装できるタスク群**を特定してください。

チームメイトに以下のように作業を分担してください:

- **並行実装**: 依存関係がないタスクは異なるチームメイトに割り当てて並行実装
- **順次実装**: 依存関係があるタスクはチームリード（あなた）が順次実装
- **各チームメイトへの指示**: 対象ファイル、実装内容、コーディング規約を明確に伝達

**重要**: 各チームメイトが同じファイルを同時に編集しないよう、ファイル単位で作業を分割してください。

#### 統合

チームリード（あなた）は全チームメイトの成果を統合し、動作確認を行った上で dev-result.md を作成してください。

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/dev-result.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/dev-result.md`

**複数タスクモードの場合**: タスクごとにパスが変わるため、以降は `<TASK>`（ループ中の対象タスク名）を用いて表記します。

- `<PROJECT_ROOT>/.claude/tasks/<TASK>/design.md`
- `<PROJECT_ROOT>/.claude/tasks/<TASK>/todo.md`
- `<PROJECT_ROOT>/.claude/tasks/<TASK>/dev-result.md`

成果物 `dev-result.md` は、**タスクごとのディレクトリ配下にそれぞれ作成**します。

## 手順

### ステップ0: 全フェーズを Task として登録する【FR-1: フロー強制】

本スキルの手順に着手する前に、進捗管理用の Task ツールをロードしてください
（deferred tool のため、ロードしないと呼び出せません）。この ToolSearch は進捗管理のための
ものであり、Agent Teams とは無関係です（`--team` の有無にかかわらず実行します）。

```
ToolSearch query="select:TaskCreate,TaskUpdate,TaskList,TaskGet" max_results=10
```

判定は **スキル実行あたり1回だけ** 行い、フェーズごとに繰り返さないこと。

| ToolSearch の結果 | 進捗管理の方式 |
|---|---|
| `<functions>` ブロックに `TaskCreate` / `TaskUpdate` が含まれる | **Task 方式**（主経路） |
| 含まれない、または ToolSearch がエラー終了 | **チェックリスト方式**（フォールバック） |

**Task 方式（主経路）**: 下記の全フェーズを `TaskCreate` で1件ずつ登録し、各フェーズの着手時に
`TaskUpdate` で `in_progress` へ、完了時に `completed` へ遷移させます。`subject` はフェーズ名
（imperative 形）、`description` にはそのフェーズで行うことを1文で記述します。

**チェックリスト方式（フォールバック）**: 下記の全フェーズを `- [ ]` 形式のチェックリストとして
応答中に宣言し、各フェーズの完了直後にチェックリストを再掲して `- [x]` へ更新します。
**フォールバックしたことを告知するメッセージは表示しないでください**（チェックリスト自体が
進捗表示を兼ねます）。

いずれの方式でも登録（宣言）は **省略不可** です（成果物の必須要素）。列挙順に実行し、
どのフェーズもスキップ・前倒しをしないこと。

登録するフェーズは **実行モード（「実行モードの判定」節で確定させたもの）によって異なります**。該当する側のみを登録してください。

**単一タスクモードのフェーズ**（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. design.md・todo.md を読み込む
3. dev-result-template.md を読み込む
4. dev-result.md を初期化する（todo からチェックリスト抽出）
5. ToDo リストの各タスクを実装する（着手時に下記「todo タスクの動的追加」を行う）
6. dev-result.md を完成させメタ情報を追記する

**複数タスクモードのフェーズ**（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. 引数をパースし対象タスク一覧を確定する
3. 事前検証を実行する（git 清浄性・成果物の存在・完了済みの検出）
4. 実装対象の件数を表示する
5. タスクごとに実装を委譲しコミットする（着手時に下記「todo タスクの動的追加」を行う）
6. 実行結果サマリを報告する

> **禁止事項**: (a) Task 登録／チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 状態遷移（`completed` 化・完了マーク更新）の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が自身の
> Task 一覧（フォールバック時はチェックリスト）で全フェーズを追跡してください。チームメイトへ
> 委任した作業は `Agent` の戻り値で完了を確認してから `completed` へ遷移させます。

> **ステップ1〜4 は単一タスクモード専用です。** 複数タスクモードの場合はステップ1〜4 を実行せず、**ステップ5 へ直接進んでください**（ステップ1〜4 相当の処理は、タスクごとにサブエージェントが担います）。

### ステップ1: ファイル読み込み【単一タスクモード】
Readツールで以下のファイルを読み込み、設計とタスク内容を確認してください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md`
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/todo.md`

### ステップ2: テンプレート読み込み【単一タスクモード】
Readツールで、このスキルのベースディレクトリ（起動時に `Base directory for this skill` として提示されるパス）配下の `templates/dev-result-template.md` を読み込み、報告書のフォーマットを確認してください。

### ステップ3: 報告書初期化【単一タスクモード】
Writeツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/dev-result.md` を作成し、テンプレートを基にtodo.mdからチェックリスト形式で抽出した内容で初期化してください。

#### ステップ4 の直前: todo タスクの動的追加【FR-1】

dev-result.md 初期化（ステップ3 / フェーズ4）が完了したら、実装を始める前に、todo.md に列挙された
各実装タスクを 1 件ずつ `TaskCreate` で追加してください（フォールバック時はチェックリスト項目として
追加します）。以降、各 todo タスクの着手時に `in_progress`、完了時に `completed` へ遷移させます。
全 todo タスクが `completed` になったことを確認してから、固定フェーズ「ToDo リストの各タスクを
実装する」を `completed` にしてください。

- `subject` は **`[todo <i>/<N>] <todo のタスク名>`** の形式とします（例: `[todo 3/9] 認証ミドルウェアを実装する`）。
  `TaskCreate` に親子関係の指定がないため、階層は subject の接頭辞で表現します。
  `addBlocks` / `addBlockedBy` は依存関係の意味論であり、階層表現には使いません。
- 件数 `<N>` は実行時に todo.md を読んで初めて判明するため、件数は固定せず「各タスクを追加せよ」
  という指示の形を取ります。
- `--team` 有効時は、担当チームメイト名を `description` に付記し、チームリード（あなた）の
  Task 一覧で進捗を追跡します。
- **複数タスクモードの場合**は、todo.md の個々の実装タスクではなく **対象タスク名そのもの**
  （`<TASK>` ごとに 1 件）を `subject` = `[task <i>/<N>] <TASK> を実装する` として登録してください。
  todo.md の各実装タスクの追跡は、委譲先のサブエージェントが自身の応答内で行います
  （サブエージェントによる Task ツールの利用は禁止します）。

### ステップ4: 実装【単一タスクモード】
ToDoリストの順序に従って実装を進めてください。

### ステップ5: 複数タスクモードの実行手順

**複数タスクモード（第1引数にカンマを含む場合）でのみ実行します。** 単一タスクモードではこの節を完全に無視してください。

#### 5-1. 事前検証

実装に着手する前に、以下を **1 回の Bash 呼び出しにまとめて**検証してください（トークン節約のため）。

| 検証 | 手段 | 不合格時の挙動 |
|------|------|--------------|
| V-1 git リポジトリであること | `git rev-parse --is-inside-work-tree` | **全体中断**（コミットが行えないため） |
| V-2 ワーキングツリーの清浄性 | `git status --porcelain` が空であること | **全体中断**（何も実装しない） |
| V-3 実行開始時ブランチの記録 | `git rev-parse --abbrev-ref HEAD` | 取得できなければ全体中断（detached HEAD は警告のうえ続行可） |
| V-4 タスク成果物の存在 | 各タスクの `design.md` と `todo.md` | **当該タスクのみスキップ**（区分: スキップ（成果物欠落））。全体は継続 |
| V-5 完了済みの検出 | `dev-result.md` の存在 | **当該タスクのみスキップ**（区分: スキップ（実装済み））。全体は継続 |

集約コマンドの例（`<PROJECT_ROOT>` と タスク名は実際の値に置換すること）:

```bash
cd <PROJECT_ROOT> && \
git rev-parse --is-inside-work-tree && \
git rev-parse --abbrev-ref HEAD && \
git status --porcelain && \
for t in task1 task2 task3; do
  printf '%s design=%s todo=%s dev=%s\n' "$t" \
    "$(test -f .claude/tasks/$t/design.md && echo y || echo n)" \
    "$(test -f .claude/tasks/$t/todo.md && echo y || echo n)" \
    "$(test -f .claude/tasks/$t/dev-result.md && echo y || echo n)"
done
```

V-2 が不合格の場合は、**未コミットファイルの一覧と対処方法を必ず添えて**中断してください。直前に `task-design` / `task-todo` を実行していると `.claude/tasks/**` が未コミットのまま残り、ここで中断する可能性が高いためです。

```
❌ ワーキングツリーに未コミットの変更があるため中断しました。
   タスク単位でコミットを分ける仕様のため、実行前に既存の変更をコミットまたは退避してください。
   未コミットの変更:
   <git status --porcelain の出力>
```

#### 5-2. 実装対象の件数を表示する

**ユーザーの確認入力は求めず、そのまま実装を開始してください。** 表示例:

```
実装対象: 2 件 / 指定 3 件
  - task1  … 実装対象
  - task2  … スキップ（実装済み: dev-result.md が存在）
  - task3  … 実装対象
実装を開始します（コミット先ブランチ: main）。
```

実装対象が 0 件になった場合は、「実装対象がありません」と表示し、5-5 のサマリを出して**正常終了**してください。

#### 5-3. タスクごとの実装委譲

対象タスクを **引数に書かれた順序で 1 件ずつ逐次処理**します（並列実行はしません）。各タスクについて、以下を順に実行してください。

**(a) サブエージェントへの委譲**

`Agent` ツールで実装を委譲します。パラメータ:

| パラメータ | 値 | 理由 |
|-----------|-----|------|
| `subagent_type` | `general-purpose` | ファイル書き込み・Bash が必要（`Explore` / `Plan` は書き込み不可） |
| `run_in_background` | `false`（同期） | 逐次処理とコミット順序の保証に必須。戻り値を受けてから次へ進む |
| `model` | **指定しない** | セッションモデルを継承する方針に整合 |
| `description` | `implement <TASK>` | 進捗表示用 |
| `isolation` | 指定しない | 逐次実行のため worktree 分離は不要 |

**サブエージェントはメイン会話のコンテキストを引き継ぎません。** 以下をすべてプロンプトへ明示的に埋め込んでください（1 つでも欠けると実装できません）:

1. プロジェクトルートの絶対パス
2. 対象タスク名 `<TASK>`
3. 読み込むべきファイルの絶対パス（`<PROJECT_ROOT>/.claude/tasks/<TASK>/design.md` と `todo.md`）
4. 報告書テンプレートの**絶対パス**（このスキルのベースディレクトリ配下の `templates/dev-result-template.md` を、起動時に提示された `Base directory for this skill` から解決したもの）
5. 実施すべき作業（本スキルのステップ1〜4 相当）:
   - design.md / todo.md の読み込み
   - テンプレートの読み込み
   - `<PROJECT_ROOT>/.claude/tasks/<TASK>/dev-result.md` の初期化（todo からチェックリスト抽出）
   - todo の順序に従った実装と、進捗に応じた dev-result.md の更新
   - dev-result.md の完成（メタ情報に 実行モデル名・実行日時・`Agent Teams: 無効（指定なし）` を記入）
6. 開発方針（段階的実装・品質重視・既存コード尊重）
7. **禁止事項**: `git add` / `git commit` / `git push` など **git の状態を変更する操作を一切行わないこと**（コミットはメイン会話の責務）。**他タスクのディレクトリに触れないこと**。**`TaskCreate` / `TaskUpdate` など進捗管理用の Task ツールを使用しないこと**（タスクリストはセッション単位で共有されるため、メイン会話の進捗表示を汚染します）。内部の進捗は自身の応答内で管理してください。
8. 戻り値フォーマットの厳守（下記 (b)）

**(b) 戻り値の契約**

サブエージェントには、最終メッセージを以下の固定フォーマットで返すよう指示してください。

成功時:

```
STATUS: success
FILES:
- <プロジェクトルートからの相対パス>
- <プロジェクトルートからの相対パス>
SUMMARY: <1〜3行の実装概要>
```

失敗時:

```
STATUS: failure
REASON: <失敗理由・どこまで実装したか>
FILES:
- <途中まで変更したファイル（あれば）>
```

| 規約 | 内容 |
|------|------|
| A-1 | `STATUS` は `success` / `failure` のいずれか。1 行目に置く |
| A-2 | `FILES` はプロジェクトルートからの相対パス。新規作成・修正・削除をすべて列挙し、`.claude/tasks/<TASK>/dev-result.md` を必ず含める |
| A-3 | 散文の前置き・後置きを付けない（先頭が `STATUS:` で始まること） |
| A-4 | フォーマット逸脱・`STATUS` 判別不能の場合、**`failure` とみなして中断する**（安全側に倒す） |
| A-5 | パスに空白・特殊文字を含む場合もそのままの相対パスで 1 行 1 件として記す |

**(c) コミット**

戻り値が `STATUS: success` の場合のみ、直ちにコミットします。

```bash
cd <PROJECT_ROOT> && git add -- <file1> <file2> ...
cd <PROJECT_ROOT> && git diff --cached --quiet || git commit -m "<TASK>"
```

| 規則 | 内容 |
|------|------|
| C-1 | ステージングは戻り値の `FILES` 一覧に限定する。`git add -A` / `git add .` / `git commit -a` は **使用禁止** |
| C-2 | パス指定には `--` を前置し、ファイル名を個別引数として渡す（`-` 始まりのパスやグロブ誤展開を防ぐ） |
| C-3 | `FILES` に `dev-result.md` が含まれていなければ、オーケストレータ側で補完してステージする |
| C-4 | 削除されたファイルも `git add -- <path>` でステージされる |
| C-5 | コミットメッセージは **タスク名そのまま**（`git commit -m "task1"`）。既存リポジトリの `[add]` / `[up]` 等のプレフィクス規約には合わせない |
| C-6 | `git diff --cached --quiet` が真（差分なし）ならコミットをスキップし、区分「実装完了（コミットなし）」として報告する |
| C-7 | `git push` / ブランチ作成・切替 / `git reset --hard` / `git checkout -- <path>` / `git clean` などの破壊的・遠隔操作は **行わない** |
| C-8 | コミット後に `git status --porcelain` が空でない場合（`FILES` に挙がらなかった変更が残存）は **警告を表示**し、残存ファイルをサマリに記録する。次タスクへは進む |

**git 操作の安全境界**（この表以外の git 操作は行わないこと）:

| 許可 | 禁止 |
|------|------|
| `git status` / `git rev-parse` / `git diff --cached`（読み取り） | `git push`（遠隔への反映） |
| `git add -- <明示パス>` | `git add -A` / `git add .` / `git commit -a` |
| `git commit -m "<TASK>"` | `git reset --hard` / `git checkout -- <path>` / `git clean` |
| — | ブランチ作成・切替 / `git rebase` / `git merge` |

#### 5-4. エラー時の中断

| ID | 事象 | 対応 | 全体 |
|----|------|------|------|
| E-1 | 引数の書式不正 | エラー表示して終了。ファイル作成・git 操作は一切行わない | 中断 |
| E-2 | git リポジトリでない（V-1） | エラー表示して終了 | 中断 |
| E-3 | ワーキングツリーが汚れている（V-2） | 未コミット一覧とともにエラー表示して終了 | 中断 |
| E-4 | `design.md` / `todo.md` 欠落（V-4） | 当該タスクをスキップ（成果物欠落）として記録 | 継続 |
| E-5 | `dev-result.md` が既存（V-5） | 当該タスクをスキップ（実装済み）として記録 | 継続 |
| E-6 | 実装対象が 0 件 | 「実装対象がありません」と表示しサマリを出す | 正常終了 |
| E-7 | サブエージェントの spawn 失敗・応答なし | 失敗として記録し中断 | 中断 |
| E-8 | 戻り値が `STATUS: failure` | 失敗として記録し中断（コミットしない） | 中断 |
| E-9 | 戻り値のフォーマット逸脱（A-4） | 失敗として記録し中断（コミットしない） | 中断 |
| E-10 | `git add` が失敗 | 失敗として記録し中断。ステージ済み内容は `git reset` せず残す | 中断 |
| E-11 | ステージ後に差分なし（C-6） | コミットをスキップし継続 | 継続 |
| E-12 | コミット後に未コミット変更が残存（C-8） | 警告表示・サマリに記録して継続 | 継続 |

原則:

- **fail-fast（実装系）／fail-soft（検証系）**: 実装・コミットの失敗は即中断し、後続タスクを実行しない。成果物の欠落や実装済みは当該タスクのみスキップする。
- **完了分のコミットは維持する。** `git reset` / `git revert` による自動ロールバックは行わない。
- **黙って劣化しない。** `--team` の無視、コミットのスキップ、残存変更のいずれも必ず明示表示する。

中断した場合は、サマリに加えて次の案内を必ず表示してください（未コミットの変更が残るため、そのまま再実行すると V-2 で必ず中断します）:

```
⚠️ 中断しました。未コミットの変更が残っています。
   再実行する前に、残った変更をコミットまたは破棄してください。
   完了済みのタスクは既にコミット済みのため、再実行時は自動でスキップされます。
```

#### 5-5. 実行結果サマリ

「完了後」節を参照してください。

## 開発方針

- **段階的実装**: ToDoリストの順序に従って一つずつ実装
- **品質重視**: 可読性・保守性・テスタビリティを考慮
- **既存コード尊重**: 既存のコーディング規約・パターンに従う
- **進捗報告**: 各タスク完了時にチェックリストを更新

## 完了後

### 単一タスクモード

「開発作業が完了しました。dev-result.mdに詳細な報告書を作成しました。」と表示してください。

**モード表示・サマリ表・事前検証メッセージのいずれも出しません**（従来と完全に同一の表示を維持します）。

### 複数タスクモード

正常終了・中断のいずれの場合も、**必ず**タスクごとの結果を一覧で報告してください。

```markdown
## 実行結果サマリ

| # | タスク | 結果 | コミット | 備考 |
|---|-------|------|---------|------|
| 1 | task1 | 実装完了 | あり (`task1`) | 変更 4 ファイル |
| 2 | task2 | スキップ（成果物欠落） | なし | todo.md が存在しません |
| 3 | task3 | 失敗 | なし | テスト実行に失敗（未コミットの変更が残っています） |
| 4 | task4 | 未実行 | なし | task3 の失敗により中断 |

コミット先ブランチ: main（push は行っていません）
```

結果区分は次の 5 値から選びます: `実装完了` / `スキップ（成果物欠落）` / `スキップ（実装済み）` / `失敗` / `未実行`。
コミット欄は `あり (\`<TASK>\`)` / `なし（差分なし）` / `なし` のいずれかを記載します。

中断した場合は、サマリの後にステップ5-4 の中断案内を続けて表示してください。

### 報告書のメタ情報（両モード共通）

報告書（dev-result.md）のメタ情報セクションに、実行モデル名・実行日時・Agent Teams の値（有効 / 無効（指定なし） / 無効（フォールバック））を正確に記入してください。複数タスクモードでは、この記入は各タスクの dev-result.md に対して**サブエージェントが行います**（`Agent Teams: 無効（指定なし）`）。
