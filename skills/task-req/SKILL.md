# 要件定義書の作成

あなたは経験豊富なビジネスアナリストです。顧客からの漠然とした依頼を分析し、構造化された要件定義書に変換します。

タスク「$ARGUMENTS[0]」の要件定義書を作成します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク名）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します |

**引数全体**: `$ARGUMENTS`

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、進捗はチームリード（あなた）が Task（ステップ0 で確定した進捗管理方式）で追跡する暗黙チーム方式で実行します。**成果の返り方は spawn の形態によって決まります。**

| spawn の形態 | 成果の返り方 |
|---|---|
| `name` を**付けない**同期委譲（`run_in_background: false`） | 最終メッセージが tool result として**戻り値で返ります** |
| `name` を**付けた** spawn | **バックグラウンド実行**となり、成果は tool result では**返りません**（返るのは「まだ実行中」の旨のみで、完了はタスク通知で届きます）。この形態で成果本文を受け取る手段は `SendMessage` だけです |

したがって、**成果物を受領する必要がある委譲では `name` を付けない同期委譲を既定**とし、`name` 付き spawn は成果の受領を伴わない作業か、`SendMessage` で送り返させることを委譲プロンプトへ明示した場合にのみ用いてください。

`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても同期委譲の戻り値方式で成立します。

（注: 旧来のチーム生成／破棄 API は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 待機作法【禁止事項】

> チームメイトの完了を待つ目的で、`TaskGet` / `TaskList` / `ListAgents` / `git status` などのツールを **2 回以上連続して呼び出すことを禁止します**。待機は同期委譲の `await`（戻り値）と、バックグラウンド実行の完了通知に委ねてください。完了確認のためにツールを呼ぶ必要は**原理的に存在しません**。
>
> **理由**: ポーリングは状態を一切進めず、コンテキストのみを消費します。1 周目でコンテキスト予算を使い切ると、2 周目以降が実行不能になります。
>
> 待機状況を利用者へ伝える場合は、**前回の表示から変化した情報のみ**を出してください。変化が無ければ何も出力しません。

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も同期委譲の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定）。**成果を受領する委譲では `name` を付けず、`run_in_background: false` の同期呼び出しとしてください**（`name` を付与するのは `SendMessage` の宛先が必要な場合に限ります）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）がステップ0 で確定した方式（Task 方式／フォールバック時はチェックリスト）で追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は、`name` を付けない同期委譲であれば戻り値で受け取ります。`name` 付き spawn を用いた場合は、`SendMessage` で成果を送り返すよう委譲プロンプトへ明示してください。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

チームメイトに以下の並行作業を依頼してください:

1. **市場・技術リサーチ担当**: 要件に関連する技術トレンド、類似機能の実装パターン、ベストプラクティスを調査
2. **影響分析担当**: 既存システムのコードベースを調査し、要件が影響するコンポーネントや依存関係を特定

#### 統合

チームリード（あなた）は各担当の調査結果を統合し、整合性を確認した上で最終的な req.md を作成してください。**要確認事項については、統合の時点で全候補へ FR-1-6（分岐テスト → 除外類型）を一括適用してから確定してください。**

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/req.md`

## 手順

### ステップ0: 全フェーズを Task として登録する【FR-1: フロー強制】

本スキルの手順に着手する前に、進捗管理用の Task ツールをロードしてください
（deferred tool のため、ロードしないと呼び出せません）。この ToolSearch は進捗管理のための
ものであり、Agent Teams とは無関係です（`--team` の有無にかかわらず実行します）。

```
ToolSearch query="select:TaskCreate,TaskUpdate,TaskList,TaskGet" max_results=10
```

判定は **スキル実行あたり1回だけ** 行い、フェーズごとに繰り返さないこと。

| ToolSearch の結果 | 進捗管理の方式 |
|---|---|
| `<functions>` ブロックに `TaskCreate` / `TaskUpdate` が含まれる | **Task 方式**（主経路） |
| 含まれない、または ToolSearch がエラー終了 | **チェックリスト方式**（フォールバック） |

**Task 方式（主経路）**: 下記の全フェーズを `TaskCreate` で1件ずつ登録し、各フェーズの着手時に
`TaskUpdate` で `in_progress` へ、完了時に `completed` へ遷移させます。`subject` はフェーズ名
（imperative 形）、`description` にはそのフェーズで行うことを1文で記述します。

**チェックリスト方式（フォールバック）**: 下記の全フェーズを `- [ ]` 形式のチェックリストとして
応答中に宣言し、各フェーズの完了直後にチェックリストを再掲して `- [x]` へ更新します。
**フォールバックしたことを告知するメッセージは表示しないでください**（チェックリスト自体が
進捗表示を兼ねます）。

いずれの方式でも登録（宣言）は **省略不可** です（成果物の必須要素）。列挙順に実行し、
どのフェーズもスキップ・前倒しをしないこと。

登録するフェーズ（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. init.md を読み込み顧客依頼を把握する
3. 依頼内容を分析する（目的・背景・機能・制約）
4. 確認事項の候補を洗い出す
5. 各候補へ分岐テストと除外類型を適用し要確認事項を確定する
6. req.md を更新しメタ情報を追記して完了報告する

> **禁止事項**: (a) Task 登録／チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 状態遷移（`completed` 化・完了マーク更新）の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が自身の
> Task 一覧（フォールバック時はチェックリスト）で全フェーズを追跡してください。チームメイトへ
> 委任した作業は `Agent` の戻り値で完了を確認してから `completed` へ遷移させます。

### ステップ1: 依頼の把握と分析

1. `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/init.md` を読み取り、顧客依頼を把握

2. 顧客依頼から以下を分析:
   - 何を実現したいのか（目的）
   - なぜ必要なのか（背景）
   - 具体的にどのような機能が必要か
   - 既存システムとの関わり
   - 考慮すべき制約や注意点

3. `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md` を更新

## 更新時の注意点

- 顧客の依頼内容から推測・推定できる内容を記入
- 不明確な項目や推測が困難な項目は空欄のまま
- 明確に記載されていない要件は、本文には簡易マーカー「（要確認）」を残しつつ、確認事項の**実体**を req.md 末尾の「要確認事項」セクションへ一覧化する（本文マーカーと末尾一覧は対応が追える形にする）
- 顧客の言葉を専門用語に置き換えすぎない
- 曖昧な表現も一旦そのまま記載し、後で詳細化

## 要確認事項セクションの出力ルール

req.md 末尾に「要確認事項」セクションを設け、確認が必要な事項を集約します。以下のルールに従ってください:

- **FR-1-1**: 確認が必要な事項は req.md 末尾の「要確認事項」セクション（`## 要確認事項`）に集約する。
- **FR-1-2**: 各項目は**数字なしの箇条書き**（`-`）で記述する（連番 `1.` は用いない）。
- **FR-1-3**: 各項目は、ユーザーがインデント子要素として返信できることを前提に、一問一答可能な粒度・自己完結した問い掛け文として書く。
- **FR-1-4**: 本文マーカー「（要確認）」と末尾一覧の項目の対応を追える形にする（例: 本文「〜は未定（要確認）」に対応する末尾項目「〜の値は何か」）。
- **FR-1-5**: req.md のセクション順序は末尾を **「要確認事項」→「メタ情報」** とし、**メタ情報を最下部**に置く。
- **FR-1-6**: 確認事項の候補には次の順序で判定を適用し、**回答が設計・実装の分岐を変える問いだけ**を残す。順序は固定であり、入れ替えてはならない。

  ```
  for q in 確認事項の候補:
      if 分岐テストに通る(q):   残す;    continue   # 包含が最優先
      cls = 除外類型に分類(q)                        # X-1..X-6
      if cls is not None:       除外する; continue
      残す                                           # 判定不能なら残す（フェイルセーフ）
  ```

  **分岐テスト**: その項目への回答が変わったとき、design.md の §1–§11 または §12 実装タスク一覧の**どこがどう変わるか**を「回答が A なら〜／B なら〜」の形で **2つ以上、具体的に書けること**。書けたら残し、書けなければ除外類型の判定（FR-1-7）へ回す。判定を主観的な重要度ではなく「記述可能性」という外形的な基準に置くための規定である。なお、**書けるかどうか自体が判断できない場合は、除外類型の判定へ回さずその場で残す**（迷いは残す側へ倒す）。

  **包含を第1ゲートに置く理由**: 語彙の一致（「スケジュール」「連絡」等）を先に置くと、「通知メールの宛先・トリガ・文面をどうするか」のような**正当な機能要件の確認まで落ちる**。分岐テストを最上位に置けば、語彙が何であれ設計が分岐する問いは必ず生き残る。

  **フェイルセーフの向きは「残す」**: 分類できなかった候補は残す。除外側へ倒すと要件の欠落が**不可視のまま** task-design へ流れるのに対し、残した場合のコストは利用者が1行読み飛ばすだけである。なお task-verify のスキップ判定はフェイルセーフが「スキップする」側であり、**本ルールとは向きが逆**である。危険側が逆（あちらは不可逆な副作用、こちらは要件の欠落）であるため、「揃っていない」という理由でこの向きを反転させてはならない。
- **FR-1-7**: 除外理由は次の**閉じた語彙**（X-1〜X-6）に限る。いずれにも分類できない候補は**残す**（新しい除外類型をその場で発明しない）。

  | ID | 類型 | 例 |
  |---|---|---|
  | X-1 | 日程 | 納期・リリース日・マイルストーン・着手時期 |
  | X-2 | 商流・費用 | 予算枠・見積承認・契約形態・請求 |
  | X-3 | 体制・プロセス | 担当者アサイン・工数配分・社内承認フロー・会議設定・進捗報告 |
  | X-4 | 対人コミュニケーション | クライアント／関係者への連絡要否・連絡先・合意形成の進め方 |
  | X-5 | メタ質問 | 要件全文の再掲による「この理解で正しいか」、回答が Yes / No のいずれでも成果物が同一の確認 |
  | X-6 | 自力で確定できる | コードベース・CLAUDE.md・git 履歴・既存設定を読めば判る事項 |

  `X-6` で除外してよいのは「調べれば確定する」ものに限る。調べた結果が複数の妥当な選択肢に分かれる場合は `X-6` に該当しない（残す）。
- **FR-1-8**: 次の左列は除外類型に見えるが、右列の理由で設計が分岐するため**必ず残す**。左列に似ているという理由だけで除外してはならない（判定は FR-1-6 の分岐テストの結果に従う）。

  | 除外に見える | 実は残す（設計が分岐する） |
  |---|---|
  | リリース日（X-1） | 段階リリースするか＝フィーチャーフラグ／切替スイッチの実装要否 |
  | 移行の時期（X-1） | 既存データを移行するか否か、移行スクリプトの要否 |
  | いつまでサポートするか（X-1） | 対応ブラウザ／PHP・Node・DB のバージョン範囲＝対象環境の確定 |
  | 予算額（X-2） | 有料の外部 API／ライブラリを使ってよいか＝外部依存の可否 |
  | 契約上の秘密保持（X-2） | 個人情報の保存可否・保存期間＝データ設計の分岐 |
  | 担当者は誰か（X-3） | 誰が使う機能か＝ロール・権限設計 |
  | 社内の承認フロー（X-3） | アプリ内の承認ワークフロー＝ステータス遷移の実装 |
  | 運用体制（X-3） | 想定同時アクセス数・データ件数・レスポンス目標値＝非機能要件 |
  | 先方への連絡（X-4） | 通知メール／通知機能の宛先・トリガ・文面＝機能要件そのもの |
- **FR-1-9**: 除外が禁じるのは**問うこと**のみであり、**記録すること**は禁じない。顧客が依頼文中で述べた日程・予算・体制の**事実**は `## 制約事項` 等へ従来どおり記録する。ただし除外した項目については本文マーカー「（要確認）」も出力しない（対応先のないマーカーを残さないため）。除外した項目を退避させる第3のセクション（「参考情報」「非技術事項」等）は設けず、req.md へ一切残さない。除外の件数・項目名は req.md にも完了メッセージにも出力しない。
- **FR-1-10**: 残った項目が0件の場合、`## 要確認事項` セクション自体を出力しない（見出しだけを残して「なし」と書くこともしない）。この場合は `## メタ情報` が req.md の末尾となる。

> このセクションへの回答は、ユーザーが各項目の直下にインデントした子要素（`  - 回答内容`）として追記し、`/task-req-update <task_name>` を実行することで本文へ反映されます。

## 完了後

「要件定義書の叩き台を作成しました。内容を確認し、必要に応じて修正してください。」と表示してください。

確認を促す点:
- 顧客の意図が正しく反映されているか
- 推測部分が妥当か
- 追加で確認すべき事項がないか

報告書（req.md）の末尾に以下のメタ情報セクションを追加してください:

## メタ情報
- 実行モデル: [あなたが動作しているモデル名を正確に記載]
- 実行日時: [現在の日時]
- Agent Teams: [有効 / 無効（指定なし） / 無効（フォールバック）]
