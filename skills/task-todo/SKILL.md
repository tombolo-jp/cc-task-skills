# タスクのToDoリストと工数見積もり作成

あなたは経験豊富なプロジェクトマネージャーです。要件定義・詳細設計に基づいて実装可能な具体的なToDoリストを作成し、各タスクの工数見積もりを行います。

タスク「$ARGUMENTS[0]」のToDoリストと工数見積もりを作成します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク名）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します |

**引数全体**: `$ARGUMENTS`

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、各 teammate の成果を `Agent` の **戻り値**（最終メッセージが tool result として返る）で収集し、進捗はチームリード（あなた）のチェックリストで追跡する暗黙チーム方式で実行します。`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても上記の戻り値方式で成立します。

（注: 旧来の `TeamCreate` / `TeamDelete` は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も `Agent` の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定。`SendMessage` を併用する場合は `name` を付与して宛先を指定できるようにします）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）のチェックリストで追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は `Agent` の戻り値で受け取ります。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

チームメイトに以下の並行作業を依頼してください。**2名の役割は対称ではありません。**

1. **分解・積み上げ担当**: 設計書を基にタスクを分解し、依存関係・実装順序を整理したうえで、各タスクの工数を積み上げる
2. **削減レビュア**: 積み上げられた見積もりが**過大ではないか**を検証する。具体的には、
   - 既存コード・既存クラス・既存パターンの**流用可能性**を洗い出し、削れる工数を具体的に指摘する
   - 「ステップ3: コード量サニティチェック」を実施し、**行/h が閾値を下回った場合は見積もりを差し戻す**
   - 青天井のバッファ（「+0〜40h」のような幅）を見つけたら、**スパイクへの変換**（ステップ2-3）を提案する

> **なぜ非対称にするか**: 両担当とも「漏れを見つける」役にすると、指摘が加算方向にしか出ず、リードは両者を足すだけになります。工数が構造的に過大化する最大の原因がこれです。**削減レビュアは「減らすこと」が仕事**であると、依頼プロンプトに明記してください。

#### チームメイトへの依頼時の禁止事項

以下のような**上方バイアスを注入する指示を出さないでください**:

- ❌「リスクを厳しく評価してください」
- ❌「不確実性の高い箇所を洗い出してください」（リスク列挙のみを依頼する形）
- ✅「リスクは**スパイクで解消できないか**を必ず検討したうえで、残る分だけを計上してください」

#### 統合

チームリード（あなた）は各担当の成果を統合し、全体の整合性を確認した上で最終的な todo.md を作成してください。**削減レビュアの指摘は、採用しない場合にその理由を todo.md に残してください。**

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/todo.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/todo.md`

## 手順

### ステップ0: 全フェーズをチェックリストとして宣言する【FR-1: フロー強制】

本スキルの手順に着手する前に、まず以下の全フェーズを `- [ ]` 形式のチェックリスト
として応答中に宣言してください。この宣言は省略不可です（成果物の必須要素）。
宣言後は列挙順に実行し、どのフェーズもスキップ・前倒しをしないこと。
各フェーズの完了直後にチェックリストを再掲し、完了項目を `- [x]` へ更新して
進捗を明示します。

宣言するフェーズ（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. req.md・design.md を読み込む
3. 実装順序・依存関係・難易度・工数を分析する
4. コード量サニティチェックで見積もりを検算する
5. todo-template.md を読み込む
6. todo.md を作成する（工数見積もり込み）
7. メタ情報を追記し完了報告する

> **禁止事項**: (a) チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 完了マーク更新の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が
> 自身のチェックリストで全フェーズを追跡してください。チームメイトへ委任した作業は
> `Agent` の戻り値で完了を確認してからチェックを付けます。

### ステップ1: ファイル読み込み
Readツールで以下のファイルを読み込み、タスクの全体像を把握してください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md`（要件定義）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md`（詳細設計）

### ステップ2: 分析
実装順序と依存関係を分析し、各タスクの難易度と工数を評価してください。

#### 2-1. 既存の見積もりを先に見ない【アンカリング回避】

design.md やその他の資料に**既存の工数見積もりが記載されている場合があります**（本来 `task-design` は工数を出しませんが、要件によっては混入します）。

- **必ず、自分で一から積み上げてから**、既存の見積もりと照合してください。
- 先に既存の数字を読むと、「その数字を検証・補正する」立場に固定されます。この立場では**指摘が加算方向にしか出ません**（「工程が漏れている」は計上しやすく、「厚すぎる」は言い出しにくい）。
- 照合の結果は「差異」として記載してかまいませんが、**自分の積み上げを正**とし、既存見積もりに寄せないでください。

#### 2-2. タスクの粒度

**タスク総数は 8〜12 件を目安**とし、20 件を超えたら統合してください。

同一ファイル・同一クラスに対する作業は 1 タスクにまとめます（例:「テーブル定義」「`record()` 実装」「`find()` 実装」「マスク処理」は、すべて同じクラスなら 1 タスク）。

> **なぜか**: 細分化そのものが工数を膨らませます。各タスクが最小 0.5〜1h に切り上がるため、28 タスクに割ると、それだけで下限 14〜28h が積み上がります。分解の細かさは見積もりの精度を上げません。

#### 2-3. 不確実性はバッファではなくスパイクに変換する【必須】

「未検証の外部 API」「使ったことのないライブラリ」「動くか分からない機能」に対して、**`+0〜40h` のような青天井のバッファを積まないでください。**

代わりに、**30分〜1時間で白黒をつけるスパイクタスク**に変換し、todo.md の「§0 事前スパイク」に置きます。

| 悪い例 | 良い例 |
|---|---|
| リスク「新 API が動かないかもしれない」→ バッファ +0〜40h | スパイク「ダミーデータ1件で最小構成の疎通を確認する（0.5h）」→ **成功なら +0、失敗なら自前実装 +4h の二択** |

青天井のバッファは、**ほぼ常に測定可能な質問に還元できます**。「分からないから多めに積む」の前に、「30分で確かめられないか」を必ず検討してください。

### ステップ3: コード量サニティチェック【必須・省略禁止】

ステップ2で積み上げた**実装工数**（コードを書く時間。環境構築・リリース・ドキュメント等の付帯工程は含めない）に対して、以下を必ず計算してください。

```
新規・変更コードの概算行数 ÷ 実装工数（h） = ?行/h
```

| 区分 | 妥当な範囲 |
|---|---|
| 既存パターン・既存クラスの流用が効くコード | 80〜150行/h |
| 新規性が高いコード（社内前例なし・外部 API・未使用ライブラリ） | 40〜80行/h |
| UI 操作のみで完結する作業（管理画面の設定・フィールド追加等） | 行数の対象外。別途計上 |

**判定**:

- **30行/h を下回った場合は、見積もりが過大です。** ステップ2に戻り、内訳を見直してください。特に「コードを書いていないのに計上されている工数」（設計読解・関係者調整・レビュー対応・過剰な検証時間）を疑ってください。
- 150行/h を大きく超えた場合は、逆に過小です。設計の読み落としがないか確認してください。

計算結果は **todo.md に必ず記載**してください（数値と判定）。

> **なぜ必須か**: 積み上げ式の見積もりは、個々のタスクが妥当に見えても合計が破綻していることに最後まで気づけません。この 1 行の計算だけが、それを検出できます。

### ステップ4: テンプレート読み込み
Readツールで、このスキルのベースディレクトリ（起動時に `Base directory for this skill` として提示されるパス）配下の `templates/todo-template.md` を読み込み、工数見積もりセクションのフォーマットを確認してください。

### ステップ5: ToDoリスト作成
Writeツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/todo.md` を作成し、ToDoリストと工数見積もりを記載してください。

## ToDoリスト構成

- **前提条件**: **このコードベースを熟知した開発者**（設計読解・既存パターンの把握が不要な状態）、手作業実装、1日8時間稼働
- **工数サマリー**: 3層（§0 / §A / §B）の内訳と合計（表形式）
- **サニティチェック**: ステップ3の計算結果（行数・行/h・判定）
- **§0 事前スパイク**: 着手前に潰すブロッカー（ステップ2-3で変換したもの）
- **§A 実装工数**: 開発順序、タスク分解（作業内容・対象ファイル・チェック項目・見積もり根拠）
- **§B 付帯工程**: 環境準備・アップグレード・リリース・ドキュメント等
- **優先度**: 必須・推奨・オプションの分類
- **リスク要因**: 各リスクに「不確実性レベル（低/中/高）」と「影響時間の範囲」を付与する
- **バッファ**: 下記の規定に従う
- **最終見積もり**: テンプレートの形式に従い、基本工数、最少工数（楽観）、最大工数（悲観）、営業日換算（範囲）を記載

### 前提条件について

**既定は「このコードベースを熟知した開発者」です。** したがって、以下は**工数に計上しません**:

| 計上しないもの | 理由 |
|---|---|
| 設計書の読解時間 | design.md が実装仕様レベルまで書かれている前提。読解が必要なら、それは設計の不足であって実装工数ではない |
| 既存コード・既存パターンの調査 | 熟知している前提 |
| 関係者への確認・調整 | 工数ではなく**ブロッカー**として §0 に記載する（時間ではなく可否で管理する） |
| カレンダー上のリードタイム | 「翌月の実データ待ち」等は工数ではない。**スケジュール所見として分離**して記載する |

レビュー対応を計上する場合は、**実装工数の 15% を上限**とします。

### 3層構成【必須】

工数を1つの数字に混ぜないでください。**コードを書く時間が何時間なのかが見えなくなり、過大さを検出できなくなります。**

| 層 | 内容 | 扱い |
|---|---|---|
| **§0 事前スパイク** | 未検証要素を白黒つける作業（各 0.5〜1h） | 着手前に実施。結果で分岐を確定させる |
| **§A 実装工数** | コードを書く時間 ＋ 動作確認 | **サニティチェックの対象**。バッファ ±30% |
| **§B 付帯工程** | 環境準備・プラグイン更新・リリース・ドキュメント・設定作業 | **下限〜上限をそのまま提示**（係数を掛けない） |

### バッファ規定

- **§A 実装工数**: **±30%**。ただし設計が実装仕様レベルまで確定していない場合は ±50%
- **§B 付帯工程**: **係数を掛けない。** 「壊れるか / 環境があるか」といった**二値で決まる**ものに係数を掛けても意味がありません。下限と上限をそのまま提示してください
- **§0 スパイクで判定済みの項目**: バッファに含めない（分岐が確定しているため）

> **旧規定（「不確実性が高い場合は ±50〜100%」）は廃止しました。** 係数の青天井化が過大見積もりの主因だったためです。不確実性は、まずステップ2-3でスパイクに変換してください。変換できないものだけが、上記の範囲でバッファの対象になります。

## 完了後

「ToDoリストと工数見積もりファイルが作成されました。必要に応じて todo.md を修正してください。」と表示してください。

- 実行日時: [現在の日時]
- Agent Teams: [有効 / 無効（指定なし） / 無効（フォールバック）]
