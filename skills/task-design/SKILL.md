# タスクの詳細設計と工数見積もり

あなたは経験豊富なソフトウェアアーキテクトです。要件に基づいて詳細設計を作成し、続けて実装タスクへの分解と工数見積もりまでを 1 回の実行で完結させます。

タスク「$ARGUMENTS[0]」の詳細設計・実装タスク一覧・工数見積もりを作成します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク名）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します |

**引数全体**: `$ARGUMENTS`

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、進捗はチームリード（あなた）が Task（ステップ0 で確定した進捗管理方式）で追跡する暗黙チーム方式で実行します。**成果の返り方は spawn の形態によって決まります。**

| spawn の形態 | 成果の返り方 |
|---|---|
| `name` を**付けない**同期委譲（`run_in_background: false`） | 最終メッセージが tool result として**戻り値で返ります** |
| `name` を**付けた** spawn | **バックグラウンド実行**となり、成果は tool result では**返りません**（返るのは「まだ実行中」の旨のみで、完了はタスク通知で届きます）。この形態で成果本文を受け取る手段は `SendMessage` だけです |

したがって、**成果物を受領する必要がある委譲では `name` を付けない同期委譲を既定**とし、`name` 付き spawn は成果の受領を伴わない作業か、`SendMessage` で送り返させることを委譲プロンプトへ明示した場合にのみ用いてください。

`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても同期委譲の戻り値方式で成立します。

（注: 旧来のチーム生成／破棄 API は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 待機作法【禁止事項】

> チームメイトの完了を待つ目的で、`TaskGet` / `TaskList` / `ListAgents` / `git status` などのツールを **2 回以上連続して呼び出すことを禁止します**。待機は同期委譲の `await`（戻り値）と、バックグラウンド実行の完了通知に委ねてください。完了確認のためにツールを呼ぶ必要は**原理的に存在しません**。
>
> **理由**: ポーリングは状態を一切進めず、コンテキストのみを消費します。1 周目でコンテキスト予算を使い切ると、2 周目以降が実行不能になります。
>
> 待機状況を利用者へ伝える場合は、**前回の表示から変化した情報のみ**を出してください。変化が無ければ何も出力しません。

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も同期委譲の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定）。**成果を受領する委譲では `name` を付けず、`run_in_background: false` の同期呼び出しとしてください**（`name` を付与するのは `SendMessage` の宛先が必要な場合に限ります）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）がステップ0 で確定した方式（Task 方式／フォールバック時はチェックリスト）で追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は、`name` を付けない同期委譲であれば戻り値で受け取ります。`name` 付き spawn を用いた場合は、`SendMessage` で成果を送り返すよう委譲プロンプトへ明示してください。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

本スキルは **設計フェーズ → 見積もりフェーズの 2 フェーズ逐次**でチームメイトを起動します。**5 担当を同時並列にしないでください。**

**フェーズ1: 設計3担当（並列起動）** — 同一メッセージ内に 3 つの `Agent` 呼び出しを並べて起動する

1. **データ設計担当**: データモデル、スキーマ変更、データフローの設計
2. **API・インターフェース設計担当**: API エンドポイント、インターフェース、入出力の設計
3. **セキュリティ・パフォーマンス担当**: セキュリティ考慮事項、パフォーマンス最適化、エラーハンドリング方針の設計

→ チームリード（あなた）が成果を統合し、**設計セクション（§1〜§11）を確定させます**。

**フェーズ2: 見積もり2担当（フェーズ1の完了後に起動・非対称）** — **2名の役割は対称ではありません。**

4. **分解・積み上げ担当**: 確定した設計章を基にタスクを `T-nnn` へ分解し、依存関係・実装順序を整理したうえで、各タスクの工数を積み上げる
5. **削減レビュア**: 積み上げられた見積もりが**過大ではないか**を検証する。具体的には、
   - 既存コード・既存クラス・既存パターンの**流用可能性**を洗い出し、削れる工数を具体的に指摘する
   - 「ステップ5-3: コード量サニティチェック」を実施し、**行/h が閾値を下回った場合は見積もりを差し戻す**
   - 青天井のバッファ（「+0〜40h」のような幅）を見つけたら、**スパイクへの変換**（ステップ5-2）を提案する

> **なぜ非対称にするか**: 両担当とも「漏れを見つける」役にすると、指摘が加算方向にしか出ず、リードは両者を足すだけになります。工数が構造的に過大化する最大の原因がこれです。**削減レビュアは「減らすこと」が仕事**であると、依頼プロンプトに明記してください。

> **なぜ 5 担当を同時並列にしないか**: 設計が確定しないと分解・積み上げができません。同時に走らせると見積もり担当が未確定の設計を推測で埋め、「設計を確定させてから見積もる」という順序固定（ステップ6 の前提）が崩れます。トレードオフとしてトークン消費と実行時間の増加を許容します。

#### チームメイトへの依頼時の禁止事項

以下のような**上方バイアスを注入する指示を出さないでください**:

- ❌「リスクを厳しく評価してください」
- ❌「不確実性の高い箇所を洗い出してください」（リスク列挙のみを依頼する形）
- ✅「リスクは**スパイクで解消できないか**を必ず検討したうえで、残る分だけを計上してください」

#### 統合

チームリード（あなた）は各担当の成果を統合し、整合性を確認した上で最終的な design.md を作成してください。**削減レビュアの指摘は既定で採用します。採用しない場合は、その理由を design.md の `### 13-9. バッファ` に残してください。**

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/design.md`

## 手順

### ステップ0: 全フェーズを Task として登録する【FR-1: フロー強制】

本スキルの手順に着手する前に、進捗管理用の Task ツールをロードしてください
（deferred tool のため、ロードしないと呼び出せません）。この ToolSearch は進捗管理のための
ものであり、Agent Teams とは無関係です（`--team` の有無にかかわらず実行します）。

```
ToolSearch query="select:TaskCreate,TaskUpdate,TaskList,TaskGet" max_results=10
```

判定は **スキル実行あたり1回だけ** 行い、フェーズごとに繰り返さないこと。

| ToolSearch の結果 | 進捗管理の方式 |
|---|---|
| `<functions>` ブロックに `TaskCreate` / `TaskUpdate` が含まれる | **Task 方式**（主経路） |
| 含まれない、または ToolSearch がエラー終了 | **チェックリスト方式**（フォールバック） |

**Task 方式（主経路）**: 下記の全フェーズを `TaskCreate` で1件ずつ登録し、各フェーズの着手時に
`TaskUpdate` で `in_progress` へ、完了時に `completed` へ遷移させます。`subject` はフェーズ名
（imperative 形）、`description` にはそのフェーズで行うことを1文で記述します。

**チェックリスト方式（フォールバック）**: 下記の全フェーズを `- [ ]` 形式のチェックリストとして
応答中に宣言し、各フェーズの完了直後にチェックリストを再掲して `- [x]` へ更新します。
**フォールバックしたことを告知するメッセージは表示しないでください**（チェックリスト自体が
進捗表示を兼ねます）。

いずれの方式でも登録（宣言）は **省略不可** です（成果物の必須要素）。列挙順に実行し、
どのフェーズもスキップ・前倒しをしないこと。

登録するフェーズ（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. req.md を読み込み要件を確認する
3. 既存プロジェクト構造を分析する
4. design-template.md を読み込む
5. 設計セクション（§1〜§11）を確定させる
6. 実装タスク一覧（§12）と工数見積もり（§13）を作成する
7. メタ情報を追記し完了報告する

> **フェーズ5と6を1つにまとめないこと。** まとめると設計と見積もりが同一の思考ブロックで進行し、
> 「設計を確定させてから見積もる」という順序固定（設計確定線）が実効性を失います。

> **禁止事項**: (a) Task 登録／チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 状態遷移（`completed` 化・完了マーク更新）の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が自身の
> Task 一覧（フォールバック時はチェックリスト）で全フェーズを追跡してください。チームメイトへ
> 委任した作業は `Agent` の戻り値で完了を確認してから `completed` へ遷移させます。

### ステップ1: 要件確認
Readツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md` を読み込み、要件を確認してください。

`req.md` が存在しない場合は、エラーを表示して終了してください（design.md は作成しません）。`/task-init` → `/task-req` の実行を案内します。

### ステップ2: プロジェクト分析
Glob/Grep/Readツールで既存プロジェクトの構造を分析してください（整合性と保守性を考慮）。

### ステップ3: テンプレート読み込み
Readツールで、このスキルのベースディレクトリ（起動時に `Base directory for this skill` として提示されるパス）配下の `templates/design-template.md` を読み込み、生成物のセクション構成を確認してください。

読み込みに失敗した場合は、警告を表示したうえで**下記「生成物のセクション構成」に従って続行**してください（テンプレートは骨格の提示であり、構成の正は本 SKILL.md です。中断はしません）。

### ステップ4: 設計セクション（§1〜§11）の確定
Writeツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md` を作成し、**まず設計セクションのみ**を書き切ってください。この段階で工数見積もりを書き始めないでください。

`## 4. ファイル構造` には、新規作成・変更・削除するファイルごとに「新規/変更」と**概算行数**を必ず記載し、合計行数を集計してください。**この合計がステップ5-3 のサニティチェックの入力になります。**

既存の design.md がある場合は上書きしますが、上書きする旨を先に表示してください。

### ステップ5: 実装タスク一覧（§12）と工数見積もり（§13）の作成

設計セクションを確定させてから、**独立した工程として**着手してください。

#### 5-0. 設計確定線【必須・順序固定】

| # | 規定 | 内容 |
|---|---|---|
| (1) | **順序固定** | 設計セクション（§1〜§11）を確定させてから §12・§13 を作成する。見積もりの途中で設計を書き換えたくなった場合は、**見積もりを破棄して最初からやり直す** |
| (2) | **read-only 規定** | 見積もりフェーズでは設計セクションを**入力としてのみ**扱う。見積もりの都合で設計を書き換えることを禁止する |

**アンカリング回避**: req.md やその他の資料に**既存の工数見積もりが記載されている場合**は、**必ず、自分で一から積み上げてから**照合してください。先に既存の数字を読むと「その数字を検証・補正する」立場に固定され、**指摘が加算方向にしか出ません**。照合結果は「差異」として記載してかまいませんが、**自分の積み上げを正**とし、既存見積もりに寄せないでください。

#### 5-1. 実装タスク一覧（§12）

`## 12. 実装タスク一覧` に、実装単位を `T-nnn` 形式で列挙します。

| 項目 | 規定 |
|---|---|
| 書式 | `` `T-nnn` ``（バッククォートで囲む。`nnn` は**3桁ゼロ埋め**、`T-001` から開始） |
| 採番順 | **採番順＝実装順**。依存関係の解決順に、文書の出現順で振る |
| 欠番 | **許容する**（パースは出現順の抽出のみで、連番性に依存しない） |
| 重複 | **禁止**（識別子が一意でないと dev-result.md / review.md との突合が成立しない） |
| 追番・削除 | 後からタスクを足す場合は「既存の最大値 + 1」。**既存番号は振り直さない**。削除した ID は**再利用しない** |
| 粒度 | **8〜12件を目安**とし、20件を超えたら統合する。同一ファイル・同一クラスに対する作業は1タスクにまとめる |

各項目は `- [ ] ` のチェックボックス＋以下のフィールドで構成します（**注意点** のみ任意、他は必須）:

**対象**（ファイルパス＋新規/変更＋概算行数）／**作業**／**依存**（先行タスクの `T-nnn`、なければ「なし」）／**完了条件**／**見積もり**（時間）／**注意点**（任意）

> **なぜ粒度を絞るか**: 細分化そのものが工数を膨らませます。各タスクが最小 0.5〜1h に切り上がるため、28 タスクに割ると、それだけで下限 14〜28h が積み上がります。分解の細かさは見積もりの精度を上げません。

> **役割分離**: 具体的な作業手順・対象ファイル・順序・概算行数は §12 に書き、`## 3. コンポーネント設計` には**構造と責務のみ**を書きます。同じ情報を両方に書かないでください。

> **`## 12.` は下流スキル（`task-dev`）が機械的に読み取る唯一のセクションです。** 見出し文言と `T-nnn` の書式を崩さないでください。なお **design.md のチェックボックスは `task-dev` が書き換えません**（進捗は dev-result.md が持ちます）。

#### 5-2. 不確実性はバッファではなくスパイクに変換する【必須】

「未検証の外部 API」「使ったことのないライブラリ」「動くか分からない機能」に対して、**`+0〜40h` のような青天井のバッファを積まないでください。**

代わりに、**30分〜1時間で白黒をつけるスパイクタスク**に変換し、`### 13-4. §0 事前スパイク` に置きます。

| 悪い例 | 良い例 |
|---|---|
| リスク「新 API が動かないかもしれない」→ バッファ +0〜40h | スパイク「ダミーデータ1件で最小構成の疎通を確認する（0.5h）」→ **成功なら +0、失敗なら自前実装 +4h の二択** |

青天井のバッファは、**ほぼ常に測定可能な質問に還元できます**。「分からないから多めに積む」の前に、「30分で確かめられないか」を必ず検討してください。

#### 5-3. コード量サニティチェック【必須・省略禁止】

積み上げた**実装工数**（コードを書く時間。環境構築・リリース・ドキュメント等の付帯工程は含めない）に対して、以下を必ず計算してください。

```
新規・変更コードの概算行数 ÷ 実装工数（h） = ?行/h
```

行数は `## 4. ファイル構造` の合計を**正**として引用します（機械的削除だけで完結する行数は分母に含めません）。

| 区分 | 妥当な範囲 |
|---|---|
| 既存パターン・既存クラスの流用が効くコード | 80〜150行/h |
| 新規性が高いコード（社内前例なし・外部 API・未使用ライブラリ） | 40〜80行/h |
| UI 操作のみで完結する作業（管理画面の設定・フィールド追加等） | 行数の対象外。別途計上 |

**判定**:

- **30行/h を下回った場合は、見積もりが過大です。** ステップ5-1 に戻って内訳を見直してください。特に「コードを書いていないのに計上されている工数」（設計読解・関係者調整・レビュー対応・過剰な検証時間）を疑ってください。
- 150行/h を大きく超えた場合は、逆に過小です。差し戻しは行いませんが、設計の読み落としがないか確認し、その旨を `### 13-3. サニティチェック` の判定欄へ記載してください。
- 行数を算出できない場合（UI 操作のみのタスク等）も、**サニティチェック自体は省略しません**。対象行数が 0 なら「対象外」と判定を記します。

計算結果（行数・行/h・判定）は **design.md の `### 13-3. サニティチェック` に必ず記載**してください。

> **なぜ必須か**: 積み上げ式の見積もりは、個々のタスクが妥当に見えても合計が破綻していることに最後まで気づけません。この 1 行の計算だけが、それを検出できます。

#### 5-4. 差し戻しの上限【終了保証】

サニティチェックによる差し戻しは無限には行いません。

| 規定 | 内容 |
|---|---|
| **上限** | 差し戻しは**最大2回**まで（＝見積もりの作成は最大3回） |
| **停滞判定** | 前回と今回の「§A 実装工数の合計値」が**同一**なら、上限に達していなくても即座に打ち切る |
| **上限到達時** | その時点の見積もりを採用し、`### 13-3.` の判定欄へ「過大の疑いが残る（差し戻し上限到達）」と明記し、想定される原因（タスク細分化／バッファ過大／設計側の過剰）を列挙して**利用者の判断へ委ねる** |
| **設計への巻き戻し禁止** | 設計側の過剰が原因と判断される場合も、設計セクションの自動巻き戻しは行わない（その旨を design.md に明記する） |

差し戻し時は「サニティチェック: <X>行/h（30行/h 未満）。見積もりを見直します（<n>/2 回目）。」と表示してください。

### 前提条件について

`### 13-1. 前提条件` には以下を必ず含めます。

- **実施者**: **このコードベースを熟知した開発者**（設計読解・既存パターンの把握が不要な状態）
- **実装方法**: 手作業実装
- **稼働**: 1日8時間 = 1人日
- **注記**: 「本見積もりは**手作業で実装した場合の人日換算**であり、実際の実装は AI が行う」

したがって、以下は**工数に計上しません**:

| 計上しないもの | 理由 |
|---|---|
| 設計書の読解時間 | 設計セクションが実装仕様レベルまで書かれている前提。読解が必要なら、それは設計の不足であって実装工数ではない |
| 既存コード・既存パターンの調査 | 熟知している前提 |
| 関係者への確認・調整 | 工数ではなく**ブロッカー**として §0 事前スパイクに記載する（時間ではなく可否で管理する） |
| カレンダー上のリードタイム | 「翌月の実データ待ち」等は工数ではない。**スケジュール所見として分離**して記載する |

レビュー対応を計上する場合は、**実装工数の 15% を上限**とします。

### 3層構成【必須】

工数を1つの数字に混ぜないでください。**コードを書く時間が何時間なのかが見えなくなり、過大さを検出できなくなります。**

| 層 | 内容 | 扱い |
|---|---|---|
| **§0 事前スパイク** | 未検証要素を白黒つける作業（各 0.5〜1h） | 着手前に実施。結果で分岐を確定させる |
| **§A 実装工数** | コードを書く時間 ＋ 動作確認 | **サニティチェックの対象**。バッファ ±30% |
| **§B 付帯工程** | 環境準備・プラグイン更新・リリース・ドキュメント・設定作業 | **下限〜上限をそのまま提示**（係数を掛けない） |

### バッファ規定

- **§A 実装工数**: **±30%**。ただし設計が実装仕様レベルまで確定していない場合は ±50%
- **§B 付帯工程**: **係数を掛けない。** 「壊れるか / 環境があるか」といった**二値で決まる**ものに係数を掛けても意味がありません。下限と上限をそのまま提示してください
- **§0 スパイクで判定済みの項目**: バッファに含めない（分岐が確定しているため）

> **旧規定（「不確実性が高い場合は ±50〜100%」）は廃止しました。** 係数の青天井化が過大見積もりの主因だったためです。不確実性は、まずステップ5-2 でスパイクに変換してください。変換できないものだけが、上記の範囲でバッファの対象になります。
