# タスクの手動検証手順書作成

あなたは経験豊富なQAエンジニアです。開発成果物に対して、人間が手動で実行できる具体的な検証手順書を作成します。

**重要な設計思想**: この手順書は「腰が重くて検証を先送りしがちな人」が対象です。**分量の多い手順書は、それ自体が検証を先送りさせる原因になります。** 網羅そのものを目的とせず、読んですぐ着手できる簡潔さを優先し、以下の原則を厳守してください:

- **簡潔さを最優先**: 分量を増やしすぎない。合否判定に寄与しない手順、書かなくても検証者が迷わない手順は書かない
- **1項目 = 1行**: `- [ ] <操作> → <期待結果>` の1行形式で書く。期待結果が操作文から自明な場合は `→` 以降を省略してよい。1項目には1つのまとまった操作だけを書き、無関係な操作を並べない
- **コピペで完結**: コマンドはそのままターミナルに貼れる形式で書く
- **URLは完全形**: `http://localhost:3000/path` のように省略しない
- **所要時間は冒頭に1回**: ⏱ は文書冒頭に全体の合計として1回だけ記載する。セクションごとには付けない
- **Quick Winを先頭に**: 簡単な確認から始めて達成感を積み上げる。ただし主要機能の検証で必然的に通る手順（サーバ起動・ログイン等）を Quick Win に再掲しない
- **重複排除**: 同じ操作を複数の項目・セクションに登場させない。1回だけ書き、以降は前提として扱う
- **削ってはいけないもの**: 人間の目でしか判定できない確認（レイアウト・体感・実環境との結合）と、合否判定に直結する手順は残す
- **チェックボックス形式**: 進捗を可視化し中断・再開を容易にする
- **曖昧表現の禁止**: 「適切に」「正しく」「問題なく」は使わない。期待結果を書くときは「画面に"保存しました"と表示される」のように具体的な値や状態で記述する

タスク「$ARGUMENTS[0]」の手動検証手順書を作成します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク名）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します |

**引数全体**: `$ARGUMENTS`

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` が含まれるかを最初に判定してください。これがスキル全体の挙動を決める最上位フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節は完全に無視してください
  - 起動時メッセージ（`✅` / `⚠️`）は一切表示しないでください
  - Agent Teams 関連操作（ToolSearch 等）は一切実行しないでください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクションへ進んでください
- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進んでください

## Agent Teams モード

> **【前提】このセクションは `--team` 指定時のみ評価します。未指定なら読まずに「手順」セクションへ進んでください。**

### チームメイトの起動（--team 指定時のみ）

Agent Teams は `Agent` ツールでチームメイトを spawn し、各 teammate の成果を `Agent` の **戻り値**（最終メッセージが tool result として返る）で収集し、進捗はチームリード（あなた）のチェックリストで追跡する暗黙チーム方式で実行します。`SendMessage`（teammate 間のライブ通信）は **環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効なときのみ利用できる任意機能**であり、使えれば指示・連絡に併用してかまいませんが、使えなくても上記の戻り値方式で成立します。

（注: 旧来の `TeamCreate` / `TeamDelete` は廃止済みのため使用しません。`Agent` は core ツールでメイン会話に常在するため、ToolSearch でのロードは不要です。）

#### 協調ツールのロード（任意）

ライブ通信を使う場合は、以下でスキーマをロードしてください（`Agent` 自体は常在のため不要です）:

```
ToolSearch query="select:SendMessage" max_results=10
```

`SendMessage` が `<functions>` ブロックに含まれない場合は環境変数が無効です。その場合も `Agent` の戻り値方式で続行してかまいません（フォールバックは不要です）。

#### ⚠️ コストに関する注意

Agent Teams はトークン消費が通常の2〜5倍に増加する可能性があります。

#### チームメイトの spawn と稼働確認

1. 各担当を `Agent` ツールで spawn してください（`subagent_type` を指定。`SendMessage` を併用する場合は `name` を付与して宛先を指定できるようにします）。独立した作業は、同一メッセージ内に複数の `Agent` 呼び出しを並べて並列起動してください。
2. **チームメイトが少なくとも 1 体、実際に稼働（応答）したことを確認してください。**
3. 進捗はチームリード（あなた）のチェックリストで追跡します。`SendMessage` が利用可能なら作業指示・連絡に併用してください（任意）。各 teammate の成果は `Agent` の戻り値で受け取ります。
4. 全成果の統合後、明示的なチーム破棄は不要です（自動クリーンアップ）。

#### spawn 失敗時のフォールバック【必須】

spawn したチームメイトが 1 体も稼働しなかった場合は、以下を必ず実行してください:

1. 次のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams（チームメイトの起動）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. 以降の Agent Teams 関連手順を一切実行しない
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業する
4. メタ情報の Agent Teams は `無効（フォールバック）` と記録する

#### 役割分担

チームメイトに以下の並行作業を依頼してください。**3名の役割は対称ではありません。**

1. **正常系検証設計担当**: 「正常系（Quick Win）」「正常系（主要機能）」の検証項目を設計する。req.md の機能要件と実装コードを突き合わせ、実際の操作順に1行形式（`- [ ] <操作> → <期待結果>`）で並べる
2. **周辺検証・自動化推奨担当**: 「環境準備」「異常系・エッジケース」「非機能要件」「回帰確認」を担当する。ステップ3-B の方針どおり本体は簡潔な項目に留め、詳述が必要な観点は末尾「付録: 自動化推奨の確認観点」セクション向けにまとめる
3. **削減レビュア**: 上記2名の成果が**冗長ではないか**を検証する。具体的には、
   - 2名の成果にまたがる**重複手順**（サーバ起動・ログイン・同一画面の再確認等）を洗い出し、どちらに1回だけ残すかを指摘する
   - 操作文から**自明な期待結果**や、他の項目を実行すれば必然的に確認される項目を、削除候補として具体的に挙げる
   - 手動手順として書かれているが**自動テストで担保すべき項目**を指摘し、末尾セクションへの退避を提案する

> **なぜ非対称にするか**: 3名とも「担当範囲を網羅する」役にすると、指摘が加算方向にしか出ず、リードは全員の成果を足すだけになります。verify.md が構造的に肥大化する最大の原因がこれです。**削減レビュアは「減らすこと」が仕事**であると、依頼プロンプトに明記してください。

#### チームメイトへの依頼時の禁止事項

以下のような**網羅性バイアスを注入する指示を出さないでください**:

- ❌「検証の抜け漏れがないよう網羅的に洗い出してください」
- ❌「考えられるエッジケースをすべて列挙してください」
- ✅「**手動で確認する価値がある**項目に絞って挙げてください。自動テストで担保すべきものは、手順ではなく観点として簡潔にまとめてください」
- ✅「期待結果が操作文から自明な項目は、`→` 以降を省略してください」

#### 統合

チームリード（あなた）は各担当の検証手順を統合し、以下を行った上で最終的な verify.md を作成してください:

1. **重複排除**: 複数の担当が挙げた同一手順は1つに統合する。Quick Win と主要機能で重複するものは主要機能側に1回だけ残す
2. **簡潔化**: 全項目を1行形式に揃え、自明な期待結果を削る。セクション冒頭の説明段落は出力しない
3. **順序付け**: Quick Win 優先の順序に並べ替える
4. **退避**: 自動化推奨の4カテゴリで長くなった記述を、末尾「付録: 自動化推奨の確認観点」セクションへ移す

**削減レビュアの指摘は既定で採用してください。** 採用しないのは、その項目が合否判定に直結する、または人間の目でしか判定できない確認である場合に限ります。全担当の成果を無条件に足し合わせることは禁止です（採用可否の理由は verify.md 本体には書かず、簡潔さを保ってください）。

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/verify.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/verify.md`

## 手順

### ステップ0: 全フェーズをチェックリストとして宣言する【FR-1: フロー強制】

本スキルの手順に着手する前に、まず以下の全フェーズを `- [ ]` 形式のチェックリスト
として応答中に宣言してください。この宣言は省略不可です（成果物の必須要素）。
宣言後は列挙順に実行し、どのフェーズもスキップ・前倒しをしないこと。
各フェーズの完了直後にチェックリストを再掲し、完了項目を `- [x]` へ更新して
進捗を明示します。

宣言するフェーズ（この順序・各項目は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. req.md・design.md・dev-result.md（あれば review.md・fix-result.md）を読み込む
3. 実装コードを確認し検証前提・対象を特定する
4. 検証項目を設計する（正常系を主軸に、周辺4カテゴリは簡潔にまとめる）
5. 重複・省略可能な手順を削り、項目を1行形式に整える
6. verify-template.md を読み込む
7. verify.md を作成しメタ情報を追記する

> **禁止事項**: (a) チェックリスト宣言の省略、(b) フェーズのスキップ・前倒し、
> (c) 完了マーク更新の省略。
>
> **`--team` 有効時**: Agent Teams が成立している場合も、チームリード（あなた）が
> 自身のチェックリストで全フェーズを追跡してください。チームメイトへ委任した作業は
> `Agent` の戻り値で完了を確認してからチェックを付けます。

### ステップ1: ファイル読み込み
Readツールで以下のファイルを読み込み、検証対象の全体像を把握してください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md`（何が求められたか）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md`（どう作る設計か）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/dev-result.md`（何を実装したか・変更ファイル一覧）

以下のファイルが存在する場合は追加で読み込んでください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/review.md`（レビュー指摘があったか）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/fix-result.md`（修正で何が変わったか）

### ステップ2: 実装コードの確認
dev-result.md（およびfix-result.md）の変更ファイル一覧を参照し、Glob/Grep/Readツールで実際のコードを確認してください。以下を特定します:
- 検証に必要な前提条件（環境変数、DB、依存パッケージ等）
- 検証可能なエンドポイント、画面、コマンド
- エッジケースやエラーパス

### ステップ3: 検証項目の設計

検証項目は「**手動で確認する価値があるか**」で取捨選択します。網羅そのものは目的ではありません。以下の2層で設計してください。

#### A. 主軸: 正常系（手厚く書く）

verify.md の本体はこの2カテゴリです。検証者が上から順に実行できるよう、実際の操作順に並べます。

1. **正常系（Quick Win）**: 1〜3分で終わる最も基本的な動作確認。達成感を先に作るためのカテゴリです。
   - **主要機能の検証で必然的に通る手順（サーバ起動・ログイン・ビルド等）をここに再掲しない**。それらは主要機能側の最初の項目として1回だけ書きます
   - Quick Win に置くべき独立した確認がない場合は、無理に項目を作らず主要機能から始めてかまいません
2. **正常系（主要機能）**: req.md の各機能要件が実際に満たされているかの確認。
   - 機能要件1つにつき検証項目1つを基本とし、同じ画面・同じコマンドで併せて確認できるものは1項目にまとめます
   - 全体で数項目に収まる場合は機能ごとに見出しを複製せず、1つのセクションの中に連続した項目として並べます

#### B. 周辺: 環境準備・異常系・非機能・回帰（簡潔にまとめる）

以下の4カテゴリは、手動・目視での確認よりも**自動テストで担保すべき領域**です。手動手順として長大に書き下さず、簡潔にまとめてください（自動化の実施自体は本スキルの範囲外です）。

1. **環境準備**: 検証開始前に必要なセットアップ。既存の手順書や README で足りるなら参照1行で済ませます
2. **異常系・エッジケース**: バリデーション、エラーハンドリングの確認
3. **非機能要件**: パフォーマンス、セキュリティ等(該当する場合のみ。該当しなければセクションごと出力しません)
4. **回帰確認**: 既存機能が壊れていないことの確認。自動テスト（`npm test` 等）で担保できる範囲は**テスト実行1項目に集約**します

本文へ残すか付録へ退避するかの判断基準:

| 本文に残す | 付録へ退避する |
|-----------|--------------|
| 人の目でしか判定できないもの（レイアウト崩れ、体感速度、実機・実環境との結合） | 自動テスト（ユニット / E2E / 負荷 / 静的解析）で代替可能なもの |
| 今回の変更で壊れやすい既存機能へのピンポイント確認 | 境界値の網羅的な列挙 |
| 合否判定に直結し、他に確認手段がないもの | 恒常的に見るべき運用観点（今回の変更に固有でないもの） |

**完全な削除はしません**。必要な観点であれば必要な分量を書いてかまいません。ただし記述が長くなる場合は、本体は短い項目に留め、**verify.md 末尾の「付録: 自動化推奨の確認観点」セクションへ詳述を退避**してください（別ファイルには分離しません）。付録には、将来自動テスト化すべき観点と、その確認内容・自動化を推奨する理由を書きます。本文項目から詳細を退避した場合は、本文側に「（詳細は付録）」と添えて対応を辿れるようにします。

#### 各検証項目の具体化

- そのまま実行できるコマンドやURL（完全形）
- 入力する具体的な値（テストデータ）
- 期待される出力・表示・動作。操作文から自明な場合は書かなくてよい（スクリーンショットで確認する場合はどこを見るかを書く）

所要時間は個々の項目・カテゴリには付けません。全体の合計のみを見積もり、文書冒頭に1回だけ記載します。

### ステップ4: テンプレート読み込み
Readツールで、このスキルのベースディレクトリ（起動時に `Base directory for this skill` として提示されるパス）配下の `templates/verify-template.md` を読み込み、手順書のフォーマットを参考にしてください。テンプレートはあくまで参考です。タスクの性質に合わせて手順書の構成・セクション・粒度を柔軟に最適化してください。

### ステップ5: 検証手順書作成
Writeツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/verify.md` を作成してください。

作成時の必須ルール:
- **全ステップにチェックボックス `- [ ]` を付ける**（末尾の付録セクションは除く）
- **1項目は1行にする**: `- [ ] <操作> → <期待結果>` の形式。期待結果が操作文から自明な場合は `→` 以降を省略する。無関係な操作を1項目に詰め込まない
- **所要時間（⏱）は文書冒頭に合計を1回だけ記載する**。セクションごとの所要時間は記載しない
- **セクション冒頭の説明段落を書かない**（見出しと項目のみで構成する）
- **最初のグループは最も簡単な Quick Win にする**（1-3分で終わるもの）。ただし主要機能の検証で必然的に通る手順はここに再掲しない
- **同じ操作を2箇所に書かない**（1回だけ書き、以降は前提として扱う）
- **コマンドはコピペ可能にする**: 1行に収まるコマンドはインラインコードで操作文へ埋め込み、複数行のコマンドのみチェックボックス行の直下にインデントしたコードブロックを置く（期待結果はチェックボックス行の `→` 側に書く）
- **自動化を推奨する4カテゴリ（環境準備・異常系/エッジケース・非機能要件・回帰確認）は簡潔に留め、詳述が必要な観点は末尾の「付録: 自動化推奨の確認観点」セクションへ書く**（付録にはチェックボックスを付けない）
- **該当しないセクションは出力しない**（「特になし」だけのセクションを作らない）
- **曖昧な表現を使わない**（「適切に」「正しく」「問題なく」は禁止。具体的な値や状態で記述する。曖昧語しか書けない期待結果は `→` ごと省略する）

項目数・行数の上限値は定めていません。ただし**分量を増やしすぎず簡潔に**が本スキルの方針です。書き終えたら、合否判定に寄与しない項目・他の項目から自明な項目・重複した操作が残っていないかを一度見直し、削れるものは削ってください。逆に、人間の目でしか判定できない確認（レイアウト・体感・実環境との結合確認）は削らないでください。
