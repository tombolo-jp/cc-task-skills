# タスクの手動検証手順書作成

あなたは経験豊富なQAエンジニアです。開発成果物に対して、人間が手動で実行できる具体的な検証手順書を作成します。

**重要な設計思想**: この手順書は「腰が重くて検証を先送りしがちな人」が対象です。以下の原則を厳守してください:

- **1ステップ = 1アクション**: 「AしてBを確認」ではなく「Aする」「Bを確認する」に分ける
- **コピペで完結**: コマンドはそのままターミナルに貼れる形式で書く
- **URLは完全形**: `http://localhost:3000/path` のように省略しない
- **期待結果を明示**: 「正しく動作すること」ではなく「画面に"保存しました"と表示される」のように具体化
- **時間見積もり**: 各グループに所要時間を付け、心理的ハードルを下げる
- **Quick Winを先頭に**: 簡単な確認から始めて達成感を積み上げる
- **チェックボックス形式**: 進捗を可視化し中断・再開を容易にする
- **曖昧表現の禁止**: 「適切に」「正しく」「問題なく」は使わない。具体的な値や状態で記述する

タスク「$ARGUMENTS[0]」の手動検証手順書を作成します。

## 引数の解釈

このスキルは以下の引数を受け取ります:

- **第1引数（タスク名）**: `$ARGUMENTS[0]` — 必須。処理対象のタスク名。
- **オプション**: 第2引数以降に `--team` などのフラグが指定される場合があります。

### オプション一覧

| オプション | 説明 |
|-----------|------|
| `--team` | Agent Teams を有効化し、チームメイトと協調して作業を実行します |

**引数全体**: `$ARGUMENTS`

### 重要: `--team` の有無による分岐【最優先】

引数全体に `--team` という文字列が含まれているかを **最初に** 判定してください。
判定結果はスキル全体の挙動を決定する最上位の制御フラグです。

- **含まれない場合**:
  - 「Agent Teams モード」節（次節）は **完全に無視** してください
  - 起動時メッセージ（`✅ ...` / `⚠️ ...`）は **一切表示しない** でください
  - 環境変数確認・ToolSearch・TeamCreate などの Agent Teams 関連操作は **一切実行しない** でください
  - メタ情報の Agent Teams は `無効（指定なし）` と記録してください
  - 「手順」セクション以降の通常フローへ進んでください

- **含まれる場合のみ**:
  - 「Agent Teams モード」節へ進み、前提条件の確認手順を実行してください

## Agent Teams モード

> **【前提】このセクション以下の内容は `--team` が指定されている場合にのみ評価対象です。**
> `--team` が指定されていない場合は、ここから先を読まずに「手順」セクションへ進んでください。

### 前提条件の確認【必須実行】（--team 指定時のみ）

Agent Teams を使用するには、環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` が有効になっている必要があります。
**`--team` を検出した場合、必ず以下の手順で環境変数を確認してください。確認をスキップして「無効と判断する」ことは禁止です。**

#### 確認手順（必須）

1. Bashツールで以下のコマンドを実行する:
   ```bash
   printenv CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS || echo "__UNSET__"
   ```
2. 出力値を以下の判定ルールに従って解釈する:

   | 出力値 | 扱い |
   |--------|------|
   | `1` | 有効 |
   | `true`（大文字小文字問わず） | 有効 |
   | `__UNSET__` | 無効（未設定） |
   | 空文字列 | 無効（空値） |
   | 上記以外（例: `0`, `false`, `no` 等） | 無効（明示的に無効化） |

#### 判定が「有効」の場合

- ユーザーに「✅ Agent Teams が有効化されています。チームメイトを編成して並行作業を開始します（コストが通常の2〜5倍に増加する可能性があります）。」と表示する
- 後述「チーム編成と作業分担」へ進む
- メタ情報の Agent Teams は **「有効」** と記録する（ただし、実際にチームメイトが稼働した場合のみ。§稼働確認 参照）

#### 判定が「無効」の場合（フォールバック）

- ユーザーに以下のメッセージを **必ず** 表示する（省略・要約禁止）:

  > ⚠️ Agent Teams が有効化されていません。`~/.claude/settings.json` の `env` フィールドに `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` を設定してください。今回は通常モードで実行します。

- メッセージ表示後、単一エージェントモードで通常の手順を実行する
- メタ情報の Agent Teams は **「無効（フォールバック）」** と記録する

### ⚠️ コストに関する注意（--team 指定 + 環境変数有効時のみ）

Agent Teams はトークン消費が大幅に増加します。チームメイトの生成・管理に伴い、通常の2〜5倍のトークンを消費する可能性があります。

### チーム編成と作業分担（--team 指定 + 環境変数有効 + ツール利用可能時のみ）

#### ツール準備（必須・失敗時はフォールバック）

Agent Teams 用ツール（`TeamCreate`, `TeamDelete`, `SendMessage`, `TaskStop` 等）は deferred tools として扱われる場合があります。
**初回利用前に必ず以下を実行してスキーマをロードしてください:**

```
ToolSearch query="select:TeamCreate,TeamDelete,SendMessage,TaskStop" max_results=10
```

##### ツール準備の判定ルール【重要】

ToolSearch の結果を以下のいずれかに分類してください:

| 結果 | 扱い |
|------|------|
| `TeamCreate` が `<functions>` ブロックに含まれる | **次のステップ「チーム生成」へ進む** |
| `TeamCreate` が含まれない、または `<functions>` ブロックが空 | **ツール利用不可 — フォールバック実行** |
| ToolSearch 自体がエラー終了 | **ツール利用不可 — フォールバック実行** |

##### ツール利用不可時のフォールバック手順【必須】

ツールがロードできなかった場合は、以下を **必ず** 実行してください:

1. ユーザーに以下のメッセージを表示する（省略・要約禁止）:

   > ⚠️ Agent Teams ツール（TeamCreate 等）が現在の環境で利用できないため、Agent Teams モードを起動できません。今回は通常モードで実行します。

2. その後の Agent Teams 関連手順（TeamCreate / SendMessage / TeamDelete）を **一切実行しない**
3. 「手順」セクションへ進み、単一エージェントとして通常通り作業を遂行する
4. メタ情報の Agent Teams は **`無効（フォールバック）`** と記録する

##### チーム生成と稼働確認

ToolSearch で `TeamCreate` が利用可能と確認できた場合のみ、以下を実行してください:

1. `TeamCreate` で各担当チームメイトを生成する
2. `SendMessage` で各チームメイトに作業指示を送る
3. **チームメイトが少なくとも 1 体実際に稼働（応答）したことを確認する**
4. 全成果統合後、`TeamDelete` で整理する

##### 「TeamCreate は呼べたがチームメイトが spawn できない」場合

- TeamCreate 後に SendMessage が失敗する、もしくはチームメイトが応答しないなど **「空チーム状態」になった場合は Agent Teams 実行は成立していません**
- ただちに `TeamDelete` でクリーンアップし、上記「ツール利用不可時のフォールバック手順」と同じメッセージ表示・通常モード移行を行ってください
- メタ情報は **`無効（フォールバック）`** と記録してください（`有効` と記録することは禁止）

#### 役割分担

チームメイトに以下の並行分析を依頼してください:

1. **正常系検証設計担当**: 要件定義の各機能要件に対する正常系の検証手順を設計
2. **異常系・エッジケース検証設計担当**: バリデーション、エラーハンドリング、エッジケースの検証手順を設計
3. **非機能・回帰検証設計担当**: パフォーマンス、セキュリティ、既存機能への影響の検証手順を設計

#### 統合

チームリード（あなた）は各担当の検証手順を統合し、Quick Win 優先の順序に並べ替えた上で最終的な verify.md を作成してください。

> **注**: チームメイトが稼働せず、結果としてチームリード（あなた）が一人で全作業を完遂した場合、それは Agent Teams 実行が成立していない状態です。メタ情報は `無効（フォールバック）` と記録してください。

## パス解決ルール

**重要**: タスクファイルはプロジェクトルート配下に格納されています（`~/.claude/tasks/` ではありません）。

最初に Bash ツールで `pwd` を実行し、プロジェクトルートの絶対パスを取得してください。
以降のすべてのファイルパスは、取得したプロジェクトルートを先頭に付けた絶対パスで指定してください。

例: `pwd` → `/Users/yuki/dev/www/my-project` の場合
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/verify.md` → `/Users/yuki/dev/www/my-project/.claude/tasks/$ARGUMENTS[0]/verify.md`

## 手順

### ステップ0: 全フェーズを Task に登録する【FR-1: フロー強制】

本スキルの手順に着手する前に、まず以下の全フェーズを `TaskCreate` で一括登録してください。
登録順に実行し、どのフェーズもスキップ・前倒しをしないこと。各フェーズは着手直前に
`TaskUpdate` で `in_progress`、完了直後に `completed` へ更新します。

登録するフェーズ（この順序・各 subject は imperative 形）:

1. プロジェクトルートを pwd で解決する
2. req.md・design.md・dev-result.md（あれば review.md・fix-result.md）を読み込む
3. 実装コードを確認し検証前提・対象を特定する
4. 検証項目を設計する（環境準備〜回帰の6カテゴリ）
5. verify-template.md を読み込む
6. verify.md を作成しメタ情報を追記する

> **Task ツールが利用できない場合のフォールバック**: `TaskCreate` / `TaskUpdate` が
> 当該環境で利用できない場合は、上記フェーズ一覧を本文中のチェックリスト（`- [ ]`）として
> 保持し、各フェーズ完了を明示しながら順守してください。Task ツールの不在を理由に
> フェーズを省略しないこと。Task ツールの可用性は `ToolSearch query="select:TaskCreate,TaskUpdate"`
> で判定し、`<functions>` ブロックに両方が含まれれば利用可、含まれない／ToolSearch が
> エラー終了した場合は利用不可としてチェックリストへフォールバックします。フォールバック時は
> 「Task ツールが使えないため地の文チェックリストで進行します」と1行表示してから続行してください。
>
> **`--team` 有効時**: Agent Teams が成立している場合は、チーム共有タスクリスト上で
> 各フェーズを Task として扱います（フェーズ=親、todo 項目=子）。独自のフェーズ追跡は
> 共有タスクリストに統合してください。

### ステップ1: ファイル読み込み
Readツールで以下のファイルを読み込み、検証対象の全体像を把握してください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/req.md`（何が求められたか）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/design.md`（どう作る設計か）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/dev-result.md`（何を実装したか・変更ファイル一覧）

以下のファイルが存在する場合は追加で読み込んでください:
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/review.md`（レビュー指摘があったか）
- `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/fix-result.md`（修正で何が変わったか）

### ステップ2: 実装コードの確認
dev-result.md（およびfix-result.md）の変更ファイル一覧を参照し、Glob/Grep/Readツールで実際のコードを確認してください。以下を特定します:
- 検証に必要な前提条件（環境変数、DB、依存パッケージ等）
- 検証可能なエンドポイント、画面、コマンド
- エッジケースやエラーパス

### ステップ3: 検証項目の設計
以下の観点で検証項目を洗い出してください:

1. **環境準備**: 検証開始前に必要なセットアップ手順
2. **正常系（Quick Win）**: 最も基本的な動作確認（簡単で短時間なものを優先）
3. **正常系（主要機能）**: req.mdの各機能要件に対する検証
4. **異常系・エッジケース**: バリデーション、エラーハンドリングの確認
5. **非機能要件**: パフォーマンス、セキュリティ等の検証（該当する場合）
6. **回帰確認**: 既存機能が壊れていないことの確認

各検証項目について以下を具体化:
- そのまま実行できるコマンドやURL
- 入力する具体的な値（テストデータ）
- 期待される出力・表示・動作（スクリーンショットで確認する場合はどこを見るか）
- 所要時間の目安

### ステップ4: テンプレート読み込み
Readツールで、このスキルのベースディレクトリ（起動時に `Base directory for this skill` として提示されるパス）配下の `templates/verify-template.md` を読み込み、手順書のフォーマットを参考にしてください。テンプレートはあくまで参考です。タスクの性質に合わせて手順書の構成・セクション・粒度を柔軟に最適化してください。

### ステップ5: 検証手順書作成
Writeツールで `<PROJECT_ROOT>/.claude/tasks/$ARGUMENTS[0]/verify.md` を作成してください。

作成時の必須ルール:
- **全ステップにチェックボックス `- [ ]` を付ける**
- **各グループの冒頭に所要時間の目安を記載する**（例: "⏱ 約2分"）
- **最初のグループは最も簡単なQuick Winにする**（1-3分で終わるもの）
- **コマンドはコードブロック内に記載し、コピペ可能にする**
- **期待結果は「✅ 期待結果:」で始める**
- **1つのチェックボックスに複数のアクションを入れない**
- **曖昧な表現を使わない**（「適切に」「正しく」「問題なく」は禁止。具体的な値や状態で記述する）

メタ情報セクションに実行モデル名・実行日時・Agent Teams の値（有効 / 無効（指定なし） / 無効（フォールバック））を正確に記入してください。

## 完了後

「検証手順書が完了しました。verify.md に手動検証の手順を作成しました。チェックボックスを使って進捗を管理してください。」と表示してください。
