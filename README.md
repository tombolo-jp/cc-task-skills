# CC Task Skills

Claude Codeで段階的な開発ワークフローを支援するカスタムスキル集です。個々の機能追加や改修を「タスク」として管理し、要件定義→詳細設計→ToDoリスト→実装→レビュー→修正→検証を順に進めることで、品質の高いソフトウェア開発を実現します。

## インストール

1. このリポジトリをクローンします：
```bash
git clone https://github.com/tombolo-jp/cc-task-skills.git
```

2. Claude Codeのスキルディレクトリにコピーします：
```bash
cp -r cc-task-skills/skills/* ~/.claude/skills/
```

3. （任意・このリポジトリを編集する場合）整合性チェックの pre-commit フックを有効化します：
```bash
git config core.hooksPath scripts/hooks
```
スキル定義やドキュメントの定型文のズレをコミット時に自動検出できます（詳細は後述「整合性チェック」）。

## 使用方法

> **フロー強制について**: 各スキルは「手順」冒頭のステップ0で自身の全フェーズを Task として登録し、着手時に `in_progress`・完了時に `completed` へ遷移させながら進みます（進捗は Claude Code のタスク表示に反映されます）。これにより、フェーズのスキップ・実装の早すぎる着手・手順の取りこぼしを構造的に防ぎます（地の文の手順記述だけに頼りません）。Task ツールが利用できない環境では `- [ ]` 形式のチェックリスト宣言へ自動的にフォールバックします。登録は省略不可の必須要素として扱われます。

### 基本的なワークフロー

#### 1. **タスク環境準備** `/task-init`
```bash
/task-init your-task-name
/task-init your-task-name 'https://example.com/issue/123'   # URL から内容を自動取得
```
- **機能**: 新しいタスクの環境準備と要件ヒアリング
- **用途**: プロジェクトの新機能開発や、課題対応の開始時
- **作成ファイル**: `.claude/tasks/{your-task-name}/`

コマンド実行後、`init.md`ファイルに要件を簡潔に入力してください。この段階では、まだ詳細な要件定義は不要です。

**URL を指定した場合**（第2引数）: 指定 URL（Backlog / GitHub / Jira / 一般 Web ページ等）から **本文とコメントを改変せず全文転記**し、添付ファイルがあればサブディレクトリ `attachments/` に保存します。`init.md` の末尾には別セクションとして **要約** を付与します。

- **取得方法**: 可能な限り **MCP を優先**し、利用できなければ **ブラウザ優先のフォールバック**（claude-in-chrome → chrome-devtools → Playwright → WebFetch）で取得します。取得手段が一つも利用できない場合は **エラー終了し、`init.md` は作成しません**。
- **URL のクォート**: URL は `?` `&` `#` 等の特殊文字を含むため、**シングルクォートで囲むことを推奨**します（例: `'https://...'`）。シングルクォートは内部を一切展開しないため最も安全です。
- **部分取得時**: 取得方式の制約で一部（添付・コメント等）が取得できない場合でも処理は続行し、取得できなかった項目を `init.md` 内に明記します。

#### 2. **要件定義作成** `/task-req`
```bash
/task-req your-task-name
/task-req your-task-name --team   # Agent Teams モード（市場リサーチ・影響分析を並行実施）
```
- **機能**: 入力された要件から要件定義書を作成
- **用途**: 曖昧な要求を構造化された要件に変換
- **入力ファイル**: `.claude/tasks/{your-task-name}/init.md`
- **作成ファイル**: `.claude/tasks/{your-task-name}/req.md`

要件定義ファイル `req.md` が作成されます。末尾の「要確認事項」セクションに、確認が必要な項目が一問一答可能な箇条書きで一覧化されます。各項目の直下にインデントした子要素（`  - 回答内容`）で回答を追記し、次の `/task-req-update` で本文へ反映できます。

#### 3. **要確認事項の反映** `/task-req-update`
```bash
/task-req-update your-task-name
/task-req-update your-task-name --team   # Agent Teams モード（返信反映・整理確定を並行実施）
```
- **機能**: 「要確認事項」へのユーザー回答を req.md 本文へ反映し、確定版へ整理
- **用途**: 要件定義書の要確認事項を解消し、詳細設計へ進める状態にする
- **入力ファイル**: `.claude/tasks/{your-task-name}/req.md`
- **更新ファイル**: 同 `req.md`（専用報告書は作成せず直接更新）

各「要確認事項」項目の直下にインデント子要素で回答が付いていれば「解決済み」とみなし、その内容を本文へ反映して当該項目を削除します。回答のない項目は「未解決」として残置します。全項目が解決すると「要確認事項」セクション自体が削除され、req.md は確定版になります。未解決が残る場合は件数が提示されるので、回答を追記して再実行してください（「回答→再実行」ループ）。

#### 4. **詳細設計** `/task-design`
```bash
/task-design your-task-name
/task-design your-task-name --team   # Agent Teams モード（データ設計・API設計・セキュリティ設計を並行実施）
```
- **機能**: 既存システムを分析し、詳細設計を作成
- **用途**: 要件定義後の技術的設計
- **作成ファイル**: `.claude/tasks/{your-task-name}/design.md`

詳細設計ファイル `design.md` が作成されます。内容を確認し、必要に応じて修正してください。

#### 5. **ToDoリストと工数見積もり作成** `/task-todo`
```bash
/task-todo your-task-name
/task-todo your-task-name --team   # Agent Teams モード（分解・積み上げと削減レビューを並行実施）
```
- **機能**: 詳細設計に基づく実装作業のタスクを分解し、工数見積もりを実施
- **用途**: 開発作業の具体的な計画立案と、コードベースを熟知した開発者が手作業で実装する場合の工数算出（最少〜最大の範囲表示）
- **作成ファイル**: `.claude/tasks/{your-task-name}/todo.md`

ToDoリストと工数見積もりを統合したファイル `todo.md` が作成されます。各タスクの見積もり時間、リスク要因（不確実性レベル付き）、最少工数（楽観）・最大工数（悲観）の範囲見積もりを含みます。内容を確認し、必要に応じて修正してください。

**過大見積もりを防ぐ仕組み**（工数が実態の数倍に膨らむのを構造的に抑えます）:

| 仕組み | 内容 |
|--------|------|
| **3層構成** | §0 事前スパイク / §A 実装工数 / §B 付帯工程 に分けて計上。「コードを書く時間」が独立して見えるようにする |
| **サニティチェック** | 見積もり確定前に「コード行数 ÷ 実装工数」を計算。**30行/h を下回ったら過大と判定し差し戻す** |
| **スパイク変換** | 「未検証の外部API」等に青天井のバッファ（+0〜40h）を積まず、30分〜1時間で白黒つけるスパイクに変換して二択に落とす |
| **バッファ規定** | §A は ±30%（設計未確定なら ±50%）、§B は係数を掛けず下限〜上限をそのまま提示 |
| **計上しないもの** | 設計書の読解、既存コード調査、関係者調整（ブロッカーとして別管理）、カレンダー上の待ち時間 |
| **タスク粒度** | 8〜12件が目安。細分化は精度を上げず、切り上げの積み重ねで工数を膨らませるため |
| **アンカリング回避** | design.md に既存の見積もりがあっても、先に自分で積み上げてから照合する |

#### 6. **開発実行** `/task-dev`
```bash
/task-dev your-task-name
/task-dev your-task-name --team   # Agent Teams モード（独立したタスクを並行実装）
/task-dev task1,task2,task3       # 複数タスクを一括実行（タスクごとにコミット）
```
- **機能**: ToDoリストに基づく段階的な実装と開発完了報告書の作成
- **用途**: 実際の開発作業の実行
- **作成ファイル**: `.claude/tasks/{your-task-name}/dev-result.md`
- **特徴**:
  - todo.mdのタスクを自動的にdev-result.mdにチェックリスト形式でコピー
  - 各タスク完了時にチェックマーク [x] を付けて進捗を可視化

開発完了後、チェックリスト付きの進捗状況、実装概要、変更ファイル一覧、技術的詳細を含む報告書 `dev-result.md` が作成されます。

##### 複数タスクの一括実行（カンマ区切り）

第1引数をカンマ区切りにすると、1回の実行で複数タスクを **左から順に逐次実装** します。各タスクの実装は独立したサブエージェントへ委譲されるため、**タスク間でコンテキストが蓄積せず、後半のタスクほど品質が落ちるという問題が起きません**。

```bash
/task-dev task1,task2,task3
```

- **タスクごとにコミット**: 1タスクの実装が完了するたびに、タスク名そのままのメッセージでコミットします（`git commit -m "task1"`）。ステージングはそのタスクで変更したファイルのみに限定され、`git push` やブランチ操作は行いません
- **実行前の検証**: ワーキングツリーに未コミットの変更があると **何も実装せず中断** します（先にコミットまたは退避してください）。`design.md` / `todo.md` が無いタスクはスキップし、`dev-result.md` が既にあるタスクは実装済みとして自動スキップします
- **中断からの再開**: 途中で失敗した場合はその時点で中断しますが、完了済みタスクのコミットは維持されます。同じコマンドを再実行すると完了済みが自動スキップされ、失敗したタスクから再開できます
- **書式**: 区切りは `,` のみです。カンマ前後に空白を入れたもの（`task1, task2`）、空要素（`task1,,task2` / 末尾カンマ）はエラーになります
- **`--team` との排他**: 複数タスク指定時は `--team` を利用できません（サブエージェントはさらに別のサブエージェントを spawn できないため）。同時に指定した場合は警告を表示して `--team` を無視します
- **後方互換**: カンマを含まない従来の単一指定は、`--team` の挙動も含めて完全に従来どおり動作します

#### 7. **コードレビュー** `/task-review`
```bash
/task-review your-task-name
/task-review your-task-name --team   # Agent Teams モード（要件整合性・コード品質・セキュリティを並行レビュー）
```
- **機能**: 要件定義・設計書・ToDoリストと照合し、実装コードの品質を検証
- **用途**: 開発完了後のコードレビュー
- **入力ファイル**: req.md, design.md, todo.md, dev-result.md + 実装コード
- **作成ファイル**: `.claude/tasks/{your-task-name}/review.md`

レビュー報告書 `review.md` が作成されます。総合判定（修正不要/修正推奨/修正必須）、要件・設計との整合性、コード品質チェック、修正方針が含まれます。

#### 8. **修正実行** `/task-fix`
```bash
/task-fix your-task-name
/task-fix your-task-name --team   # Agent Teams モード（独立した修正箇所を並行修正）
```
- **機能**: レビュー指摘に基づいてコードを修正
- **用途**: コードレビュー後の修正作業
- **入力ファイル**: review.md, design.md
- **作成ファイル**: `.claude/tasks/{your-task-name}/fix-result.md`

修正報告書 `fix-result.md` が作成されます。指摘事項ごとの対応内容、変更ファイル一覧、動作確認結果が含まれます。

#### 9. **検証手順書作成** `/task-verify`
```bash
/task-verify your-task-name             # 既定: 自動実行を前提とした詳細なテストケース
/task-verify your-task-name --manual    # 人間向けの簡潔版
/task-verify your-task-name --team      # Agent Teams モード（3担当を並行実施）
```
- **機能**: 開発成果物に対する検証手順書を生成
- **用途**: 開発・修正完了後の検証（`/task-verify-run` による自動実行、または人手による手動検証）
- **入力ファイル**: req.md, design.md, dev-result.md（+ review.md, fix-result.md が存在する場合）
- **作成ファイル**: `.claude/tasks/{your-task-name}/verify.md`

**既定（詳細版）** では、`/task-verify-run` がそのまま自動実行できるテストケースが生成されます。文書先頭に機械可読な `## 検証前提`（ベース URL・起動コマンド・テストアカウント）を持ち、各項目は安定識別子 `` `V-nnn` `` 付きの多行形式（`前提` / `操作` / `入力` / `期待結果` / `自動化メモ`）で書かれます。**期待結果の省略は禁止**され、人の目でしか判定できない項目のみ `## 人手確認（自動化不可）` セクションへ分離されます。

**`--manual`（簡潔版）** では、従来どおり `` - [ ] `V-nnn` <操作> → <期待結果> `` の1行形式で生成されます（期待結果が操作から自明な場合は省略されます）。所要時間は文書冒頭に合計として1回だけ記載され、簡単なQuick Winから始まる構成で検証を始めやすくしています。

> **仕様変更（意図的な非互換）**: 既定の出力が簡潔版から詳細版へ変わりました。従来の出力が必要な場合は `--team` と併用可能な `--manual` を指定してください。また「付録: 自動化推奨の確認観点」セクションは**両モードとも廃止**されています（詳細版では実行可能な手順として本文へ統合されます）。

#### 10. **検証の自動実行** `/task-verify-run`
```bash
/task-verify-run your-task-name
```
- **機能**: verify.md の手順を自動実行し、失敗した項目を修正して再確認するループを回す
- **用途**: 検証手順書の作成後、実行そのものを Claude Code に任せる
- **入力ファイル**: `.claude/tasks/{your-task-name}/verify.md`
- **作成ファイル**: `.claude/tasks/{your-task-name}/verify-result.md`（+ verify.md への実行結果の書き戻し）
- **`--team` 非対応**: 指定しても警告を表示して無視されます

verify.md のチェックボックス項目をブラウザ自動化ツールで実行し、要修正事項を `verify-result.md` へチェックリストとして記録します。修正と再確認のループを**最大5回**まで回し、合格した項目は verify.md のチェックボックスへ書き戻します。

| 仕組み | 内容 |
|--------|------|
| **自動化手段の選択** | `playwright-cli` → Chrome DevTools for agents（CLI）→ Chrome DevTools MCP → Claude in Chrome の順に探索し、**最初に利用可能なものを採用**します。1つも使えない場合は、ブラウザ操作を1件も行わずに中断します |
| **自動確認が困難な項目のスキップ** | 目視・主観／系外リソース（実機・SSO・決済・本番）／保護措置で担保できない破壊的操作／実行の手掛かり不在、の4軸で判定し、判定不能もスキップします。スキップした項目と理由は verify.md 末尾へ記録されます |
| **副作用の抑止と原状復帰** | 検証前に**外部へのメール送信を遮断**し、**DB をバックアップ**します（環境を検出できた場合のみ）。検証後は DB を復元し、変更した設定も元に戻します。保護措置を検出できない環境では破壊的操作を自動実行しません |
| **安全境界** | **コミットしません**（インデックスにも触れません）。実行開始時に作業ツリーが dirty なら中断します。修正の採否は `git diff` を見てユーザーが判断します |
| **終了保証** | ループ上限5回に加え、2ループ連続で指摘内容が変化しない場合は早期中断します |
| **冪等な再開** | 中断しても完了済みの確認結果は残り、再実行すると続きから再開します |

> **コストに関する注意**: 本スキルは確認と修正のループを回すため、トークン消費が大きくなります。実行開始時に対象件数と上限ループ数が表示されます（確認入力は求められません）。

### ファイル構造

各タスクの出力は以下の構造で管理されます：
```
.claude/tasks/{your-task-name}/
├── init.md         # 要件ヒアリング（URL 指定時は取得内容を転記）
├── attachments/    # URL から取得した添付ファイル（添付がある場合のみ）
├── req.md          # 要件定義
├── design.md       # 詳細設計
├── todo.md         # ToDoリストと工数見積もり
├── dev-result.md   # 開発完了報告書
├── review.md       # コードレビュー報告書
├── fix-result.md   # 修正完了報告書
├── verify.md       # 検証手順書
└── verify-result.md # 検証実行結果（/task-verify-run 実行時）
```

**注意**: タスクファイルは常に**プロジェクトルート**配下の `.claude/tasks/` に作成されます（`~/.claude/tasks/` ではありません）。各スキルは実行時に `pwd` でプロジェクトルートの絶対パスを取得し、すべてのファイル操作に使用します。

### 使用するモデルの選択

各スキルはモデルを固定していません。実行時の**セッションモデルをそのまま継承**しますので、モデルを変えたい場合は `/model` で切り替えてからスキルを実行してください。

```bash
/model sonnet          # Sonnet に切り替え
/task-design my-task   # Sonnet で実行される

/model opus            # Opus に戻す
/task-review my-task   # Opus で実行される
```

`opus` / `sonnet` / `fable` などのエイリアスが指定できます。スキルは高精度な設計・レビュー・実装を要求するため **Opus 系を推奨**しますが、コストを抑えたい場合は Sonnet も選択できます。軽量モデルでは生成物の品質が落ちる点にご留意ください。

実際に使われたモデルは、各報告書の末尾「メタ情報」セクションに記録されます。

## Agent Teams オプション

全10スキルのうち、`task-init` と `task-verify-run` を除く8スキルが `--team` オプションに対応しています。このオプションを使うと、Claude Code の `Agent` ツールで複数のチームメイトを spawn し、並行して作業させます。`--team` を付けるだけで並列実行は起動します（環境変数の事前設定は不要）。トークン消費が増えますので、必要なときに限って `--team` を指定してください。

### （任意）SendMessage ライブ協調の有効化

チームメイト間の**ライブ通信**（`SendMessage`）を使いたい場合のみ、`~/.claude/settings.json` に以下を追加してください。これは **任意設定** であり、未設定でも `--team` による並列実行は問題なく起動します（`SendMessage` が使えない場合は各チームメイトの戻り値で成果を収集します）。

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

> 環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` がゲートするのは `SendMessage`（teammate 間ライブ通信）のみです。`Agent` による spawn と、チームリードの Task による進捗追跡はこの変数なしでも動作します。

### 使用例

```bash
/task-req my-task --team          # 市場リサーチ・影響分析を並行実施
/task-req-update my-task --team   # 返信反映・整理確定を並行実施
/task-design my-task --team   # データ設計・API設計・セキュリティ設計を並行実施
/task-todo my-task --team     # 分解・積み上げと削減レビューを並行実施
/task-dev my-task --team      # 独立したタスクを並行実装
/task-review my-task --team   # 要件整合性・コード品質・セキュリティを並行レビュー
/task-fix my-task --team      # 独立した修正箇所を並行修正
/task-verify my-task --team   # 詳細版: 正常系・周辺のテストケース設計と自動実行可能性レビューを並行実施
/task-verify my-task --manual --team  # 簡潔版: 正常系検証設計・周辺検証・削減レビューを並行実施
```

> `/task-dev` にカンマ区切りで複数タスクを指定した場合、`--team` は利用できません（警告を表示して無視されます）。複数タスクモードは各タスクをサブエージェントへ委譲してコンテキストを分離するため、その内部でチームメイトを spawn できないためです。

> `/task-verify-run` は `--team` に対応していません（確認手順と期待結果が既に定まっており合議の価値が乏しく、修正がリポジトリを書き換えるため並列実行が競合します）。指定した場合は警告を表示して無視します。

### コストに関する注意

Agent Teams はトークン消費が大幅に増加します（通常の2〜5倍）。必要な場合にのみ使用してください。

## 整合性チェック

このスキル集は include 機構を持たないため、Agent Teams 共通ブロックやフォールバック文言などの定型文が複数のファイルに重複しています。`scripts/check_consistency.py`（Python 3 標準ライブラリのみ）は、これらの重複箇所のズレを機械的に検出します。

```bash
python3 scripts/check_consistency.py        # 不一致のみ表示
python3 scripts/check_consistency.py -v     # 全7検査の結果を表示
bash scripts/test/run_consistency_tests.sh  # 検査自体の回帰テスト
```

検査内容は frontmatter / Agent Teams 共通ブロック / フォールバック文言 / メタ情報フォーマット / 環境変数 JSON / テンプレート参照 / フロー進捗管理（廃止済みツール名の再混入検出と、ステップ0 が Task 方式＋フォールバックを備えることの構造確認）の7種です。終了コードは `0`=整合 / `1`=不整合 / `2`=実行エラー。

- **ローカルフック**: `git config core.hooksPath scripts/hooks` で pre-commit フックを有効化すると、対象ファイル変更時に自動でチェックが走ります（対象外の変更は高速スキップ、緊急時は `git commit --no-verify` でバイパス可能）。整合性チェックはこのローカルフックで担保します（GitHub Actions による CI は使用していません）。
