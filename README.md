# CC Task Skills

Claude Codeで段階的な開発ワークフローを支援するカスタムスキル集です。個々の機能追加や改修を「タスク」として管理し、タスク環境準備→要件定義→要確認事項の反映→設計・計画→実装（レビュー・修正を内包）→検証（手順書の作成と自動実行）を順に進めることで、品質の高いソフトウェア開発を実現します。

## インストール

1. このリポジトリをクローンします：
```bash
git clone https://github.com/tombolo-jp/cc-task-skills.git
```

2. Claude Codeのスキルディレクトリにコピーします：
```bash
cp -r cc-task-skills/skills/* ~/.claude/skills/
```

3. （推奨）進捗管理用 Task ツールを有効化します。`~/.claude/settings.json` に以下を追加してください：
```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"
  }
}
```

> **なぜ必要か**: 全スキルは進捗管理の主経路として Claude Code の Task ツール（`TaskCreate` / `TaskUpdate` / `TaskList` / `TaskGet`）を使いますが、**Claude Code 2.1.233 以降、一定バージョン以上のモデルではこれらが既定で無効**になりました（Opus 4.8 以上 / Sonnet 5 以上 / Fable 5 以上が対象。2.1.232 までは既定で有効でした）。この環境変数を設定すると、モデルによらず有効化されます。
>
> 未設定でもスキルは動作しますが、チェックリスト宣言方式へフォールバックするため、Claude Code のタスク表示・スピナーに進行中フェーズが出なくなります。設定後は `--version` の再確認は不要ですが、反映されない場合は Claude Code を再起動してください。

4. （任意・このリポジトリを編集する場合）整合性チェックの pre-commit フックを有効化します：
```bash
git config core.hooksPath scripts/hooks
```
スキル定義やドキュメントの定型文のズレをコミット時に自動検出できます（詳細は後述「整合性チェック」）。

## 使用方法

> **フロー強制について**: 各スキルは「手順」冒頭のステップ0で自身の全フェーズを Task として登録し、着手時に `in_progress`・完了時に `completed` へ遷移させながら進みます（進捗は Claude Code のタスク表示に反映されます）。これにより、フェーズのスキップ・実装の早すぎる着手・手順の取りこぼしを構造的に防ぎます（地の文の手順記述だけに頼りません）。Task ツールが利用できない環境では `- [ ]` 形式のチェックリスト宣言へ自動的にフォールバックします。登録は省略不可の必須要素として扱われます。Task ツールを主経路で使うには前述「インストール」手順3の `CLAUDE_CODE_ENABLE_TODO_TOOLS` の設定を推奨します。

### 基本的なワークフロー

#### 1. **タスク環境準備** `/task-init`
```bash
/task-init your-task-name
/task-init your-task-name 'https://example.com/issue/123'   # URL から内容を自動取得
```
- **機能**: 新しいタスクの環境準備と要件ヒアリング
- **用途**: プロジェクトの新機能開発や、課題対応の開始時
- **作成ファイル**: `.claude/tasks/{your-task-name}/`

コマンド実行後、`init.md`ファイルに要件を簡潔に入力してください。この段階では、まだ詳細な要件定義は不要です。

**URL を指定した場合**（第2引数）: 指定 URL（Backlog / GitHub / Jira / 一般 Web ページ等）から **本文とコメントを改変せず全文転記**し、添付ファイルがあればサブディレクトリ `attachments/` に保存します。`init.md` の末尾には別セクションとして **要約** を付与します。

- **取得方法**: 可能な限り **MCP を優先**し、利用できなければ **ブラウザ優先のフォールバック**（claude-in-chrome → chrome-devtools → Playwright → WebFetch）で取得します。取得手段が一つも利用できない場合は **エラー終了し、`init.md` は作成しません**。
- **URL のクォート**: URL は `?` `&` `#` 等の特殊文字を含むため、**シングルクォートで囲むことを推奨**します（例: `'https://...'`）。シングルクォートは内部を一切展開しないため最も安全です。
- **部分取得時**: 取得方式の制約で一部（添付・コメント等）が取得できない場合でも処理は続行し、取得できなかった項目を `init.md` 内に明記します。

#### 2. **要件定義作成** `/task-req`
```bash
/task-req your-task-name
/task-req your-task-name --team   # Agent Teams モード（市場リサーチ・影響分析を並行実施）
```
- **機能**: 入力された要件から要件定義書を作成
- **用途**: 曖昧な要求を構造化された要件に変換
- **入力ファイル**: `.claude/tasks/{your-task-name}/init.md`
- **作成ファイル**: `.claude/tasks/{your-task-name}/req.md`

要件定義ファイル `req.md` が作成されます。末尾の「要確認事項」セクションに、確認が必要な項目が一問一答可能な箇条書きで一覧化されます。各項目の直下にインデントした子要素（`  - 回答内容`）で回答を追記し、次の `/task-req-update` で本文へ反映できます。

一覧化されるのは**回答によって設計・実装が変わる問いだけ**です。日程・費用・体制・対人連絡・「この理解で正しいか」といったメタ質問・コードベースを読めば判る事項は、回答しても `task-design` / `task-dev` の作業が変わらないため一覧化されません（判定に迷う項目は残す側に倒します）。結果として0件になった場合は、「要確認事項」セクション自体が出力されません。なお顧客が述べた日程・予算・体制の**事実**は、確認事項としては問わずとも `## 制約事項` 等へ従来どおり記録されます。

#### 3. **要確認事項の反映** `/task-req-update`
```bash
/task-req-update your-task-name
/task-req-update your-task-name --team   # Agent Teams モード（返信反映・整理確定を並行実施）
```
- **機能**: 「要確認事項」へのユーザー回答を req.md 本文へ反映し、確定版へ整理
- **用途**: 要件定義書の要確認事項を解消し、詳細設計へ進める状態にする
- **入力ファイル**: `.claude/tasks/{your-task-name}/req.md`
- **更新ファイル**: 同 `req.md`（専用報告書は作成せず直接更新）

各「要確認事項」項目の直下にインデント子要素で回答が付いていれば「解決済み」とみなし、その内容を本文へ反映して当該項目を削除します。回答のない項目は「未解決」として残置します。全項目が解決すると「要確認事項」セクション自体が削除され、req.md は確定版になります。未解決が残る場合は件数が提示されるので、回答を追記して再実行してください（「回答→再実行」ループ）。

#### 4. **詳細設計と工数見積もり** `/task-design`
```bash
/task-design your-task-name
/task-design your-task-name --team   # Agent Teams モード（設計3担当 → 見積もり2担当の2フェーズで実行）
```
- **機能**: 既存システムを分析して詳細設計を作成し、続けて実装タスク一覧と工数見積もりまでを1回の実行で作成
- **用途**: 要件定義後の技術的設計と、開発作業の具体的な計画立案（コードベースを熟知した開発者が手作業で実装する場合の工数を最少〜最大の範囲で算出）
- **作成ファイル**: `.claude/tasks/{your-task-name}/design.md`

詳細設計ファイル `design.md` が作成されます。設計章（§1〜§11: 影響分析・アーキテクチャ・コンポーネント・ファイル構造・データ・API・インターフェース・エラーハンドリング・パフォーマンス・セキュリティ・テスト戦略）に加えて、**`## 12. 実装タスク一覧`**（各タスクに `T-001` 形式の識別子を採番。対象ファイル・作業・依存・完了条件・見積もり時間を持つ）と **`## 13. 工数見積もり`**（リスク要因、最少工数（楽観）・最大工数（悲観）の範囲見積もり）を含みます。内容を確認し、必要に応じて修正してください。

`## 12. 実装タスク一覧` は、後続の `/task-dev` が機械的に読み取るセクションです。`T-nnn` の識別子を介して、実装の進行と、レビューフェーズでの完了照合が行われます。

設計と見積もりの間には**設計確定線**があり、設計章を確定させてから実装タスク一覧と工数見積もりを作成します（見積もりの都合で設計を書き換えることはありません）。`--team` を指定した場合も、まず設計3担当（データ設計・API設計・セキュリティ/パフォーマンス）を並列で走らせて設計章を確定させ、その完了後に見積もり2担当（分解・積み上げ担当／削減レビュア）を起動する**2フェーズ逐次**で動作します。

**過大見積もりを防ぐ仕組み**（工数が実態の数倍に膨らむのを構造的に抑えます）:

| 仕組み | 内容 |
|--------|------|
| **3層構成** | §0 事前スパイク / §A 実装工数 / §B 付帯工程 に分けて計上。「コードを書く時間」が独立して見えるようにする |
| **サニティチェック** | 見積もり確定前に「コード行数 ÷ 実装工数」を計算。**30行/h を下回ったら過大と判定し差し戻す** |
| **スパイク変換** | 「未検証の外部API」等に青天井のバッファ（+0〜40h）を積まず、30分〜1時間で白黒つけるスパイクに変換して二択に落とす |
| **バッファ規定** | §A は ±30%（設計未確定なら ±50%）、§B は係数を掛けず下限〜上限をそのまま提示 |
| **計上しないもの** | 設計書の読解、既存コード調査、関係者調整（ブロッカーとして別管理）、カレンダー上の待ち時間 |
| **タスク粒度** | 8〜12件が目安。細分化は精度を上げず、切り上げの積み重ねで工数を膨らませるため |
| **アンカリング回避** | req.md 等に既存の見積もりが記載されていても、先に自分で積み上げてから照合する |

#### 5. **開発実行（レビュー・修正を内包）** `/task-dev`
```bash
/task-dev your-task-name
/task-dev your-task-name --team   # Agent Teams モード（独立したタスクを並行実装／レビューを観点3分割・3体で並列）
/task-dev task1,task2,task3       # 複数タスクを一括実行（タスクごとにコミット）
```
- **機能**: 詳細設計に基づく段階的な実装と、**続けて実行されるレビュー・修正ループ**、および開発完了報告書の作成
- **用途**: 実際の開発作業の実行と、その場でのコードレビュー・修正
- **入力ファイル**: design.md（必須）+ todo.md（存在する場合のみ）
- **作成ファイル**: `.claude/tasks/{your-task-name}/dev-result.md`
- **特徴**:
  - design.md の実装タスク一覧（`T-nnn`）を自動的にdev-result.mdにチェックリスト形式でコピー
  - 各タスク完了時にチェックマーク [x] を付けて進捗を可視化
  - 実装後、**レビュー → 修正 → 再レビューのループを最大2周**まで自動実行（2周目は修正必須の指摘が残った場合のみ）

**`design.md` 単独で実装に着手できます。** 実装順は design.md の実装タスク一覧（`T-nnn`）の採番順です。実装タスク一覧を持たない旧形式の design.md の場合は、設計章から実装単位を抽出して `## 12. 実装タスク一覧` をその場で追記し、追記した旨を表示してから着手します。

以前のバージョンで作成した `todo.md` が残っているタスクでは、**design.md と todo.md の両方を必ず参照**します（後方互換）。両者が矛盾する場合は design.md を正とし、その旨を dev-result.md へ記録します。

開発完了後、チェックリスト付きの進捗状況、実装概要、変更ファイル一覧、技術的詳細を含む報告書 `dev-result.md` が作成されます。レビュー・修正の記録も同じ `dev-result.md` へ追記されます（専用の報告書は作成しません）。

##### レビュー・修正ループ（実装に続けて自動実行）

実装が終わると、**同じ実行の中で**レビューと修正のループが走ります。レビューを省略する導線は提供していません。

- **レビューは必ず別コンテキストへ委譲されます**。実装した本人がレビューすると「直前の自分の結論を否認したくない」というバイアスが働き、指摘が過少になる（＝欠陥を見逃す）方向へ構造的に偏るためです。委譲先には `req.md` / `design.md` / **レビュー対象ファイルのパスと変更行範囲だけ**が渡され、`dev-result.md`（実装者の自己申告）も**差分本文**も渡されません。隔離が「読まないでください」という指示ではなく「そもそも渡らない」という構造になっています
- **委譲は `name` を付けない同期サブエージェント委譲（戻り値で成果を受領）で行われます**。戻り値は「応答末尾の ` ```json ` フェンス」を契約とし、スキル本体が必須キー・語彙・型を検証します。語彙外の値は**危険側へ倒さない向き**へ丸められ（例: 語彙外の優先度は「高」として扱う）、丸めた事実が記録されます。形式が崩れていた場合は**1回だけ再委譲**し、なお崩れていれば「未受領（＝検査されなかった）」として扱います。未受領には最大3回のバックオフ再送（15秒 / 60秒 / 180秒）がかかります
- **レビュー担当の体数は固定です**。`--team` 無効なら **1体**が観点①〜⑤すべてを、有効なら **3体**が観点3分割で担当します。ファイル数・行数に応じた分割ファンアウトは行いません。1体あたりの担当量の上限（40ファイル / 6,000行）を超えた場合は、超過分が**未レビューとしてパスで全件列挙**されます（黙って落ちることはありません）
- **「指摘0件」と「未確認」が区別されます**。各レビュー担当は「実際に見た範囲」と「見られなかった範囲」を申告する義務があり、1体でも成果が返らなかった場合はその担当範囲が**未確認範囲**として `dev-result.md` へパスで列挙されます。1体も返らなかった場合の終了区分は「レビュー未実施（委譲不成立）」であり、**「指摘0件」とは記録されません**
- **指摘には安定識別子 `R-nnn` が付きます**。欠陥類型は9値の固定語彙（`requirement_unmet` / `design_deviation` / `task_incomplete` / `correctness` / `security` / `error_handling` / `test_missing` / `maintainability` / `other`）から選ばれ、優先度（高＝必須／中・低＝推奨）が機械的に決まります
- **ループ上限は2周**で、2周目は1周目で修正必須の指摘が残った場合にのみ回ります。`task-verify` の自動実行（上限3）より少ないのは、レビューには「実際に動かした結果」という外部の証拠源がなく、同一入力に対する同一モデルの再判断にすぎないためです。加えて、2周連続で指摘内容が変化しない（停滞）・指摘が増えた（退行）・修正でコードが1行も変わらない、のいずれかを検出すると早期中断します
- **却下には証拠が要ります**。指摘を却下する場合は5類型（事実誤認／仕様どおり／スコープ外／既存パターン準拠／推奨のため対象外）のいずれかと、ファイル:行や設計書の原文引用といった外部参照可能な証拠を `dev-result.md` へ残す必要があります。証拠を書けない却下は却下として認められず、未解決の修正必須として扱われます
- **修正しないものも握り潰しません**。要件・設計の変更が必要なもの、安全境界に触れるもの、推奨どまりのものは「保留」「記録のみ」として記録され、完了時に区分別に提示されます
- **複数タスクモードでも委譲されます**。コミットされるのは**未解決の修正必須が0件になった場合のみ**で、レビュー・修正は実装と同一のコミットに含まれます（1タスク1コミット）。ただしレビューが不成立だった場合・範囲が不完全だった場合は、その事実を `dev-result.md` とコミットメッセージの**本文**へ明記したうえでコミットされます（**件名はタスク名のまま**であり、従来と1バイトも変わりません）
- **終了区分は9値**です: `全指摘解消` / `修正推奨のみ残存` / `ループ上限到達` / `停滞による早期中断` / `退行検出` / `無変更による中断` / `修正予算超過` / `レビュー未実施（委譲不成立）` / `レビュー範囲不完全`

> **レビューループの収束は品質の証明ではありません。** 外部の証拠源がないため、「指摘が0件になった」ことを合否判定としては扱いません。**本当の合否判定は `/task-verify`（動的検証）が持ちます。**

##### 複数タスクの一括実行（カンマ区切り）

第1引数をカンマ区切りにすると、1回の実行で複数タスクを **左から順に逐次実装** します。各タスクの実装は独立したサブエージェントへ委譲されるため、**タスク間でコンテキストが蓄積せず、後半のタスクほど品質が落ちるという問題が起きません**。

```bash
/task-dev task1,task2,task3
```

- **タスクごとにコミット**: 1タスクの実装が完了するたびに、タスク名そのままのメッセージでコミットします（`git commit -m "task1"`）。ステージングはそのタスクで変更したファイルのみに限定され、`git push` やブランチ操作は行いません
- **実行前の検証**: ワーキングツリーに未コミットの変更があると **何も実装せず中断** します（先にコミットまたは退避してください）。`design.md` が無いタスクはスキップし、`dev-result.md` が既にあるタスクは実装済みとして自動スキップします
- **中断からの再開**: 途中で失敗した場合はその時点で中断しますが、完了済みタスクのコミットは維持されます。同じコマンドを再実行すると完了済みが自動スキップされ、失敗したタスクから再開できます
- **書式**: 区切りは `,` のみです。カンマ前後に空白を入れたもの（`task1, task2`）、空要素（`task1,,task2` / 末尾カンマ）はエラーになります。受け付けるオプションは `--team` だけで、**未知のオプションは黙って無視せずエラー**になります（`--tema` のような誤記がそのまま実行へ落ちると、レビュー・修正ループがリポジトリのコードを書き換えてしまうためです）
- **`--team` との排他**: 複数タスク指定時は `--team` を利用できません（サブエージェントはさらに別のサブエージェントを spawn できないため）。同時に指定した場合は警告を表示して `--team` を無視します
- **後方互換**: カンマを含まない従来の単一指定は、`--team` の挙動も含めて完全に従来どおり動作します

#### 6. **検証手順書の作成と自動実行** `/task-verify`
```bash
/task-verify your-task-name             # 既定: 詳細なテストケースを生成し、続けて自動実行
/task-verify your-task-name --manual    # 人間向けの簡潔版を生成するのみ（自動実行なし）
/task-verify your-task-name --run-only  # 既存 verify.md の自動実行のみ（再開・再実行の導線）
/task-verify your-task-name --team      # 生成フェーズを Agent Teams で実行（3担当を並行）
```
- **機能**: 開発成果物に対する検証手順書を生成し、**その手順をそのまま自動実行**して失敗した項目を修正・再確認する
- **用途**: 開発・修正完了後の検証（既定は自動実行まで、`--manual` は人手による手動検証用）
- **入力ファイル**: req.md, design.md, dev-result.md（`## レビュー指摘一覧` / `## レビュー・修正ログ` / `## task-verify へ引き継ぐ事項` を含む）。旧バージョンで作成したタスクに限り、残っている旧レビュー・修正報告書も追加入力として読み込みます
- **作成ファイル**: `.claude/tasks/{your-task-name}/verify.md`、`.claude/tasks/{your-task-name}/verify-result.md`（自動実行時）

**既定（詳細版）** では、そのまま自動実行できるテストケースが生成されます。文書先頭に機械可読な `## 検証前提`（ベース URL・起動コマンド・テストアカウント）を持ち、各項目は安定識別子 `` `V-nnn` `` 付きの多行形式（`前提` / `操作` / `入力` / `期待結果` / `自動化メモ`）で書かれます。**期待結果の省略は禁止**され、人の目でしか判定できない項目のみ `## 人手確認（自動化不可）` セクションへ分離されます。生成に続けて、その手順を自動実行し、要修正事項を `verify-result.md` へチェックリストとして記録します。修正と再確認のループを**最大3回**まで回し、合格した項目は verify.md のチェックボックスへ書き戻します。

**`--manual`（簡潔版）** では、`` - [ ] `V-nnn` <操作> → <期待結果> `` の1行形式で生成されます（期待結果が操作から自明な場合は省略されます）。所要時間は文書冒頭に合計として1回だけ記載され、簡単なQuick Winから始まる構成で検証を始めやすくしています。**このモードは生成のみで、自動実行は行いません。**

**`--run-only`** は生成を行わず、既存の verify.md をそのまま自動実行します。中断からの再開や、修正後の再確認に使います。`--manual` との同時指定はエラーです。

| 仕組み（自動実行フェーズ） | 内容 |
|--------|------|
| **自動化手段の選択** | `playwright-cli` → Chrome DevTools for agents（CLI）→ Chrome DevTools MCP → Claude in Chrome の順に探索し、**最初に利用可能なものを採用**します。1つも使えない場合は、ブラウザ操作を1件も行わずに自動実行のみを中断します（生成済みの verify.md は残ります） |
| **自動確認が困難な項目のスキップ** | 目視・主観／系外リソース（実機・SSO・決済・本番）／保護措置で担保できない破壊的操作／実行の手掛かり不在、の4軸で判定し、判定不能もスキップします。スキップした項目と理由は verify.md 末尾へ記録されます |
| **副作用の抑止と原状復帰** | 検証前に**外部へのメール送信を遮断**し、**DB をバックアップ**します（環境を検出できた場合のみ）。検証後は DB を復元し、変更した設定も元に戻します。保護措置を検出できない環境では破壊的操作を自動実行しません |
| **安全境界** | **コミットしません**（インデックスにも触れません）。実行開始時に作業ツリーが dirty なら、**verify.md を生成する前に**中断します。修正の採否は `git diff` を見てユーザーが判断します |
| **終了保証** | ループ上限3回に加え、2ループ連続で指摘内容が変化しない場合は早期中断します |
| **冪等な再開** | 中断しても完了済みの確認結果は残り、`--run-only` で再実行すると続きから再開します |

> **コストに関する注意**: 既定モードは本スキル群で最もトークンを消費します。生成に着手する前と、実行対象の確定後の2回、消費量に関する警告が表示されます（いずれも確認入力は求められません）。手順書だけが欲しい場合は `--manual` を指定してください。

> **仕様変更（意図的な非互換）**: 既定の出力が簡潔版から詳細版へ変わり、さらに生成に続けて自動実行まで行うようになりました。従来どおり手順書だけが欲しい場合は `--manual` を指定してください。また「付録: 自動化推奨の確認観点」セクションは**両モードとも廃止**されています（詳細版では実行可能な手順として本文へ統合されます）。検証の自動実行を担っていた旧スキルは本スキルへ統合され、`--run-only` が同じ役割を担います。

### ファイル構造

各タスクの出力は以下の構造で管理されます：
```
.claude/tasks/{your-task-name}/
├── init.md         # 要件ヒアリング（URL 指定時は取得内容を転記）
├── attachments/    # URL から取得した添付ファイル（添付がある場合のみ）
├── req.md          # 要件定義
├── design.md       # 詳細設計 ＋ 実装タスク一覧 ＋ 工数見積もり
├── dev-result.md   # 開発完了報告書 ＋ レビュー指摘一覧 ＋ レビュー・修正ログ
├── verify.md       # 検証手順書
└── verify-result.md # 検証実行結果（/task-verify の自動実行時）
```

実装タスク一覧と工数見積もりは `design.md` の `## 12.` / `## 13.` セクションに含まれます（専用のファイルは作成しません）。同様に、レビュー指摘と修正の記録も `dev-result.md` に含まれます。以前のバージョンで作成した `todo.md` が残っているタスクでは、`/task-dev` がそれも併せて読み込みます。

以前のバージョンで作成したタスクには、旧レビュー・修正報告書の2ファイルが残っていることがあります。これらは**読まれず・変更されず・削除されず**そのまま残ります（検出時に1回だけ告知されます）。過去の実行記録であって現行スキルの入力仕様ではないためです。

**注意**: タスクファイルは常に**プロジェクトルート**配下の `.claude/tasks/` に作成されます（`~/.claude/tasks/` ではありません）。各スキルは実行時に `pwd` でプロジェクトルートの絶対パスを取得し、すべてのファイル操作に使用します。

### 使用するモデルの選択

各スキルはモデルを固定していません。実行時の**セッションモデルをそのまま継承**しますので、モデルを変えたい場合は `/model` で切り替えてからスキルを実行してください。

```bash
/model sonnet          # Sonnet に切り替え
/task-design my-task   # Sonnet で実行される

/model opus            # Opus に戻す
/task-dev my-task      # Opus で実行される
```

`opus` / `sonnet` / `fable` などのエイリアスが指定できます。スキルは高精度な設計・レビュー・実装を要求するため **Opus 系を推奨**しますが、コストを抑えたい場合は Sonnet も選択できます。軽量モデルでは生成物の品質が落ちる点にご留意ください。

実際に使われたモデルは、各報告書の末尾「メタ情報」セクションに記録されます。

## Agent Teams オプション

全6スキルのうち、`task-init` を除く5スキルが `--team` オプションに対応しています。このオプションを使うと、Claude Code の `Agent` ツールで複数のチームメイトを spawn し、並行して作業させます。`--team` を付けるだけで並列実行は起動します（環境変数の事前設定は不要）。トークン消費が増えますので、必要なときに限って `--team` を指定してください。

### （任意）SendMessage ライブ協調の有効化

チームメイト間の**ライブ通信**（`SendMessage`）を使いたい場合のみ、`~/.claude/settings.json` に以下を追加してください。これは **任意設定** であり、未設定でも `--team` による並列実行は問題なく起動します（`SendMessage` が使えない場合は `name` を付けない同期委譲の戻り値で成果を収集します）。

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

> 環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` がゲートするのは `SendMessage`（teammate 間ライブ通信）のみです。`Agent` による spawn と、チームリードの Task による進捗追跡は、いずれもこの変数なしで動作します。

### 使用例

```bash
/task-req my-task --team          # 市場リサーチ・影響分析を並行実施
/task-req-update my-task --team   # 返信反映・整理確定を並行実施
/task-design my-task --team   # 設計3担当を並列 → 完了後に分解・積み上げと削減レビュー
/task-dev my-task --team      # 独立したタスクを並行実装／レビューを観点3分割・3体で並列（要件整合性・コード品質・セキュリティ）
/task-verify my-task --team   # 詳細版: 正常系・周辺のテストケース設計と自動実行可能性レビューを並行実施（生成フェーズのみ）
/task-verify my-task --manual --team  # 簡潔版: 正常系検証設計・周辺検証・削減レビューを並行実施
```

> `/task-dev` の `--team` は**実装フェーズとレビューフェーズに適用**されます。**修正フェーズは対象外**で、常に単一エージェントが逐次修正します（共有資源の競合を避けるためと、並列化するとどの修正がどの指摘に対応したのかが失われて終了保証が成立しなくなるためです）。

> `/task-dev` にカンマ区切りで複数タスクを指定した場合、`--team` は利用できません（警告を表示して無視されます）。複数タスクモードは各タスクをサブエージェントへ委譲してコンテキストを分離するため、その内部でチームメイトを spawn できないためです。

> `/task-verify` の **自動実行フェーズ**は `--team` の対象外です（確認手順と期待結果が既に定まっており合議の価値が乏しく、修正がリポジトリを書き換えるため並列実行が競合します）。`--team` が効くのは手順書を生成するフェーズだけで、`--run-only` と併用した場合は警告を表示して無視します。

### コストに関する注意

Agent Teams はトークン消費が大幅に増加します（通常の2〜5倍）。必要な場合にのみ使用してください。

> **`/task-dev` のレビュー委譲は `--team` の有無と独立に必ず行われます。** `--team` を指定しない場合はレビュー担当が **1 体**（観点①〜⑤すべて）、指定した場合は **3 体**（観点3分割）です。実装のみを行う場合に比べたトークン消費は、おおむね 1.3〜1.8 倍（`--team` 指定時は 2〜3 倍）です。

## 整合性チェック

このスキル集は include 機構を持たないため、Agent Teams 共通ブロックやフォールバック文言などの定型文が複数のファイルに重複しています。`scripts/check_consistency.py`（Python 3 標準ライブラリのみ）は、これらの重複箇所のズレを機械的に検出します。

```bash
python3 scripts/check_consistency.py        # 不一致のみ表示
python3 scripts/check_consistency.py -v     # 全8検査の結果を表示
bash scripts/test/run_consistency_tests.sh  # 検査自体の回帰テスト
```

検査内容は frontmatter / Agent Teams 共通ブロック / フォールバック文言 / メタ情報フォーマット / 環境変数 JSON / テンプレート参照 / フロー進捗管理（**廃止済みツール名・廃止済みスキル起動名**の再混入検出と、ステップ0 が Task 方式＋フォールバックを備えることの構造確認）／Dynamic Workflows のランタイム API 名の再混入検出の8種です。終了コードは `0`=整合 / `1`=不整合 / `2`=実行エラー。

- **ローカルフック**: `git config core.hooksPath scripts/hooks` で pre-commit フックを有効化すると、対象ファイル変更時に自動でチェックが走ります（対象外の変更は高速スキップ、緊急時は `git commit --no-verify` でバイパス可能）。整合性チェックはこのローカルフックで担保します（GitHub Actions による CI は使用していません）。
