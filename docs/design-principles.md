## 設計原則: フローは Task ツールで明示的に追跡する

> **失効した方針（2026-07-22 〜 2026-08-06）**: 「進捗追跡の記述にツール固有名を持ち込まない（役割語で記述する）」という方針を置いていたが、**撤回する**。主経路をツールに置く以上、ロード対象と呼び出し規約を特定するためにツール名の明示は避けられないためである。

### 前提: Task ツールの提供はモデル依存でゲートされる（2026-08-16 追記）

**Claude Code 2.1.233 以降、進捗管理用の4ツールは一定バージョン以上のモデルでは既定で無効**である。したがって本原則の主経路を実際に通すには、`~/.claude/settings.json` へ次の env 設定が必要になる（README.md「インストール」手順3と同一内容）。

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"
  }
}
```

判定ロジックの実測結果（CLI バイナリの解析による）:

| バージョン | Task ツールの `isEnabled` | 既定の挙動 |
|---|---|---|
| 〜2.1.232 | `CLAUDE_CODE_ENABLE_TASKS !== false` かつリモートのキルスイッチに載っていないこと | **有効** |
| 2.1.233〜 | 上記に加え、モデルがしきい値表（Opus 4.8 / Sonnet 5 / Fable 5 / Mythos 5）**以上**なら、リモートのオプトインフラグ（既定 false）か `CLAUDE_CODE_ENABLE_TODO_TOOLS` が必要 | しきい値以上のモデルでは**無効** |

- **決定要因はモデルであってバージョンではない**、という理解は 2.1.233 以降に限って正しい。2.1.232 までは Opus 5 でも Task ツールは提供されていた。
- リモートフラグはロールアウト状況で変わりうるため、**env 設定なしで有効な時期と無効な時期が混在する**。ステップ0 の2方式分岐（Task 方式 / チェックリスト方式）は今後も維持すること。
- この env 変数は Agent Teams の `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` とは**無関係**である（前者は進捗管理の主経路、後者は `SendMessage` ライブ通信の任意スイッチ）。

> **経緯（訂正）**: 2026-07-22 の改訂時、本原則は「フローは構造化チェックリストで明示的に追跡する」へ全面移行し、その理由を「Claude Code 側の仕様変更により Task ツールが提供されなくなり、主経路が恒久的に閉塞した」と記録していた。これは**事実誤認である**。当時観測された取得不可は特定バージョン（v2.1.217 / v2.1.218）における一時的な不具合を踏んだ可能性が高く、恒久的な仕様変更ではなかった。v2.1.223 では進捗管理用の4ツールがいずれも取得可能であることを実測で確認したため、Task 方式を主経路へ戻し、チェックリスト方式をフォールバックへ再配置した。

## 設計原則: git 操作は設定で明示された範囲だけ行う（2026-09-16 追加）

> 規範の正本は `CLAUDE.md` の同名節、逐語の規約は `skills/task-dev/references/git-ops.md`（`GB-1`〜`GB-23`）。本節はその**論証・受容したリスク・却下した代案・改訂履歴**である。

### 何を覆したのか

2026-09-16 以前、`task-dev` の `C-7` と「git 操作の安全境界」表は `git push` とブランチ作成・切替を**明示的に禁止**しており、**単一タスクモードは git を一切操作しなかった**（コミットは複数タスクモードのみ）。この改訂はその禁止を**無効化ではなく条件付き許可へ置き換える**。

動機は「クラウドセッションで Claude Code が自動採番するブランチ名（`claude/...`）より、`feature/<task_name>` のほうが人間に読みやすく、タスクとの対応も明確である」ことである。これは新しい命名規約の導入ではなく、**既存の慣習の自動化**である: 利用側リポジトリでは既に `feature/n461` / `feature/n574` / `feature/n623` / `feature/n628` / `feature/n643` のように `feature/<チケット番号>` 命名が運用されている。既定の prefix を `feature/` としたのはこの実績に基づく。

### なぜブランチ作成を `task-design` / `task-init` ではなく `task-dev` に置くのか

`task-design` は工数見積もりを兼ねており、**見積もりだけ提出して実装に着手しないケースが常態的にある**。ブランチ作成を `task-init` に置くと、実装が存在しないブランチだけが増え続ける。**ブランチは「実装に着手した」という事実に結び付けるべきであり、その事実が確定するのは `task-dev` の実行時である。**

この結果、要件定義・設計の成果物は起点ブランチ側に残り、実装のみが `feature/<task>` に載る。**この分裂は許容する**（設計だけで終わったタスクの成果物が起点ブランチに自然に集約されるため、むしろ望ましい）。

### `push` の既定値を実行環境から決めることの危うさと、その扱い

判別に使う信号（`CLAUDECODE` / `CLAUDE_CODE_REMOTE` / `CLAUDE_CODE_CONTAINER_ID` / `CCR_AGENT_PROXY_ENABLED`）は **Anthropic の公開仕様ではなく、将来変更されうる**。したがって設計の中心に置いたのは「判別が当たること」ではなく「**判別が外れたときに何が起きるか**」である。

- 判別は**3値**とし、2値へ丸めない。判別不能（副信号が1つだけ、`CLAUDECODE` 自体が不在など）は `push` を行わず、**未 push のコミットが残ることを目立つ警告として表示する**（ブランチ名と未 push のコミット数を添える）。
- 将来 `CLAUDE_CODE_REMOTE` が廃止されても、劣化の方向は「黙って成果が消える」ではなく「**警告が出て手動 push を促される**」である。**この方向性を壊す変更を加えてはならない。**
- 逆方向（判別不能を `true` へ倒す）を採らないのは、push が**外部へ反映される不可逆な操作**だからである。取り消せない操作の既定値を、値域の分からない信号の推測に委ねない。
- `CLAUDE_CODE_ENTRYPOINT` を判別に使わないのは、クラウドセッションがブラウザ・モバイル・`claude --cloud`・スケジュール実行からも起動でき、**値域が開いている**ためである。「`cli` 以外ならクラウド」は未観測の値に賭ける判定になる。表示・ログへの記録は有用なので参考情報としてのみ扱う。

**環境変数による利用者向け制御を設けなかった理由**: 環境変数は「どの層の設定でその挙動になったのか」が後から追跡できない。設定ファイルなら `判断根拠: .claude/task-skills.json（push を明示）` と表示でき、**挙動の説明責任がファイルに帰着する**。`.gitignore` への登録を挙動の前提にしないのも同じ理由で、登録漏れが「エラー」ではなく「意図の逆転」として静かに現れることを避けるためである。

### 単一タスクモードへ commit を導入したことの帰結（明文化した3点）

1. **`V-2`（ワーキングツリーの清浄性）を単一タスクモードにも適用する。ただし帰結は同一にしない。**
   - `G-0`（対象タスクのディレクトリを除外）・`G-1`（基準線は開始時の1回だけ）は両モード共通で適用する。`task-design` 直後に `.claude/tasks/<TASK>/**` が未コミットで残る副作用は、`G-0` の除外で吸収できる（**除外は対象タスクに限る**ため、他タスクのディレクトリが汚れていれば従来どおり検出される）。
   - そのうえで、dirty が残った場合の帰結を**ブランチ切替の有無**で分けた。切替を伴う場合は**中断**（未コミットの変更を別ブランチへ持ち込むことになり、切替自体が失敗しうる）。切替を伴わない場合は**警告のみで続行**する。
   - 単一タスクモードで全体中断まで要求しないのは、**コミットが最大1回**であり、かつステージ範囲が `C-1` / `C-9` により明示パスへ限定されているため、無関係な未コミット変更がコミットへ混入することが**構造的に起こらない**からである。複数タスクモードは N 個のコミットへ区分の破れが波及するため、従来どおり全体中断を維持する。
2. **`C-11`（コミットしてよい3経路）を単一タスクモードにも適用する。** 未解消の修正必須を残したままコミットしないという原則は、モードによらない。これを緩めると「レビュー済みという記録つきで欠陥がコミットされる」という、本スキルが防ごうとしている事象そのものが単一タスクモードで発生する。
3. **`C-10`（1タスクにつきコミット最大1回）と整合する。** 単一タスクモードのコミットはレビュー・修正ループの**終端後に1回だけ**行う（ステップC）。レビュー修正のための追加コミットは作らない。

### 受容したリスク

- **セッションの指定ブランチとの競合**: クラウドセッションでは「指定ブランチで開発せよ／明示的な許可なく他ブランチへ push するな」という指示が入ることがある。本スキルは設定ファイルによる指定を**利用者の明示的な許可**とみなし、これに優先させる。競合そのものは消えないため、`CLAUDE_CODE_BASE_REF` が取得でき作成ブランチと異なる場合は**その値を明示して報告**し、push 先を決定した1ブランチに限り、force push を行わないことで被害範囲を閉じた。
- **既定値を `commit: true` / `branch.create: true` としたこと**: 設定ファイルを置かない既存利用者にとって、単一タスクモードの挙動が変わる（従来はコミットしなかった）。`commit: false` で従来の挙動に完全に戻せること、コミットはローカルで取り消し可能であること、`push` の既定値だけは環境判別に委ねられること、そして**作業開始前に必ず判断根拠を表示すること**をもって許容した。
- **既存ブランチの再利用時に起点を自動マージしないこと**: 遅れたブランチの上に実装が載りうる。衝突解決という重い判断を暗黙に持ち込むほうが害が大きいと判断し、**状態の表示にとどめた**。

### 今後の論点（結論を出していない）

**`task-design` / `task-req` にも同じ設定ファイルに従う commit / push を導入すべきか。** 上記のとおり「設計だけで終わるケースが常態的にある」ことを前提に置いた以上、この経路は無視できない。クラウドセッションでは、設計・見積もりだけ行って実装に進まない場合、その成果物をコミットしないと**コンテナの破棄とともに失われる**。整理した論点は次のとおりで、**結論は保留する**。

| 論点 | 導入に傾く材料 | 見送りに傾く材料 |
|---|---|---|
| 成果物の保全 | クラウドセッションでは commit しない限り `req.md` / `design.md` が失われる。`task-dev` まで到達しないタスクほど失われやすい | 利用者が手動でコミットする経路は既にある。失う範囲はタスク成果物（`.claude/tasks/**`）に限られ、リポジトリ本体のコードではない |
| ブランチとの関係 | 設計成果物は起点ブランチへコミットすればよく、ブランチ作成を伴わないため `GB-10`〜`GB-16` の複雑さを負わない | 起点ブランチ（多くは統合ブランチ）へ直接コミットすることになり、リポジトリによっては保護ブランチで拒否される |
| dirty 判定 | `task-design` がコミットすれば、直後の `task-dev` が `G-0` の除外に頼らずに済む | 逆に `task-design` 自身が実行前 dirty で中断する規律を新たに要求することになり、設計フェーズの中断理由が増える |
| 一貫性 | 「成果物を作るスキルは成果物をコミットする」という規則のほうが説明しやすい | `task-verify` は**一切コミットしない**（修正の採否を利用者が `git diff` で判断する設計）。3スキルで挙動が三様になる |
| 権限の最小化 | — | 現在 git を操作するのは `task-dev` ただ1つであり、**操作の主体を増やさない**こと自体が安全性の資産である |

## 設計原則: 静的な確認と動的な確認を分界する（2026-10-19 追加）

> 規範の正本は `CLAUDE.md` の同名節と `skills/task-dev/SKILL.md`（「実行境界」・5-5・5-12）、`skills/task-verify/SKILL.md`（「確認の分界」・付録C）。本節はその**論証・参考にした事例・受容したリスク・改訂履歴**である。

### 何を覆したのか

改訂前の `task-dev` は、レビュー観点にテストの網羅性を含め、修正後にテスト・ビルドを実行して失敗を次のレビューへ戻していた（旧 `E-22`）。結果として `task-dev` のレビューは「`task-verify` を実行しなくても済む」ほど重くなり、両者は同じ範囲を二度確かめていた。

改訂後は**証拠の種類で担当を分ける**。`task-dev` は読んで判断できること（静的）だけを、`task-verify` は動かして初めて合否が決まること（動的）だけを確かめる。`task-dev` が確かめられなかったもの（読むだけでは確定できない指摘・後出しの指摘）は `dev-result.md` から明示的に引き継ぎ、`task-verify` は全件を検証項目にする。

### なぜ `task-dev` は開発環境を起動しないのか（ローカルセッションでも）

- **データ漏洩の経路を開かないため。** 開発環境には本番相当のデータ・実在の認証情報・メールや外部 API の連携設定が載っていることが多い。起動した瞬間に WP-Cron・キューワーカー・起動時フックが動き、レビューのつもりで外部へデータを送りうる。外部通信を棚卸しして遮断する仕組みは `task-verify` だけが持つため、**遮断なしに起動する主体を `task-dev` に作らない**。
- **クラウドとローカルで挙動を揃えるため。** クラウドセッションには開発環境も DB もない。ローカルでだけ追加の確認を行うと、同じタスクでもセッションの種類によってレビューの範囲と結果が変わり、`task-verify` の担当範囲が定まらない。
- **テストの実行もプロジェクトのコードの実行である。** ユニットテストでも、モックの漏れがあれば実在のキーで外部 API を叩きうる。境界を「開発環境の起動」ではなく「プロジェクトのコードの実行」に引いたのはこのためである。静的解析ツールも設定ファイルやブートストラップでコードを実行しうるため、例外を設けていない（例外を1つ認めると境界の判定が規則ではなく判断になる）。

### 受容したリスク

- `task-dev` の完了時点では、構文エラーやテストの失敗が残っている可能性がある。これは `task-verify` が既存の自動テスト・静的解析を実行して検出する（アセットのビルドは 2026-10-24 以降 `task-dev` が実行する。下記）。`task-dev` の完了報告で `task-verify` の実行を必ず案内する。
- 静的なレビューで「動かさないと分からない」と判断された指摘はコミットを止めない（`保留（要動的確認）`）。代わりに `task-verify` が全件を検証項目にし、その対応を生成直後の自己検査（E-24 の③）で機械的に確かめる。

## 設計原則: レビューループを3周以内で閉じる（2026-10-19 改訂）

### 参考にした事例と、その検討

Claude Code チームが社内のコードレビュー運用について公開した事例（2026-10 に SNS で紹介されたもの）には、次の観察と対策が含まれていた。

| 事例の内容 | 本スキル群での扱い |
|---|---|
| ある PR がエージェントのレビューと修正を一晩で50回以上往復し、最終的に著者が手で止めた | 採用。ループには**機械的な上限**が要る（従来から `LC-2` を持つ） |
| `git blame` で調べると、繰り返し指摘された問題の約59%は**初回のレビューで既に見えていたコード**に対するものだった。エージェントは修正が新たに入れたバグを探すより、古い問題を少しずつ追加で指摘していた | 採用。これが「上限を置いても終わらない」原因であり、上限だけでは解決しない。**1周目を出し切りの周、2周目以降を修正差分に起因する欠陥だけの周**とし、範囲外の新規指摘を `diffAnchor` で機械的に**後出し**と判定して修正対象から外した（`RS-0` / `RS-8` / `RS-9`） |
| 3回目で止めて、著者に一歩引いて方針を再考させる。それ以降は diff だけを見る | 採用。上限を **3周**とし、上限到達時の告知を「一歩引いた再検討」の案内へ改めた（5-19 経路①）。2周目以降の範囲を修正差分に限ることで「diff だけを見る」を構造化した |
| 人間がレビューするかを著者に選ばせず、分類器が変更のリスク（低/中/高）に応じて必要な人数（0/1/2人）を決める。エージェントの approve は人間に数えない。エージェントを指揮して PR を書いた人は必須レビュアーに数える | **一部のみ採用。** 「エージェントの approve は人間に数えない」は 5-20 に明記した（本スキルを実行した利用者が、その変更の最初の人間レビュー担当である）。リスク分類による人数の決定は採らない。本スキル群はブランチへのコミットまでを担い、PR の承認やマージの関門を持たないため、人数を決めても強制する手段がなく、判断だけが増えるためである |

### なぜ後出しを「破棄」ではなく「引き継ぎ」にするのか

後出しの指摘にも本物の欠陥は含まれうる（1周目の見落とし）。破棄すれば、レビュー済みという記録つきで欠陥が残る。修正すればループが延び、事例のとおり終わらなくなる。**ループを延ばさないことと、指摘を握り潰さないことを両立させる**ために、`R-nnn` を採番して記録し、`task-verify` が全件を動かして確かめる。委譲先へは「範囲外の欠陥も報告してよいが、後出しとして扱われこの周では修正されない」と伝える（指摘の抑制ではなく、行き先の明示である）。

### 独立レビューで見つかった抜け道と、その塞ぎ方（同日）

改訂の直後に、別コンテキストのエージェントへ差分全体のレビューを委譲し、次の抜け道が見つかった。いずれも「機械的に判定する」はずの箇所に、推定が残っていたことが原因である。

| 抜け道 | 塞ぎ方 |
|---|---|
| 前周から残る修正必須の指摘が、根拠アンカーの書き方が変わっただけで「新規」と判定され、修正差分の外にあるため後出しへ落ちる。元の `R-nnn` は再報告されないため「解消」と推定され、未解消のままコミットされる | 後出しと判定する前に、5-7 の3要素（ファイル・シンボル・欠陥類型）で既存の `R-nnn` と突き合わせて継承する（`N-5`）。さらに**前周の指摘の解消は、レビュー担当が `priorStatus` で `resolved` と明示した場合にのみ認め**、再報告が無いことを解消とみなさない（`RS-2`）。範囲を修正差分に絞ると、範囲外の未解決の指摘は「見られなかっただけ」で消えうるため |
| 静的な後出し（冗長なコメント等）も全件を検証項目にせよという規則と、読めば分かる項目を書くなという規則が衝突する | 振る舞いに現れない類型（`maintainability` / `design_deviation` / `test_missing` / `other`）の後出しに限り、理由つきで「検証項目にしない引き継ぎ」へ挙げられるようにした。振る舞いの欠陥になりうる類型は例外にできない |
| `git commit` / `git push` がプロジェクトのフック（husky 等）を起動し、テストや `ddev exec` を走らせる | フックを起動しうる git 操作はすべて `git -c core.hooksPath=/dev/null` で実行し、実行していないことを表示する（`GB-24`） |
| `ddev exec wp eval '…'` は引数がコンテナ内のシェルで再解釈され、`$` と括弧のクォートが壊れて確認が必ず失敗する | 確認用の PHP をファイルへ書き出し、`wp eval-file` で実行する |
| `docker compose -f` を明示すると `compose.override.yaml` が読まれなくなり、開発用の安全な設定を落として起動しうる | 既定のファイルと override をすべて並べ、最後に遮断用のファイルを重ねる |

### 判定を機械的にした理由

「2周目以降は新しい観点でレビューしない」という指示は改訂前から存在した（旧 `RS-0`）。それでも旧 `RS-3`（修正したファイルの全体）と旧 `RS-7`（70%超で全件再レビュー）が見直しの範囲をファイル単位へ広げていたため、既存コードへの指摘が入り込む余地が残っていた。改訂後は範囲を**修正前の写しとの行単位の差分**に限り、指摘ごとに原因の行（`diffAnchor`）を申告させ、その行が範囲に入るかを呼び出し元が判定する。指示ではなく構造で後出しを止めるという点で、レビューの構造的隔離と同じ考え方である。`diffAnchor` を解釈できない場合や写しを取れなかった場合は、後出しと判定しない側（修正の対象に残す側）へ倒す。

## 設計原則: 外部通信を遮断してから開発環境を起動する（2026-10-19 追加）

> 規範の正本は `CLAUDE.md` の同名節、逐語の規約は `skills/task-verify/references/egress-guard.md`。

### 何を覆したのか

改訂前の `task-verify` は、検証前提の解決（`run` スキルへの委譲による起動を含む）を保護措置の適用より**前**に行っていた。さらにメールの保護措置（P-MAIL）は、DDEV の Mailpit・wp-cli による SMTP プラグインの無効化・`pre_wp_mail` の mu-plugin・`.env` の書き換えから**先着1つ**を採用する方式で、wp-cli を使う手段は開発環境の稼働を前提にしていた。つまり、**起動した瞬間の送信は止められず**、Mailpit を採用した時点で SMTP プラグインや配信 API の連携は素通りしていた（DDEV の公式ドキュメントも、Mailpit は SMTP や外部の配信サービス連携を捕捉しないと明記している）。外部 API については保護措置そのものが無かった。

### 設計の要点と理由

| 要点 | 理由 |
|---|---|
| 棚卸しを起動より前に、読み取りだけで行う | 起動の瞬間に動くもの（定期実行・起動時フック・キュー）を止めるには、起動前に経路を知る必要がある。起動前は DB を読めないため、WordPress では設置済みのプラグインを全件「有効になりうる」とみなす |
| 遮断層はファイルの設置だけで適用できるものに限る | wp-cli や DB に依存する手段は起動後にしか使えず、「起動の瞬間」に間に合わない |
| Disable Emails の mu-plugin を第1層にする | 同梱のローダーは、本体が設置されていれば**有効化されていなくても**読み込む。mu-plugins は通常のプラグインより先に読み込まれるため、SMTP プラグインやメール配信プラグインが `wp_mail()` を置き換えるより先に、送信しない実装が確定する。DB の状態（有効・無効）に依存しないことが、起動前に適用できる理由である |
| 本スキル独自の遮断用 mu-plugin を重ねる | Disable Emails を置けなかった場合や、`wp_mail()` がコアのまま残った場合に備え、コアの `wp_mail()` の短絡・PHPMailer の Mailpit への付け替え・WP HTTP API の外部遮断を重ねる。`home_url()` を許可しないのは、本番の DB を取り込んだ環境で本番のドメインを指していることがあるため |
| 数えるのは確かめられた層だけ | `pre_wp_mail` はコアの `wp_mail()` しか呼ばない。SMTP プラグインが `wp_mail()` を置き換えていれば、フィルタが登録されていても何も止まらない。そこで起動直後に**どの実装が `wp_mail()` を握っているか**を確かめ、握っている実装に効く層だけを数える。効くかどうかを確かめられない防御（プロキシの環境変数・送信設定の差し替え・PHPMailer の付け替え）は重ねるが数えない。「二重三重に止める」は、適用する層の数としては満たし、ゲートの判定は確かめられた層だけで行う |
| DDEV では通信先をループバックへ向ける上書きファイルを重ねる | アプリ層を経由しない SDK・独自クライアントにも効く。ファイル名は `.ddev/docker-compose.zz-verify-run.yaml` とし、既存の上書きより後に読み込ませる |
| 経路ごとに層を数え、0層なら起動しない | 外部 API は種類が多く事前に列挙できない。だからこそ「判別できないものは除外せず数える」「覆えないなら起動しない」を規則にし、例外は通信先ごとの明示承認に限った |
| 確認は送信しない方法で行う | 「試しに送って届かないことを確かめる」は、遮断が効いていなければそのまま送信になる。関数の定義元・フィルタの戻り値・名前解決・環境変数で確かめる |
| 稼働中の環境を止めるのはゲートを通った後だけ | ゲートが不成立で起動しないなら、利用者の環境を止める理由がない。止める手段が無い環境は、遮断なしで起動されたまま検証することになるため中断する |
| 起動・再起動を伴う検証項目を実行しない | 遮断用の上書きを欠いた `docker compose up` やホスト上の開発サーバの起動は、遮断の外で環境を作り直す |
| 遮断層を外すのは停止の後だけ | 稼働中に外すと、その瞬間から遮断のない環境が動き続ける。検証前に稼働していた環境も再起動しない（遮断なしで起動する主体を作らないため） |
| DB の復元に失敗したら遮断層を残す | 検証中に作られた送信待ちのメール・通知が残っており、遮断なしで起動すると送られる |

### 受容したリスク

- **棚卸しは網羅を保証しない。** DB に保存された送信先（管理画面で設定された Webhook URL 等）は読めない。WordPress の HTTP API を通る送信は通信先を問わず止まるが、それ以外のクライアントで通信先が不明な経路は覆えず、承認がなければ起動しない（安全側）。環境変数のプロキシ設定は効くクライアントが限られるため、層として数えない追加の防御にとどめた。
- **WordPress のメールは Mailpit にも届かない。** Disable Emails は送信そのものを行わないため、メールの到達を合否に使う検証項目はスキップされる。送信を確実に止めることを優先した。
- **Disable Emails を wordpress.org から取得して実行する。** 取得元は公式配布 URL に限り、本スキルが設置したものだけを撤去する。
- **コンテナを持たず、WordPress でもないアプリ**では、確かめられる遮断層がほぼ無い。このためそうしたアプリでは、経路ごとの承認なしには開発環境を起動しない。

### アセットのビルドを `task-dev` へ戻した理由（2026-10-24）

「実行境界」はビルドも一律に禁止していたが、Sass / JS のビルドについては次の不都合が実際に生じた。

- **配信物が古いままコミットされる。** コンパイル後の CSS / JS をリポジトリで管理するプロジェクト（WordPress のテーマなど）では、`task-dev` のコミットにソースだけが入り、`task-verify` がビルドするまで配信物が更新されなかった。`task-verify` はコミットしないため、その差分は利用者が手で拾うしかなかった。
- **コンパイルエラーが検証の周回を消費する。** Sass の構文エラーや import の誤りは実装の欠陥であり、実装した主体が直すべきものである。`task-verify` で見つかると、開発環境を起動し遮断層を張ったうえでの修正ループ（上限3周）を、実装の手戻りに使うことになった。

ビルドだけを例外にできたのは、それが「プロジェクトのコードの実行」の中でも、**ソースを読んで出力ファイルを書くだけ**の処理だからである。開発環境・DB・アプリ本体のコード・認証情報を必要とせず、ホスト上の Node.js で完結するため、クラウドセッションでも実行できる。テスト（モックの漏れで外部 API を叩きうる）や SSR / SSG のビルド（ビルド時にアプリ本体のコードや DB・外部 API を実行しうる）とは危険の質が違う。

ただし、ビルドスクリプトもプロジェクトが定義したスクリプトであり、gulp のタスクや webpack のプラグインはデプロイやアップロードを行いうる（ソースマップのアップロード、FTP デプロイ、browser-sync など）。そこで例外の範囲を**判断ではなく規則**で引いた。

- 実行してよいのは、展開した全コマンドが許可ツール（`sass` / `postcss` / `webpack` / `vite build` / `esbuild` / `tsc` / `wp-scripts build` / `mix` など）だけで構成されるスクリプト1本に限る（`AB-7`）。
- gulp / webpack / Vite などの設定ファイルと `node <ファイル>` の対象は、実行前に読み、ネットワーク・子プロセスの使用やアップロード系プラグインが無いことを確かめる（`AB-8`）。
- 確かめられなければ実行せず `見送り` と記録し、`task-verify` が遮断層の内側でビルドする。**見送りはコミットを止めない**（ソースは変わっておらず、従来の挙動へ劣化するだけだから）。
- 依存のインストールは `node_modules/` が無い場合に限り、ロックファイルどおりに1回だけ行う（`AB-10`）。ロックファイルの無いプロジェクト・依存を変更したタスクではビルドしない。ローカルセッションの `node_modules/` は作り直さない。
- ビルドはメイン会話だけが行い、委譲先の禁止は緩めない（委譲プロンプトの禁止事項は逐語のまま）。

**失敗の帰結**はコミットの停止に置いた（`E-40`）。終了区分（9値）には加えず、`## 終了サマリ` の `- ビルド:` を別に持つ。終了区分を増やすと `RS-B` の完全一致判定・複数タスクモードのサマリ語彙・`C-11` の3経路がすべて連動して変わるためである。その代わり、終了区分が書かれていても `- ビルド:` が `失敗` なら再実行時にビルドだけをやり直す経路（`R-10`）を設けた。旧 `E-22` は再定義していない（旧 `E-22` は修正後のテスト・ビルドの失敗を次のレビューへ戻す行で、帰結が異なる）。

**受容したリスク**: 許可ツールの一覧は網羅ではなく、そこに無いツールを使うプロジェクトではビルドが見送られる（安全側）。また、許可ツールのプラグイン（PostCSS・Babel のプラグインなど）が内部で通信する可能性は、設定ファイルの読解だけでは完全には排除できない。クラウドセッションではエージェントのプロキシを通るが、ローカルセッションでは遮断層が無い。これは「ソースを読んで出力を書く」ツールを信頼する範囲として受容した。
